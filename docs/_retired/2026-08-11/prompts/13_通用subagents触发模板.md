请把当前任务按“主线程 + 少量 subagents 辅助”的方式执行，但不要把它变成多线程同时乱改代码。

目标不是多开几个线程显得很忙，而是：

- 让主线程保留架构判断和最终决策权
- 让子代理并行补足能力草案、探索、审查、文档核对、受控实现和测试修复
- 在不扩大范围的前提下，提高任务推进速度

当前项目后续以新平台逐步设计开发为主。可以吸收旧平台中有价值的内容和思想，但不要默认把任务拆成旧平台迁移或等比例重做。

## 一、何时适合触发 subagents

只有在满足以下至少 2 条时，才建议触发：

- 当前任务已经有明确边界
- 主线程已知道自己要产出的结果是什么
- 任务中存在可并行的只读探索、设计审查或契约审查工作
- 任务不是纯单文件小改
- 任务存在“能力草案 + 摸底 + 审查 + 实施 + 验证”这几类天然可拆分的子工作

以下情况不建议触发：

- 任务本身非常小，只改 1 到 2 个文件
- 主线程自己还没有搞清楚问题
- 多个子代理会同时修改同一批文件
- 任务本身仍在大范围摇摆

## 二、主线程必须先做的事

在触发任何子代理前，主线程先完成以下动作：

1. 阅读并遵守以下文件：
   - `AGENTS.md`
   - `docs/architecture/ai-first-execution-standard.md`
   - `docs/architecture/componentization-guardrails.md`
   - 与当前任务直接相关的设计文档、模块边界文档或实现说明

2. 用 3 到 6 句话写清当前任务：
   - 任务目标是什么
   - 本轮不做什么
   - 预期产出是什么
   - 需要哪些子视角辅助

3. 明确本轮边界：
   - 是否已有详细设计或实施计划
   - 是否涉及 Contracts / SDK / Kernel / Host / Shell / Module
   - 是否有明确允许修改的文件集合
   - 是否有最小验证路径

## 三、推荐子代理分工

默认最多同时使用 2 到 3 个子代理，通常不要超过 4 个。

### 1. `capability_designer`

适合负责：

- 将产品诉求、领域需求或旧平台中可借鉴的思想整理为新平台能力草案
- 区分平台公共能力、模块私有能力、产品专属流程和本轮非目标
- 判断能力更适合落在 Contracts / SDK / Kernel / Host / Shell / templates / modules 的哪个边界
- 输出小步可验证切片、取舍理由和建议方案

典型提问方式：

- 请把这个需求整理成新平台能力草案，区分平台公共能力、模块私有能力和产品专属流程。
- 请不要按旧平台等比例重做，只抽象可复用思想，并给出最小可验证切片。

输出要求：

- 能力边界
- 推荐归属
- 非目标
- 最小切片
- 风险和取舍

### 2. `platform_explorer`

适合负责：

- 只读扫描目录、项目、入口文件
- 列出影响范围
- 找关键类、关键接口、关键配置
- 定位当前新平台的宿主、运行时资产、扩展点和模块边界

典型提问方式：

- 请只读扫描与当前任务相关的目录，列出入口、关键类、依赖方向和风险点。
- 请不要改代码，只输出文件路径、类名和你认为必须阅读的文件。

输出要求：

- 文件路径
- 关键类或接口名
- 影响范围
- 可能风险

### 3. `design_reviewer`

适合负责：

- 审查详细设计或实施计划是否允许进入正式实现
- 检查是否满足 `AGENTS.md`、AI-first 五项检查、受控入口、验证方案、失败信号和回滚要求
- 发现缺少详细设计、范围混杂、Host/Shell 越界、元数据承载执行逻辑等阻塞项

典型提问方式：

- 请只读审查这份设计是否可以进入实现，优先列出阻塞项。
- 请检查入口、边界、验证、失败信号和回滚是否完整。

输出要求：

- 阻塞项
- 非阻塞风险
- 必须补齐的设计或计划内容
- 是否可以进入实现

### 4. `contract_reviewer`

适合负责：

- 审查模块边界
- 审查 Host / Kernel / Module / SDK 是否越界
- 审查契约设计是否可扩展
- 审查长期耦合风险

典型提问方式：

- 请只审查当前方案的契约边界和耦合风险，不要给样式建议。
- 请指出哪些地方会让后续模块难以扩展或导致跨模块耦合。

输出要求：

- 问题点
- 风险等级
- 建议修正方向
- 哪些地方可以接受，哪些地方不应继续

### 5. `docs_researcher`

适合负责：

- 核对版本行为
- 核对框架配置
- 核对认证、授权、路由、构建等官方文档
- 确认某项实现是否符合当前技术栈

典型提问方式：

- 请核对当前技术方案对应的官方文档行为，不要改代码。
- 重点核对认证中间件、路由守卫、构建行为或 EF Core 行为。

输出要求：

- 结论
- 依据
- 是否与当前方案冲突
- 建议保留或调整的点

### 6. `module_worker`

适合负责：

- 在父线程明确文件集合后，实现一个模块、能力或文件集合
- 补局部测试或最小验证
- 返回实际改动、验证结果、风险和回滚说明

典型提问方式：

- 你只负责修改以下文件集合，不要扩大范围，也不要修改 Host/Shell 内部结构。
- 请先阅读相关设计和附近实现模式，再做最小实现，并报告验证命令。

输出要求：

- 修改文件
- 实现摘要
- 验证结果
- 已知风险
- 回滚说明

### 7. `test_fixer`

适合负责：

- 最后阶段跑 build / test
- 修复编译、类型、lint、测试问题

典型提问方式：

- 只允许修复 build/test/lint/type 错误，不允许新增功能。
- 请输出失败原因、修复点和剩余问题。

输出要求：

- 哪个命令失败
- 失败原因
- 修复摘要
- 剩余问题

## 四、严格并行规则

必须遵守：

- 主线程负责最终方案与最终改动
- 子代理尽量只做只读能力设计、探索、设计审查、契约审查和文档核对
- 真正写代码的线程尽量只有一个
- 不允许两个 live thread 同时修改同一批文件
- 不允许子代理绕开 `scope-v1` 或当前详细设计擅自扩大范围
- `capability_designer` 和 `design_reviewer` 不负责最终拍板
- `module_worker` 只有在父线程给出明确文件集合和实施边界后才适合使用

如果发现以下情况，立即收敛：

- 子代理开始建议把旧平台能力等比例重做
- 子代理开始把任务扩展为完整业务平台
- 子代理开始混做架构重构、功能新增和兼容改造
- 多个子代理开始修改同一批文件

## 五、主线程执行顺序

建议按这个顺序推进：

1. 主线程明确目标、非目标和边界
2. 如需求尚未形成平台能力边界，先让 `capability_designer` 产出能力草案
3. 让 `platform_explorer` 只读摸底当前实现入口和影响范围
4. 详细设计或实施计划完成后，让 `design_reviewer` 做一致性审查
5. 涉及契约、SDK、Host/Shell 或模块边界时，让 `contract_reviewer` 做契约审查
6. 主线程汇总，做最终方案
7. 主线程或单个 `module_worker` 实施代码或文档修改
8. `test_fixer` 在最后统一验证与修复
9. 主线程输出最终摘要

## 六、输出格式要求

任务完成后，主线程必须统一输出：

- 本轮目标
- 实际改动
- 哪些子代理参与了
- 每个子代理提供了什么价值
- 验证结果
- 剩余风险
- 回滚思路

## 八、贴近本项目的示例

### 示例 1：新增一个平台公共能力

当前任务：

- 设计并实现一个新的平台公共能力，例如标准列表页宿主、模型元数据校验或插件治理能力。

本轮明确不做：

- 不把产品专属页面放进 Shell
- 不绕过 Contracts / SDK / templates / controlled entry points
- 不同时重构无关模块

建议分工：

- `capability_designer`：抽象能力归属、非目标和最小切片
- `platform_explorer`：定位当前相关入口、模板、SDK 和模块边界
- `design_reviewer`：确认详细设计是否满足 AI-first 五项检查
- `contract_reviewer`：审查契约、Host/Shell 边界和长期扩展风险
- `module_worker`：在明确文件边界后做最小实现
- `test_fixer`：最后修复验证失败

### 示例 2：吸收旧平台某个思想

当前任务：

- 参考旧平台中某个有价值的思想，为新平台设计对应能力。

本轮明确不做：

- 不搬旧框架启动代码
- 不隐式迁移旧运行时元数据
- 不把旧页面或旧流程直接放进平台 Shell

建议分工：

- `capability_designer`：只抽象可复用思想，输出新平台能力草案
- `platform_explorer`：只读定位当前新平台可承接的入口和边界
- `design_reviewer`：确认设计不是旧平台等比例重做
- `contract_reviewer`：审查新能力是否通过契约和 SDK 暴露
