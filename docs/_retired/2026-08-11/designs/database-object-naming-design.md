# 数据库对象命名规范设计

## 1. 背景

当前新平台的持久化实现同时存在两类命名风格：

- 首批手写 `ModelDefinition` 与已生成迁移中，很多表名、列名采用小写 `snake_case`
- 元数据试点链路与旧平台惯例中，存在 `EID / LID / PEID / CEID / ENAME / ECODE` 这类平台协议字段

随着后续更多表进入 `model` 驱动的持久化链路，如果不尽快统一命名规则，仓库会继续累积“同一层语义却有多种命名方式”的问题，增加 AI 生成、人工维护、结构比对和更新数据结构工具的复杂度。

当前项目还有两个现实约束：

- 表和列数量还不多，且尚未形成大量真实业务依赖，具备较低成本的统一窗口
- 团队更看重规则足够简单、容易执行，而不是为了极少发生的 rename 场景长期维护多套名称

## 2. 目标

- 为新平台数据库表名、列名、模型名、代码名建立一套统一且长期稳定的命名规则
- 避免同时维护“逻辑名 + 物理名”两套现行名称，降低 authoring 与评审成本
- 保留平台级对象标识协议字段的稳定语义，不把它们退化为普通业务字段
- 为后续 `model` authoring、migration、schema diff、更新数据结构工具提供清晰基础

## 3. 非目标

- 本设计不在本轮直接批量改造现有全部表和列
- 本设计不重新设计 `EID` 值的编码协议
- 本设计不展开 DTO 自动生成的具体实现机制，只定义 DTO 命名、生成方向与输出约束
- 本设计不讨论数据库索引、约束、存储类型的完整规则，只聚焦命名规范

## 4. 设计约束

- 规则必须足够简单，让人工和 AI 在小上下文内都能稳定执行
- 普通业务字段不长期维护第二套现行物理名
- rename 属于低频动作，应通过显式历史名承接，而不是为低频动作牺牲日常简单性
- 平台协议字段是协议资产，不按普通业务字段命名习惯处理

## 5. 命名方案

### 5.1 总体原则

新平台默认采用“单一现行名称”策略：

- 模型名使用 `PascalCase`
- 代码名使用 `PascalCase`
- 表名使用 `PascalCase`
- 普通列名使用 `PascalCase`

这意味着新建模型时，默认不再额外维护：

- 独立 `tableName`
- 独立 `columnName`

除非进入明确的历史兼容场景，否则现行名只有一套。

### 5.1.1 当前 metadata 契约约束

按当前仓库已有 metadata 契约，模型与字段层继续只保留：

- `Name`
- `HistoryName`

不新增以下现行命名字段：

- `TableName`
- `ColumnName`

也就是说：

- 模型当前名称直接承担模型名与表名语义
- 字段当前名称直接承担字段名与列名语义
- 历史兼容仍只通过 `HistoryName` 表达

这样可以保证命名规范直接落到现有 metadata 结构上，而不是先设计一套新字段、再要求实现层额外判断是否启用。

### 5.2 平台协议字段

以下平台协议字段继续保留全大写写法，不改为普通 `PascalCase`：

- `EID`
- `LID`
- `PEID`
- `CEID`
- `ENAME`
- `ECODE`

原因如下：

- 它们不是普通业务字段，而是平台统一对象协议与内建语义的一部分
- 它们已经在旧平台约定、当前元数据 projector、仓储读取逻辑和迁移链路中形成事实协议
- 保持全大写有利于把“协议关键字”和“普通业务字段”显式区分开

### 5.3 普通业务字段

普通业务字段统一使用 `PascalCase`，例如：

- `Id`
- `DisplayName`
- `Description`
- `ModuleId`
- `CreatedAt`
- `UpdatedBy`

不建议新增以下风格：

- 全大写业务字段，例如 `DISPLAYNAME`
- 下划线业务字段，例如 `display_name`
- 混合缩写风格，例如 `DisplayNAME`

### 5.4 表名规则

新建表统一使用 `PascalCase`，并直接使用模型语义名作为表名，例如：

- 模型 `Role` -> 表 `Role`
- 模型 `ConfigItem` -> 表 `ConfigItem`
- 模型 `PersonUserLink` -> 表 `PersonUserLink`

本设计不要求表名复数化，也不引入额外前缀拼装规则。模块归属应优先通过目录、模块边界、契约与代码组织表达，而不是继续把物理表名做成一套额外命名系统。

### 5.5 列名规则

普通列名直接使用字段名，例如：

- 字段 `DisplayName` -> 列 `DisplayName`
- 字段 `ModuleId` -> 列 `ModuleId`
- 字段 `CreatedAt` -> 列 `CreatedAt`

平台协议字段保持协议写法，例如：

- 字段 `EID` -> 列 `EID`
- 字段 `PEID` -> 列 `PEID`

## 6. 为什么不采用双命名

本设计明确不把“逻辑名”和“现行物理名”长期拆成两套，原因如下：

- 现实中表名、列名 rename 极少发生，不值得为了低频场景让所有日常 authoring 都变复杂
- 一旦规范允许长期同时维护两套现行名称，人工往往会为了省事直接写成一样，最终仓库会出现两种风格并存
- AI 和人工评审时，需要频繁判断“这是逻辑名、物理名还是旧名”，理解成本会被放大
- 更新数据结构工具、schema diff、migration 生成会被迫长期处理更多分支

因此，默认策略应是：

- 现行名只保留一套
- 历史兼容只在需要时显式声明历史名

## 7. 历史兼容规则

当旧表、旧列需要接入新规范时，允许使用 `historyName` 承接历史名称。

`historyName` 的作用仅限于：

- 告诉 schema diff / migration 工具“旧名称是什么”
- 支撑显式 rename 识别
- 帮助旧资产迁入新规范

`historyName` 不是：

- 第二套长期并行现行名称
- 日常 authoring 必填项
- 让新模型继续一边写新名、一边长期依赖旧名的机制

## 8. 对更新数据结构功能的影响

采用本方案后，更新数据结构功能可以保持简单：

- 现行表名、列名直接来自模型名、字段名
- 工具按当前名称直接比对目标结构与数据库结构
- 只有在声明了 `historyName` 时，才进入 rename 分支

这样能避免长期维护“模型名变了但表名不变”“字段名变了但列名不变”的双命名复杂度。

## 9. 对 DTO 与代码映射的影响

本方案的目标之一就是减少无谓映射：

- DTO 原始值字段、领域对象、模型字段默认直接使用同一套 `PascalCase` 名称
- 不因为数据库物理层另起一套名字而迫使 DTO 跟着做额外映射
- 只有平台协议字段作为特例保留其既有协议命名

这意味着：

- 普通字段变化时，是否调整 DTO，取决于业务契约是否变化
- 不会因为单独维护一套物理列名而额外触发 DTO 层面的机械改动

### 9.1 DTO 生成策略

后续默认采用：

- `model -> 直接生成并覆盖 DTO`

不把“手工长期维护全部 DTO”作为默认路线，也不把业务层大范围退回到 `GetObjectDBValue("列名")` 这类字符串访问方式。

原因如下：

- `model` 已经是字段结构真源，直接生成 DTO 更符合单一真源原则
- 自动覆盖 DTO 能减少重复维护与机械同步成本
- 相比字符串列名访问，生成后的 DTO 仍具备更好的结构性、可读性和可校验性

动态对象、字典实体或底层存储字典仍可存在于持久化内核与基础设施适配层，但不应扩散为业务层的默认访问方式。

### 9.1.1 DTO 形态

每个 `model` 默认只生成一套 DTO。

这套 DTO 同时用于：

- 读取返回
- 写入接收

也就是说，列表、详情、新增、编辑默认都不再拆成多套模型派生 DTO，而是先统一收口为一套结构。

该规则只针对由单个 `model` 直接派生的主数据 DTO 生效；分页包装对象、通用响应包装对象、跨多个 `model` 聚合的组合 DTO、统计摘要类 DTO 仍不在本规则内。

这样做的原因是：

- 进一步降低 DTO 数量与维护心智成本
- 让 `model -> DTO` 的生成规则保持最直接
- 避免在早期阶段过早拆分出多套高度相似的 DTO

### 9.2 显示值字段规则

DTO 不能只承载数据库原始值；当字段存在展示语义时，应同时生成“原始值 + 显示值”。

当字段存在展示语义时，在原字段基础上追加辅助显示字段。

辅助显示字段统一使用：

- `_DisplayValue`

作为固定后缀，不再混用：

- `DisplayName`
- `Label`
- `Text`

这是 DTO 命名中的唯一默认下划线例外；除 `*_DisplayValue` 外，其余字段仍按 `PascalCase` 生成。

示例：

- `DepartmentId` -> `DepartmentId_DisplayValue`
- `EmploymentStatus` -> `EmploymentStatus_DisplayValue`
- `CreatedBy` -> `CreatedBy_DisplayValue`

适用范围：

- 枚举字段
- 引用字段
- 用户、组织、角色等需要从原始值映射到展示文本的字段

### 9.2.1 显示值来源与回退规则

为避免各模块各自定义“显示值从哪里取”，统一约束如下：

- 枚举字段：从对应枚举定义或枚举字典解析显示文本
- 模型引用字段：从目标对象解析显示文本
- 用户、组织、角色等平台对象引用：本质上仍按“目标对象显示文本”规则处理，不再单独发散出多套命名约定

模型引用字段的显示值回退顺序统一为：

1. `ENAME`
2. `ECODE`
3. `EID`

枚举字段的显示值回退顺序统一为：

1. 枚举项显示文本
2. 原始值

通用失败处理规则如下：

- 原始值为空时，对应的 `_DisplayValue` 返回 `null`
- 原始值非空、但无法解析到显示文本时，对应的 `_DisplayValue` 回退为原始值
- 不允许因为显示值解析失败而阻断主 DTO 输出

显示值解析应收口在后端统一生成链路中完成，不把“前端自行拼显示值”作为默认方案。

### 9.3 同一 DTO 的读写约束

由于每个 `model` 默认只保留一套 DTO，因此统一约束如下：

- 读取时，DTO 可以同时包含原始值字段与对应的 `_DisplayValue`
- 写入时，调用方不需要提交任何 `_DisplayValue` 字段
- 即使请求里带了 `_DisplayValue` 字段，后端也应忽略，不参与写入
- `_DisplayValue` 不是持久化字段，不进入数据库结构，不参与更新数据结构

也就是说，`_DisplayValue` 属于同一 DTO 中的只读展示补充字段，而不是存储真源的一部分。

## 10. 示例

### 10.1 推荐示例

```text
模型名: Role
表名: Role
主键列: EID
普通列: DisplayName, Description, CreatedAt
```

```text
模型名: ConfigItem
表名: ConfigItem
主键列: EID
普通列: Key, Value, ModuleId, UpdatedBy
```

```text
统一 DTO:
DepartmentId
DepartmentId_DisplayValue
EmploymentStatus
EmploymentStatus_DisplayValue
```

### 10.2 不推荐示例

```text
模型名: Role
表名: auth_roles
列名: display_name
```

问题：

- 引入第二套长期物理命名风格
- 增加理解与映射成本

```text
模型名: Role
表名: Role
列名: DISPLAYNAME
```

问题：

- 普通业务字段全大写不利于与协议字段区分

## 11. 落地建议

- 从现在开始，新建表与新建普通列统一按本规范执行
- 现有已落地但尚未形成真实业务依赖的表，可在后续独立整理中按本规范统一
- 不要把命名统一和功能开发混在同一批改动里
- 更新 `model` authoring、projector、migration 相关文档时，同步引用本规范

## 12. 已知风险

- 短期内仓库会出现“旧 `snake_case` 资产 + 新 `PascalCase` 资产”并存
- 若后续没有单独安排清理批次，历史风格可能保留较久
- 第三方脚本或数据库使用者若已默认 `snake_case`，需要适应新的命名口径

## 13. 回滚思路

若后续实践证明统一 `PascalCase` 无法满足跨库工具或团队协作需求，可回滚到“表名/列名统一由逻辑名投影为固定物理命名规则”的方案；但在回滚前必须先补充新的详细设计文档，不能在日常开发中局部自发引入第二套现行命名。

## 14. 结论

基于当前新平台处于早期阶段、表和列数量较少、rename 低频且团队更重视简单统一的现实约束，推荐采用以下默认规范：

- 模型名、代码名、表名、普通列名统一使用 `PascalCase`
- 平台协议字段继续使用全大写协议写法
- 不长期维护独立的现行 `tableName / columnName`
- 每个 `model` 默认只生成一套 DTO，展示补充字段统一使用 `*_DisplayValue`
- 历史兼容只通过 `historyName` 承接

该方案优先保证：

- 简单
- 一致
- 易执行
- 易校验
- 易被 AI 和人工共同维护
