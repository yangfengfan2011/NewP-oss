# Cookie 认证写请求统一使用 platformFetch

前端 SDK 提供唯一的 `platformFetch` 请求 seam，负责从 Host 的匿名防伪令牌端点获取请求令牌，并为所有 `POST`、`PUT`、`PATCH` 和 `DELETE` 请求自动附加防伪请求头与 Cookie；登录成功、密码轮换和退出改变认证主体后必须丢弃旧令牌并重新获取。Host 对所有浏览器可访问且依赖认证 Cookie 的写端点统一验证令牌，登录和退出也不例外。只有服务器明确返回 `400 ANTIFORGERY_TOKEN_INVALID` 时，`platformFetch` 才清除旧令牌、重新获取并自动重试一次；该错误必须在进入业务命令前产生，因此一次重试不会重复业务写入。

模块不得自行实现防伪协议或绕过该 seam 发送认证写请求；现有直接 `fetch` 的写调用必须在该能力实施时迁移，读请求可以继续通过同一入口但不附加防伪头。除上述业务执行前的防伪失败外，`platformFetch` 不得在网络错误、超时、其他 `4xx/5xx` 或结果未知时自动重试登录、删除、凭据重置、永久绑定或其他写命令。这样防伪令牌的取得、认证切换后的刷新和失败映射都集中在小接口内，避免安全语义散落到每个模块，同时不把业务 API 或模块数据所有权移入 Shell。
