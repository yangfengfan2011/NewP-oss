# Phase 5 首个旧资产迁移 POC 设计

## 1. 背景

根据当前计划，`Phase 5` 的目标不是新增一个平台模块，而是完成首个真实旧资产迁移 POC，验证旧平台资产能够按新平台认可的方式导入、承载和验证。

当前仓库已经具备以下基础：

- `ConfigCenter` 已具备最小配置承载能力
- 前后端 Shell、认证和模块装配已打通
- `Authorization / Audit / Files` 已完成阶段性收口
- 迁移策略文档和元数据迁移策略文档已存在

当前缺口在于：

- 尚未冻结首个迁移对象
- 尚未形成一条可执行、可验证、可复用的迁移路径
- 尚未交付一个真实导入样例

## 2. 目标

- 冻结首个旧资产迁移对象。
- 明确来源位置、目标模型、映射规则和验证步骤。
- 交付最小可运行导入路径。
- 形成后续同类资产迁移可复用的设计基线。

## 3. 非目标

- 不在本轮完成 `Icp Studio` Web 化。
- 不做大规模旧资产批量迁移。
- 不处理 `.page`、`.view`、`.generator` 等高复杂设计器资产。
- 不在本轮扩展为完整迁移平台。

## 4. 迁移对象选择

本轮仍推荐将 `Setting` 作为 `Phase 5` 首个迁移 POC，但这里的 `Setting` 明确指旧平台中的 `.setting` 文件体系，而不是少量特例化 JSON 配置文件。

## 5. 选择 `.setting` 作为首个 POC 的原因

- 与 `ConfigCenter` 的定位最直接吻合。
- 更容易验证“旧配置资产进入新平台配置中心”的主链路。
- 比页面、视图、设计器类资产复杂度更低，更适合作为机制验证样本。
- 能直接为未来 `Icp Studio` Web 化铺路，因为配置维护是桌面工具替代的基础。

当前已确认旧平台的通用 `Setting` 主体是 `.setting` 文件，而 `WebSiteSetting.json` 一类文件更偏单点 UI 外观配置，不适合作为本轮通用 POC 样本。

`Dictionary` 仍然是强候选对象，但更偏资源与多语言迁移；如果本轮目标是验证新平台的配置承载和配置维护链路，`.setting` 更适合作为第一优先。

## 6. 总体方案

采用“旧 `.setting` 解析 + 统一映射 + 导入 `ConfigCenter` + API/页面验证”的最小闭环方案。

主链路如下：

1. 从 OldP 中选定一组真实 `.setting` 资产作为样本。
2. 建立旧结构到 `ConfigItem` 的映射规则。
3. 通过导入层写入 `ConfigCenter` 的运行时承载模型。
4. 通过 API 和前端配置页验证导入结果可见、可读、可维护。
5. 固化迁移设计、执行过程和限制说明。

本轮同时遵循一条默认原则：

- 尽量不改变旧平台配置项的使用规则
- 优先保持旧配置项的语义和理解方式
- 只有在旧规则明显不合理、过时或不适合新平台承载时，才进行受控升级

如果发生规则升级，必须在迁移文档中补充新旧规则映射与差异说明。

## 7. 样本选择原则

首个样本应满足：

- 真实存在于 OldP 配置目录
- 结构简单、字段稳定
- 不强依赖旧运行时上下文
- 不涉及复杂引用链或脚本逻辑
- 导入后能在 `ConfigCenter` 中自然表达

优先选择公共平台设置，而不是深业务或强耦合配置。

当前建议优先从结构简单、条目数量少、语义明确的 `.setting` 文件切入，例如：

- `OldP/Runtime/1_Server/Config/CompanyRuleSetting.setting`
- `OldP/Runtime/1_Server/CommandServiceManagement/Config/CommandService.setting`

像 `Base.setting`、`Web.setting` 这类文件覆盖面更大、条目更多，适合作为第二步扩展样本，而不是第一批机制验证样本。

## 8. 目标模型

首个 POC 不新建独立配置子系统，直接落到现有 `ConfigCenter` 模型。

基于当前样本观察，旧 `.setting` 文件的核心结构是：

- 根节点：`root`
- 配置项节点：`AppSet`
- 关键属性：`Key`、`Value`、`ToClient`、`Description`

因此本轮 POC 以 `AppSet` 为最小解析单元。

建议最小映射目标为：

- `AppSet.Key` -> `ConfigItem.Key`
- `AppSet.Value` -> `ConfigItem.Value`
- 文件归属或导入上下文 -> `ConfigItem.ModuleId`
- 文件名或预设规则 -> `ConfigItem.Group`
- `AppSet.Description` -> `ConfigItem.Description`
- `AppSet.Key` 或规则派生名称 -> `DisplayName`
- 环境或租户信息 -> 当前若样本不涉及，可先映射为全局配置

原则：

- 不保留旧文件结构作为运行时主模型
- 不把旧解析格式暴露给业务层
- 通过导入层做转换，而不是通过兼容层长期读取旧文件

## 9. 逻辑分层

建议按以下边界落地：

### 导入层

- 负责读取旧 `.setting` 样本
- 负责解析 XML 与 `AppSet` 节点
- 负责产出中间导入模型

### 映射层

- 负责旧字段到新平台 `ConfigItem` 的映射
- 负责键名、分组、模块归属和默认值策略
- 负责导入前校验

### 应用层

- 负责发起导入流程
- 负责幂等处理、覆盖策略和执行结果返回

### 承载层

- 由 `ConfigCenter` 仓储和服务承接导入结果
- 不感知旧文件结构

## 10. 关键设计点

### 10.1 导入执行方式

首个 POC 建议采用受控导入，而不是启动时自动全量扫描。

原因：

- 风险更低
- 更便于验证和回放
- 便于明确样本范围
- 便于记录结果和失败原因

### 10.2 幂等策略

首个导入流程应具备最小幂等能力。

建议规则：

- 同一 `Key` 视为同一目标配置
- 当多个组件声明相同 `Key` 时，按组件装配顺序处理，后声明者覆盖前声明者
- 本轮覆盖策略保持简单，不做复杂合并，也不引入额外优先级引擎

### 10.3 错误处理

需要明确处理以下情况：

- 旧配置格式不合法
- 映射字段缺失
- 目标配置键冲突
- 导入部分成功、部分失败

首个 POC 不必追求复杂补偿机制，但要输出清晰结果。

### 10.4 审计与记录

如果当前阶段联动成本可控，建议为导入操作至少保留执行记录；即便还不完整接入 `Audit`，也应留下验证记录和操作说明。

## 11. 验证方案

首个 POC 的成功标准建议包括：

1. 存在一份已冻结的旧 `.setting` 样本来源说明。
2. 导入逻辑可以对样本执行并得到稳定结果。
3. 导入后的配置可通过 `ConfigCenter` API 查询。
4. 导入后的配置可在前端配置页看到。
5. 至少完成一次端到端验证记录。
6. 文档中明确当前限制和后续扩展方式。

### 11.1 已知限制

- **中文 Description 编码不稳定**：中文 Description 在当前脚本化 smoke 中存在编码不稳定风险。
- **影响范围**：仅影响 Description 字段显示，不影响 Key 和 Value 的正确性和功能使用。

## 12. 推荐交付物

- 迁移设计文档
- 样本来源说明
- 导入器或导入服务最小实现
- API 或脚本执行入口
- 端到端验证记录
- 当前限制说明

## 13. 后续扩展路径

当 `Setting` 首个 POC 成功后，推荐按以下顺序扩展：

1. `Dictionary`
2. `Enumeration`
3. 更复杂的配置分组与覆盖规则
4. 批量导入能力
5. 更正式的导入报告和审计联动

这条路径与未来 `Icp Studio` Web 化方向一致，因为配置维护能力是桌面端替代的第一层基础。

## 14. 风险与当前限制

### 14.1 设计风险

- 如果样本选择过重，POC 会被拖成完整迁移项目。
- 如果直接引入旧运行时解析机制，会形成新的技术债。
- 如果跳过映射规则设计，后续 `Dictionary / Enumeration` 无法复用。
- 如果只做脚本不做验证记录，`Phase 5` 仍不能算真正完成。

### 14.2 当前已知限制

- **中文 Description 编码不稳定**：中文 Description 在当前脚本化 smoke 中存在编码不稳定风险。

## 15. 结论

`Phase 5` 首个旧资产迁移 POC 推荐从旧平台 `.setting` 文件开始，通过 `ConfigCenter` 承接静态业务规则配置，先打通一条最小但真实的导入闭环。为控制范围，首批样本应优先选用简单 `.setting` 文件，而不是 `WebSiteSetting.json` 一类特例化外观配置或 `Base.setting` / `Web.setting` 这类大体量文件。这条路径既能完成当前计划要求，也能为未来 `Icp Studio` 配置能力的 Web 化替代建立直接基础。

## 16. AI-First 调整

本阶段在继续沿用 `.setting -> ConfigCenter` 路线的同时，需要把“完成一个迁移样例”调整为“沉淀一条 AI 可复制执行的迁移模板”。

因此本阶段应额外满足以下要求：

- 冻结首批样本，不在实施中途频繁更换来源文件。
- 冻结字段映射和覆盖规则，避免实现阶段临时猜测。
- 优先通过固定 API、脚本或测试执行导入，而不是依赖大量人工操作。
- 验证记录要能支持后续 agent 复跑，不能只保留口头结论。
- 文档中要明确指出这次 POC 对 `Dictionary`、`Enumeration` 等后续迁移对象有哪些可复用部分。

据此判断，`Phase 5` 不需要推倒重做，但需要补强“样本冻结、规则冻结、执行冻结、验证冻结、复用冻结”这五类交付。
