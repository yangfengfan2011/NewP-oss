# Phase 6 第一版：前端组件化模板设计

## 1. 背景

在第六阶段后端组件化模板第一版完成后，仓库已经具备较稳定的后端模块接入路径，但前端侧虽然已有 `Shell`、`SDK` 和多个真实模块样本，仍缺少一份正式、统一、可复用的“前端模块标准模板”设计。

结合当前仓库状态，前端已经具备：

- `frontend/packages/sdk` 中的前端模块契约与 `ModuleRegistry`
- `frontend/packages/shell` 中的宿主路由、菜单聚合、权限守卫和集中注册入口 `registerModules.ts`
- 多个真实模块样本：`demo`、`audit`、`authorization`、`config-center`、`files`
- `frontend/docs/module-integration-guide.md` 中的接入说明

但当前仍存在三个问题：

- 前端模板规范仍以“文档说明 + 现有模块自行归纳”为主，尚未沉淀为正式模板设计
- 现有模块在 `moduleId` 大小写、包名命名、`requireAuth` 使用方式上存在不完全一致
- `frontend/packages/ui` 仍是占位状态，如果过早把它写进模板，会把未稳定能力反向固化成约束

因此，`Phase 6` 前端组件化模板第一版的目标应是先把“现有前端模块契约”沉淀成正式设计，并输出一套仓库内可复制的模板骨架与最小验证口径，为下一步端到端示例模块和脚手架打基础。

## 2. 目标

- 输出正式的前端组件化模板设计文档
- 明确当前仓库中前端模块的标准接入契约、目录结构和宿主集成方式
- 提供仓库内可复制的前端模板骨架
- 固化新增前端模块所需的最小文件集合、职责边界和验证命令
- 为后续端到端示例模块与脚手架提供稳定上游，而不是让工具反过来塑造契约

## 3. 非目标

- 本阶段不实现端到端全栈示例模块
- 本阶段不把 `frontend/packages/ui` 扩展成真正的共享组件库
- 本阶段不引入新的宿主能力、动态远程加载或复杂插件市场机制
- 本阶段不重构现有 `Shell`、`SDK` 或已落地业务模块
- 本阶段不强行统一历史模块中所有命名差异，只定义第一版模板应遵循的新标准

## 4. 设计原则

### 4.1 契约优先于页面样式

前端模板第一版的核心不是“产出漂亮页面”，而是确保新增模块按既定契约接入宿主：模块通过 `FrontendModule` 描述元数据、路由、菜单、权限和生命周期，宿主只做聚合，不承载模块私有逻辑。

### 4.2 模块优先于共享 UI

当前 `frontend/packages/ui` 仍未形成稳定能力，因此第一版模板必须建立在已稳定的 `sdk + shell + modules/*` 结构之上，而不是假设未来共享 UI 组件库已经可用。模板可以预留组件目录，但不能把 UI 包依赖写成必需项。

### 4.3 仓库真实模式优先于抽象理想形态

模板设计必须从当前真实样本提炼，而不是凭空设计一套“更理想但仓库尚未采用”的结构。也就是说，第一版模板应围绕：

- `frontend/modules/<module-name>/src/index.ts`
- `pages/`
- 可选 `components/`、`services/`
- `package.json`
- `tsconfig.json`

来组织，而不是引入当前仓库尚未使用的目录层级和构建机制。

### 4.4 AI-First 但不牺牲边界

模板需要让 AI 和人工都能在小上下文中定位修改点，因此必须明确：

- 哪些文件是模块入口
- 哪些文件负责页面
- 哪些字段由宿主聚合消费
- 哪些目录是按需启用
- 新模块不应直接依赖 `shell` 内部组件实现

AI 友好来自结构清晰和职责稳定，而不是来自“把所有东西都堆进一个入口文件”。

## 5. 当前现状判断

### 5.1 已稳定的事实

- 前端模块统一通过 `FrontendModule` 契约导出
- 路由、菜单、权限均为模块声明，由 `Shell` 聚合消费
- 宿主注册入口已经集中到 `frontend/packages/shell/src/registerModules.ts`
- 模块包均为 workspace 包，集中位于 `frontend/modules/*`
- 页面一般位于 `src/pages/`

### 5.2 尚未稳定的部分

- `moduleId` 在大小写和命名风格上并不完全一致
- 包名存在 `@icp-modules/*` 与 `@icp-platform/module-*` 混用情况
- `requireAuth` 在不同模块中的使用并不完全统一
- `frontend/packages/ui` 尚未进入实际使用链路

### 5.3 设计结论

第一版前端模板只应固化“已经稳定”的部分；对于尚未完全稳定的部分，模板中应给出推荐标准和兼容说明，而不是试图在同一轮顺手完成全部历史清洗。

## 6. 方案选型

### 方案 A：契约模板 + 仓库骨架 + 最小验证链路

做法：

- 输出正式模板设计与仓库规范
- 在仓库中提供前端模板骨架目录
- 提供最小验证命令与复制说明
- 不在本轮引入新端到端样本模块

优点：

- 与当前阶段边界最一致
- 不提前耦合 `packages/ui`
- 为后续端到端示例模块和脚手架留出稳定上游

缺点：

- 第一轮仍以“模板 + 规范”为主，尚未形成新的活前端样本

### 方案 B：模板骨架 + 新前端示例模块

做法：

- 在方案 A 基础上额外新增一个前端示例模块

优点：

- 模板可直接由真实样本反向验证

缺点：

- 容易与下一步“端到端示例模块”阶段重叠
- 会扩大本轮范围，使收口边界变得模糊

### 方案 C：直接实现脚手架命令

做法：

- 跳过模板规范沉淀，直接做生成器

优点：

- 使用体验最直接

缺点：

- 会把当前仍在演进的前端契约过早写死
- 最容易让工具反向定义架构

### 推荐结论

采用 `方案 A`。第一版前端模板应聚焦“契约模板 + 仓库骨架 + 最小验证链路”，并把“端到端示例模块”和“脚手架”明确保留到后续阶段。

## 7. 交付物设计

### 7.1 规范层

需要一份正式文档，明确前端模块至少应说明：

- 模块用途与边界
- 模块目录结构
- `src/index.ts` 的职责
- 路由、菜单、权限的声明方式
- 生命周期钩子 `initialize` / `cleanup` 的使用边界
- 宿主注册点位置
- 推荐的包名、`moduleId`、路由前缀和权限命名规则
- 最小验证命令

### 7.2 骨架层

仓库内应提供一套可复制的前端模板骨架，推荐放在：

- `frontend/templates/frontend-module-template/`

为保证模板骨架也能被独立构建验证，前端 workspace 应显式纳入：

- `templates/*`

第一版模板骨架建议至少包含：

- `README.md`
- `package.json`
- `tsconfig.json`
- `src/index.ts`
- `src/pages/TemplatePage.tsx`

按需启用但不必默认创建的目录：

- `src/components/`
- `src/services/`
- `src/assets/`

### 7.3 验证层

前端模板第一版需要给出最小验证口径：

- 模板包自身能通过 workspace 方式执行 `pnpm --filter <package-name> build`
- 宿主能在集中注册点完成模块注册
- 整体前端工作区能 `pnpm build`

第一版不强制引入浏览器人工验证，也不要求引入前端测试框架；重点是先把模块契约和构建链路固化。

## 8. 模板边界要求

### 8.1 模块只通过 `FrontendModule` 契约接入宿主

模块必须通过 `src/index.ts` 导出 `FrontendModule`，由宿主统一注册，不允许模块自行改写 `Shell` 路由配置或菜单逻辑。

### 8.2 页面、组件、服务边界清晰

模板允许小模块只保留一个页面文件，但应明确：

- 页面文件负责展示与交互组织
- 服务文件负责接口访问或数据适配
- 组件目录只承载模块内部可复用 UI 片段

不应把路由声明、菜单声明、远程请求和全部页面 JSX 混堆在同一个大型入口文件里。

### 8.3 不直接依赖宿主内部实现

模板不应鼓励模块直接引用 `shell/src/components/*` 或 `shell/src/contexts/*` 的内部文件。模块只应依赖稳定的 workspace 包和公开契约。

### 8.4 不提前绑定 `packages/ui`

在 `packages/ui` 真正落地前，模板中只能把它视为未来扩展方向，不能作为新增模块的默认必需依赖。

## 9. 推荐标准

第一版模板建议新增模块遵循以下标准：

- 包名：`@icp-modules/<module-name>`
- 目录：`frontend/modules/<module-name>/`
- `moduleId`：采用稳定的 PascalCase 或业务既有规范，但模板样本本身要固定一种写法并在文档中说明
- 路由前缀：与模块目录语义一致
- 权限命名：`<Module>.<Resource>.<Action>`
- 菜单 `id`：保持全局唯一，且与模块语义相关

由于历史模块已有差异，第一版文档应把这些标准标记为“新增模板推荐标准”，而不是宣称现有模块已全部满足。

## 10. AI-First 对齐方式

前端模板第一版对 `AI-First` 的落实体现在：

- 新增模块时，AI 可以只围绕模板目录和 `src/index.ts` 完成局部修改
- 宿主注册点单独集中，便于 AI 明确接入位置
- 模板中显式标明“必改项、可删项、禁改项”
- 验证命令局部化，降低每次改动的回归成本

换句话说，本阶段不是做“AI 帮你自动生成任意前端页面”，而是先把“AI 和人工都能稳定新增前端模块”的路径做成标准件。

## 11. 验证标准

`Phase 6` 前端组件化模板第一版完成时，应至少满足：

- 已存在正式的前端组件化模板设计文档
- 已存在仓库内前端模板骨架目录
- 已存在模板 README，明确复制方式、必改项和验证命令
- `registerModules.ts` 或等价集中接入点被文档正式纳入模板规范
- 模板包可独立构建
- 前端工作区整体构建通过
- 文档中已明确哪些能力延后到端到端示例模块阶段处理

## 12. 实施边界

第一版实施应控制在“前端模板闭环”内，不混入以下工作：

- `packages/ui` 真正组件库建设
- 新前端业务模块大规模开发
- 端到端联调模块实现
- 脚手架命令开发
- 宿主主题系统、通知系统、国际化系统深化

如果实施中发现需要补齐 `sdk` 或 `shell` 的小缺口，也应以“满足模板接入所需的最小补齐”为限，避免顺势扩大成新一轮前端架构重构。

## 13. 后续衔接

在前端模板第一版稳定后，建议按以下顺序推进：

1. 端到端示例模块
2. 可执行脚手架
3. `packages/ui` 共享组件能力沉淀

这样可以确保后续自动化建立在稳定模板之上，而不是把未稳定的 UI 层和脚手架生成逻辑提前绑定。

## 14. 结论

`Phase 6` 前端组件化模板第一版应聚焦于“正式规范 + 仓库骨架 + 最小验证链路”。它的成功标准不是立即做出新的复杂模块，而是在不偏离现有前端模块化架构的前提下，把新增前端模块的接入方式沉淀成清晰、可复制、可验证、也便于 AI 稳定执行的标准路径。
