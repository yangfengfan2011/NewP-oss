# Phase 6.5 多数据库持久化设计

## 1. 背景

当前新平台已经完成 `ConfigCenter`、`Authorization`、`Audit`、`Files` 等模块的基础实现，但 `ConfigCenter` 与 `Authorization` 的仓储仍以内存实现为主，尚未形成真实数据库持久化底座。下一阶段仍然需要进入 `Phase 6.5`，补齐数据库落地、初始化、迁移与可复跑验证。

此前版本的设计把本轮路线定义为“代码优先 + EF Core 多 Provider + 三套迁移集”，并明确排除了模型语义层与后续元数据演进空间。这条路线对短期落库是直接的，但它把“EF Core 的当前实现”上升成了“平台长期持久化架构本体”，会带来两个问题：

- 它把数据库表结构、约束、索引、审计字段、关系模型等长期稳定语义，和某一代 ORM/Provider 适配方式绑定得过紧。
- 它没有吸收旧平台在 `ENTITY/LINK`、字段语义、显示语义、数据库结构分层上的有效经验，只是简单地把旧平台整体归类为“模型驱动平台”后整体排除。

结合旧平台 [ModelGuide.md](D:/Github/ICP-X/OldP/ApiDoc/05_Models/ModelGuide.md) 的经验，以及当前项目的 AI-first 目标，本轮需要调整方向：

- **内核仍然代码优先**：核心领域逻辑、仓储契约、Provider 边界、事务与运行时流程继续用显式代码表达。
- **结构性部分引入强约束模型语义层**：实体/关系、字段类型、索引、唯一约束、审计字段等不再直接附着在某个 ORM 实现上，而是抽成独立、可验证、可演进的模型语义。
- **EF Core 只是第一批持久化适配器，而不是架构本体**。

因此，本轮设计不再是“纯 EF Core 落库方案”，而是“代码内核 + 强约束模型语义 + 持久化适配层”的混合架构方案。

## 2. 目标

- 为 `ConfigCenter` 与 `Authorization` 建立真实数据库持久化路径。
- 同一套宿主程序通过配置切换 `SQL Server`、`Oracle`、`MySQL`。
- 保证业务层只依赖统一仓储接口与服务接口，不感知数据库类型。
- 把数据库表结构、字段、索引、关系、审计等结构性信息沉淀为**强约束模型语义**，而不是直接散落在 ORM 映射中。
- 允许在持久化层保留受控原生 SQL 能力，但数据库差异只能沉到基础设施层。
- 形成后续可继续演进的适配层结构：本轮先落地 EF Core 适配器，后续不排斥增加其他适配器或生成器。
- 三种数据库都具备可验证的启动、迁移、初始化与 smoke 闭环。

## 3. 非目标

- 本轮不建设旧平台那种完整的模型设计器、界面化配置工具或低代码平台。
- 本轮不让业务人员通过界面直接定义表、字段和关系。
- 本轮不把全部模块一起迁入真实数据库，首批仍只覆盖 `ConfigCenter` 与 `Authorization`。
- 本轮不承诺一次性完成“模型文件 -> 全平台代码生成”的完整工具链。
- 本轮不把 EF Core 排除掉；相反，它仍是第一批落地适配器。
- 本轮不在没有真实性能证据前引入统一缓存层。

## 4. 方案对比与结论

### 4.1 方案 A：继续纯代码优先，EF Core 直接作为持久化主干

做法：

- 业务层继续依赖现有模块 `Models`、`Repositories`、`Services`。
- 数据库结构、索引、关系、迁移全部直接定义在 EF Core 配置与迁移中。
- 三种数据库通过 Provider 和独立迁移集切换。

优点：

- 对当前仓库最直接。
- 与主流 .NET 工程实践一致。
- 短期能更快落地第一批真实数据库存储。

缺点：

- “结构性语义”直接耦合在 EF Core 配置中，长期上不利于后续生成器、验证器和非 EF 适配器演进。
- 很难吸收旧平台 `ENTITY/LINK` 与字段语义的有效抽象。
- 设计层面对“为什么是这样一张表”与“为什么是这样一条索引”的表达不够独立，AI 和人都更难稳定重构。

### 4.2 方案 B：代码内核 + 强约束模型语义 + 持久化适配层

做法：

- 业务层继续保持显式代码模型、仓储契约与服务实现。
- 在业务层和持久化适配器之间增加一层**模型语义定义**，承载实体/关系、字段、索引、约束、审计等结构性信息。
- EF Core 作为第一批适配器，负责把模型语义投影到 `DbContext`、迁移与 Provider 配置上。
- 后续可在不破坏业务层和模型语义层的前提下增加其他适配方式。

优点：

- 同时满足“内核明确可调试”和“结构重复部分可标准化”的双重目标。
- 更适合 AI 参与重构、验证和后续生成工作。
- 能吸收旧平台模型思想，又不把本轮变成“先造一套设计器平台”。
- 让 EF Core 回到“实现适配器”位置，而不是平台唯一真相来源。

缺点：

- 比纯 EF Core 方案多出一层设计和校验成本。
- 需要额外定义模型语义边界、版本化和验证规则。

### 4.3 方案 C：完整模型平台先行，再做持久化

做法：

- 先建设模型定义格式、生成器、设计器和全链路工具。
- 再由模型系统统一生成数据库结构、代码和页面。

优点：

- 长期平台化能力最强。
- 理论上最利于大量标准模块生成。

缺点：

- 范围过大，容易把当前重点从“真实落库”转移到“先造平台”。
- 对当前阶段不够经济，也不符合最小可行推进路线。

### 4.4 选择结论

本轮选择 **方案 B**：

- 核心能力继续代码优先。
- 引入强约束模型语义层，吸收旧平台有效经验。
- EF Core 仍然落地，但降级为“第一批持久化适配器”。
- 不建设完整模型设计器，不把本轮目标扩大成低代码平台建设。

## 5. 核心判断

### 5.1 为什么不是继续把 EF Core 当作架构中心

当前阶段仍然需要 EF Core，因为它对多 Provider、迁移、事务与工程化支持最成熟。但成熟并不意味着它应该成为“平台的唯一结构真相来源”。

如果把表结构、字段语义、关系与索引全部直接绑到 EF Core 配置里，那么：

- 后续做模型校验器时，必须从运行时映射反推意图。
- 后续做生成器时，必须从 ORM 配置中二次抽象。
- 后续做非 EF 场景时，结构定义无法复用。

这会让当前实现方式影响未来平台边界。

### 5.2 为什么不是回到旧平台式模型驱动

旧平台有值得吸收的地方：

- 区分业务对象、关系对象和展示语义。
- 区分对象值类型、数据库类型和显示标签。
- 让索引、字段、基类审计信息有一致表达方式。

但旧平台的问题也很明显：

- 建模、显示、数据库、生成工具过度耦合。
- 运行时链路不透明。
- 对 AI 和新成员来说理解成本过高。

所以本轮只吸收**强约束模型语义**，不照搬整套 `.dic/.model/.schema + 设计器` 体系。

### 5.3 本轮的 AI-first 判断标准

本轮按下面这条规则划边界：

- **变化多、规则复杂、需要调试和重构**：继续代码优先。
- **重复多、结构稳定、适合统一校验和生成**：进入模型语义层。

因此：

- 仓储接口、服务、事务边界、Provider 切换、权限同步逻辑，继续放在代码内核。
- 实体/关系、字段、索引、唯一约束、审计字段、标准关系表模式，抽入模型语义层。

## 6. 总体架构

### 6.1 分层结构

- `Models / DTOs / Services`
  - 业务层
  - 继续表达业务对象、服务规则和用例
- `Repositories`
  - 业务层看到的数据访问契约
- `Model Semantics`
  - 结构性定义层
  - 表达实体/关系、字段、索引、约束、审计、值类型等稳定语义
- `Persistence Adapters`
  - 持久化适配层
  - 把模型语义投影到具体技术实现，例如 EF Core
- `Provider Runtime`
  - Provider 选择、连接、迁移、初始化、原生 SQL、方言能力

### 6.2 建议目录

建议新增或调整如下目录：

- `server/platform-modeling`
  - 放模型语义定义、校验器、基础枚举与公共约束
- `server/platform-persistence`
  - 放 Provider 无关的持久化内核、Provider 枚举、配置模型、启动入口、统一 SQL 抽象
- `server/platform-persistence-efcore`
  - 放 EF Core 适配器、`DbContext`、模型投影器、方言与迁移绑定
- `server/modules/ConfigCenter/Persistence`
  - 放 `ConfigCenter` 的描述定义、仓储实现、必要 SQL 查询
- `server/modules/Authorization/Persistence`
  - 放 `Authorization` 的描述定义、仓储实现、必要 SQL 查询

如果后续为了贴合仓库现有风格，需要把 `platform-modeling` 或 `platform-persistence` 吸收到 `server/kernel` 之下，本轮也允许调整；关键不是目录名，而是**分层边界必须独立存在**。

### 6.3 真相来源顺序

本轮明确真相来源顺序如下：

1. 业务接口与业务行为：代码
2. 模型结构与数据库语义：模型语义定义
3. EF Core 映射与迁移：模型语义的第一批技术投影

也就是说：

- 不是“数据库结构直接以 EF 配置为准”
- 而是“数据库结构语义以模型语义层为准，EF 配置只是当前投影方式”

## 7. 模型语义设计

### 7.1 核心对象

模型语义层至少需要表达以下对象：

- `ModelDefinition`
  - 模型名、物理表名、模型种类、说明、版本
- `ModelKind`
  - 至少区分 `Entity` 与 `Link`
- `FieldDefinition`
  - 字段名、存储列名、值语义类型、数据库类型、是否必填、是否主键、是否审计字段
- `IndexDefinition`
  - 索引名、字段集合、唯一性
- `RelationshipDefinition`
  - 用于表达 `Link` 模型或显式引用关系
- `AuditProfile`
  - 统一承载创建时间、修改时间、创建人、修改人等标准审计字段策略

### 7.2 `ENTITY/LINK` 的吸收方式

旧平台中最有价值的抽象，不是它的建模工具，而是它对对象种类的划分。本轮建议保留这个思想：

- `Entity`
  - 表达有独立生命周期的业务对象
  - 例如 `ConfigItem`、`Role`、`Permission`
- `Link`
  - 表达关系对象
  - 例如 `UserRole`、`RolePermission`

这样做的好处是：

- 一眼能看出某个模型是实体还是关系。
- 标准索引、唯一约束、审计策略可按类型复用。
- 后续生成器、校验器和 AI 都更容易理解。

### 7.3 字段语义与数据库类型分离

本轮明确区分：

- 字段语义类型
  - 例如普通文本、描述文本、布尔、日期时间、对象引用、枚举、用户引用
- 数据库存储类型
  - 例如 `nvarchar(256)`、`varchar2(256)`、`timestamp`、`number(1)` 等 Provider 相关实现

也就是说，模型语义层不直接把自己做成某个数据库方言。

### 7.4 载体形式

为了控制范围，本轮不做设计器。模型语义的初始载体建议采用：

- **仓库内、受版本控制、可代码审查的强类型定义**

第一版可以优先采用：

- C# 静态定义/Builder/Record 形式

原因：

- 对当前仓库最稳。
- 类型安全。
- 容易被测试和验证。

后续如果需要，再演进为结构化文件或生成器输入；但本轮先锁语义，不先锁文件格式工具链。

### 7.5 前期生产方式

在没有设计器之前，本轮默认采用：

- **AI 生成模型语义定义**
- **人审核结果**
- **校验器与测试兜底**

也就是说，前期不是让人手工频繁维护大量元数据，也不是立即建设一个给人直接操作的设计器，而是：

1. 由 AI 按既定约束生成或修改模型语义定义
2. 生成结果直接进入仓库并接受代码审查
3. 通过模型校验、模块测试、迁移与 smoke 验证来兜底

这样做的原因是：

- 当前阶段最需要的是稳定推进，不是先建设一套人机交互工具。
- 模型语义本身已经足够结构化，适合作为 AI 生成目标。
- 先用 AI 生成、测试校验，再做设计器，能避免过早把精力投入到界面与工具链上。

### 7.6 对未来设计器的兼容要求

如果后期建设设计器，设计器必须遵守以下边界：

- 设计器不是新的架构中心，只是新的**输入方式**。
- 设计器输出必须落到同一套 `ModelDefinition / FieldDefinition / IndexDefinition / ModelKind` 契约上。
- 设计器不能绕开模型校验器、迁移验证与测试流程。
- 设计器产物必须仍然能够进入版本库、被审查、被回滚。

也就是说，未来设计器做成以后，替换的是“谁来生成模型语义定义”，而不是替换“平台以什么作为结构真相来源”。

## 8. 持久化适配层设计

### 8.1 Provider 无关内核

持久化内核负责：

- `PersistenceProvider` 枚举与配置
- Provider 选择逻辑
- 统一 SQL 执行入口
- 事务边界复用约束
- 迁移与初始化触发入口
- Provider 能力矩阵与运行时告警

这些能力不应依赖 EF Core 才能存在。

### 8.2 EF Core 作为第一批适配器

EF Core 适配器负责：

- 把 `ModelDefinition` 投影成 `DbContext` 模型
- 注册 `SQL Server`、`Oracle`、`MySQL` Provider
- 承载第一批迁移集
- 为模块仓储提供第一批真实数据库实现

关键点：

- EF Core 是第一批适配器，不是平台架构中心。
- 如果后续要增加非 EF 查询适配器、只读投影适配器或生成型 DDL 工具，不需要推翻业务层与模型语义层。

### 8.3 原生 SQL 边界

原生 SQL 仍然保留，但规则不变：

- 只能出现在持久化适配层或仓储实现内部。
- 必须参数化。
- 必须复用当前事务与连接上下文。
- 不得让业务服务层感知 Provider 分支。

本轮建议保留：

- `ISqlQueryExecutor`
- `ISqlDialect`

但它们应位于持久化内核，而不是业务层。

## 9. Provider 切换与迁移策略

### 9.1 配置模型

宿主显式配置：

- `Persistence:Provider = SqlServer | Oracle | MySql`
- `ConnectionStrings:SqlServer`
- `ConnectionStrings:Oracle`
- `ConnectionStrings:MySql`
- `Persistence:Adapter = EfCore`
- `Persistence:AutoMigrate = true | false`
- `Persistence:AutoSeed = true | false`

这次多加一层 `Persistence:Adapter`，是为了把“Provider”与“适配器”分开。当前默认值仍然可以是 `EfCore`。

### 9.2 启动流程

宿主启动时固定执行：

1. 读取 `Persistence:Adapter`
2. 读取 `Persistence:Provider`
3. 装配对应持久化适配器
4. 绑定连接串
5. 选择对应迁移集
6. 执行迁移
7. 执行统一种子逻辑
8. 启动 Host

### 9.3 迁移策略

仍采用：

- 同一套业务模型
- 同一套模型语义定义
- 同一套仓储契约
- 三套独立迁移集

原因没有变化：

- 三数据库在主键、自增、布尔、默认值、时间类型、分页语法、DDL 细节上仍有显著差异。

变化只在于：

- 迁移不再被描述为“直接从 EF 映射长出来的唯一真相”
- 而是“模型语义经 EF 适配器投影后的第一批迁移产物”

## 10. 模块落地策略

### 10.1 第一批模块

本轮只纳入：

- `ConfigCenter`
- `Authorization`

原因不变：

- `ConfigCenter` 是旧资产导入的自然落点。
- `Authorization` 是平台公共能力，且与种子和权限同步强相关。

### 10.2 模块内落地方式

每个模块需要具备三部分：

- 业务模型与服务
  - 继续保留现有 `Models / Repositories / Services`
- 模型语义定义
  - 描述该模块有哪些实体、关系、字段、索引、约束
- 持久化适配实现
  - 当前先落地 EF 仓储与必要 SQL 查询

### 10.3 对未来模块的影响

后续模块接入不应再直接从“先写 ORM 映射”开始，而应遵循：

1. 先定义业务边界
2. 再定义模型语义
3. 最后选择适配器落地

这样能避免每个模块都把数据库结构重新耦合到某个具体技术实现里。

## 11. 分阶段交付

### 11.1 Phase 6.5A：持久化内核与模型语义底座

交付重点：

- `platform-modeling`
- `platform-persistence`
- 核心模型语义对象与校验器
- Provider/Adapter 配置模型

### 11.2 Phase 6.5B：EF Core 适配器与三库运行时承接

交付重点：

- `platform-persistence-efcore`
- `DbContext` 投影器
- Provider 方言
- 三套迁移程序集

### 11.3 Phase 6.5C：模块适配与验证闭环

交付重点：

- `ConfigCenter` 与 `Authorization` 的模型语义定义
- 对应 EF 仓储实现
- 种子、迁移、集成测试和 smoke

## 12. 验收标准

本轮验收标准调整为：

- 业务层代码零分库分支。
- 业务层不直接依赖 ORM/Connection/Command。
- `ConfigCenter` 与 `Authorization` 已具备独立的模型语义定义。
- 三数据库切换仅改配置，不改业务层接口与调用方式。
- EF Core 已经作为第一批适配器接入，但文档与代码边界上不把 EF Core 视为唯一架构中心。
- 三种数据库都具备迁移、初始化与 smoke 验证闭环。
- 原生 SQL 查询仍被限制在持久化层。
- 模型语义定义可被测试与校验，能发现重复字段、非法索引、缺失主键等结构问题。

## 13. 风险与控制

### 13.1 主要风险

- 新增模型语义层后，如果边界设计不清，容易变成“多一层无价值抽象”。
- 如果描述定义过于松散，后续生成与验证收益会很弱。
- 如果 EF 适配器仍然承载过多特殊逻辑，模型语义层就会名存实亡。
- Oracle 与 MySQL 的 Provider 差异仍可能在首批投影中暴露更多细节问题。

### 13.2 控制方式

- 模型语义层只承载“结构稳定、重复率高、适合统一校验”的内容，不承载复杂业务逻辑。
- 本轮优先采用强类型定义，不先引入松散 JSON 大杂烩。
- 所有 Provider 差异仍强制收敛在适配器和方言服务内。
- 首批只做 `ConfigCenter` 与 `Authorization`，避免多模块同时把边界做乱。
- 通过模型校验测试、集成测试与 smoke 脚本，尽早暴露语义层与适配层不一致问题。

## 14. 结论

`Phase 6.5` 不再定义为“纯代码优先的 EF Core 多 Provider 落库方案”，而调整为：

- **代码优先的内核**
- **强约束的模型语义层**
- **以 EF Core 为第一批实现的持久化适配层**

这条路线保留了当前仓库最需要的工程稳定性，也吸收了旧平台最有价值的模型分层经验，同时避免把当前阶段错误扩大成“先建设一整套模型平台”。

简化后的判断是：

- 内核与复杂行为继续显式代码化。
- 结构稳定、重复度高的数据库语义抽成可验证模型定义。
- EF Core 继续落地，但不再被视为平台长期唯一真相来源。

这比原来的纯 EF Core 设计更适合当前项目的长期演进，也更适合 AI 参与重构、验证和后续生成工作。
