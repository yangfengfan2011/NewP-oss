# 强约束元数据与代码内核边界

## 1. 文档目的

本文档用于收口当前仓库在插件包、运行时投影、元数据 authoring 与静态资源治理上的统一边界。

当前目标不是把平台继续推向“元数据万能化”，而是明确以下分工：

- 元数据负责声明、约束、归属与可校验输入
- 代码内核负责装载、校验、执行、切换、回滚与冲突处理

本文件优先约束以下目录与链路：

- `modules/<ModuleId>/metadata/**`
- `resources/**`
- `server/kernel/PluginPackages/**`
- `server/modules/MetadataConfigCenter/**`

## 2. 总体原则

### 2.1 元数据只表达事实，不承载流程

元数据可以表达：

- 模块暴露哪些元数据类型
- 某类元数据的 `sourcePath`
- 某类资源或文件的归属范围
- 是否允许某类覆盖
- 版本、兼容性、校验所需的静态约束

元数据不应该表达：

- 多步骤执行流程
- 条件分支算法
- 合并策略实现细节
- 回滚算法
- 运行时装载顺序算法

换句话说，元数据是“受控输入”，不是“解释器脚本”。

### 2.2 代码内核只消费声明，不猜业务语义

内核负责：

- 打包时收集受控内容
- 安装时拆分版本目录与状态目录
- 启用时生成 `runtime/` 与 `public/` 投影视图
- 对路径安全、兼容性、依赖、冲突进行校验
- 在 enable / disable / rollback 时执行原子切换与恢复

内核不应继续依赖“隐式约定 + 复制顺序”来决定最终有效状态。

### 2.3 运行时视图不是 authoring 源

`runtime/` 的职责是“当前生效视图”，不是“长期编辑源”。

因此：

- 读取当前有效元数据时，可以 `runtime` 优先、仓库根目录兜底
- 保存 authoring 结果时，默认应回到可提交的源目录，而不是直接把 `runtime` 当成唯一真源
- 若存在“应用到运行时”的动作，应由内核显式执行，而不是由 authoring 服务隐式写入投影视图

## 3. 模块元数据边界

### 3.1 `modules/<ModuleId>/metadata/**` 的职责

模块元数据用于声明模块自己的结构化定义，例如：

- `metadata.manifest.json`
- `settings/*.json`
- 后续受控纳入的其它定义类元数据

这类元数据具有以下特征：

- 作用域天然限定在单一 `ModuleId`
- 可随插件版本进入包目录
- 启用后可投影到 `runtime/modules/<ModuleId>/metadata/**`
- 不允许跨模块互相覆盖

### 3.2 模块元数据的职责分界

模块元数据负责：

- 声明类型是否启用
- 声明类型的 `sourcePath`
- 声明 authoring 能力是否开放

`MetadataConfigCenter` 与 Kernel 负责：

- 发现 manifest
- 定位实际文件
- 解析、校验、序列化
- 生成版本摘要
- 处理保存与后续应用链路

因此，`settings` 的 schema、校验和写回格式属于代码适配器职责，不应反向塞回元数据去描述“如何执行保存”。

## 4. `resources/**` 边界

### 4.1 `resources/**` 的定位

`resources/**` 表示平台级静态资源命名空间，不等同于单模块私有目录。

它可以承载：

- `resources/localization/**`
- `resources/enumerations/**`
- 后续被纳入平台治理的静态资源

它不应该变成：

- 任意插件私有缓存目录
- 无边界的扩展脚本入口
- 复杂流程配置中心

### 4.2 `resources/**` 的默认治理原则

`resources/**` 的后续处理必须遵守以下默认规则：

1. 包内 `resources/**` 是版本化快照

每个插件版本下携带的 `resources/**`，表示该版本安装包所依赖或声明的资源快照，真实版本归属在：

- `packages/<ModuleId>/<Version>/resources/**`

2. `runtime/resources/**` 是非版本化生效视图

`runtime/resources/**` 只表达“当前启用组合下的最终结果”，不表达来源算法，不保存 authoring 历史。

3. 同路径资源不得依赖隐式覆盖

若多个已启用插件向同一路径投影资源：

- 内容完全一致：允许复用
- 内容不一致：默认视为冲突，应由内核拒绝投影或显式报错

默认禁止“最后一个复制进去就生效”的隐式覆盖语义。

4. 覆盖必须是显式许可，而不是复制副作用

后续若确实需要覆盖，元数据最多只声明：

- 谁是资源 owner
- 哪类路径允许 override
- override 的范围是模块私有、平台共享还是兼容补丁

真正的冲突检测、排序与最终替换动作必须由内核执行。

5. 版本语义属于内核，不属于资源文件自身

资源文件本身不负责描述“如何从 A 升到 B、如何从 B 回滚到 A”。

版本切换语义应由：

- 插件版本
- 安装状态
- 校验摘要
- 内核投影规则

共同决定。

## 5. 当前推荐的冲突语义

在正式引入更细的资源声明前，仓库应采用以下临时收口口径：

- `modules/<ModuleId>/metadata/**`：模块私有，按模块边界隔离，不允许跨模块覆盖
- `resources/**`：平台共享，默认“同路径同内容可共存；同路径不同内容即冲突”
- 冲突处理：以“失败并提示”优先，不以“静默覆盖”优先
- 回滚语义：始终基于已安装版本目录重新投影，不直接在 `runtime/resources/**` 上做增量热修补

这条规则的核心目的是防止 `resources/**` 在没有治理协议时演化成“谁最后复制，谁说了算”。

## 6. 对当前实现的直接约束

基于当前仓库代码，后续修改应遵守以下收口要求：

1. `scripts/pack-unified-plugin.ps1`

- 可以继续把 `modules/<ModuleId>/metadata/**` 与根 `resources/**` 带入插件包
- 但后续若扩展 `resources/**`，必须同步定义资源归属与冲突口径

2. `RuntimeViewMaterializer`

- 不能长期依赖当前复制顺序决定 `runtime/resources/**` 的最终结果
- 后续应显式检测资源冲突，并把“相同内容可复用 / 不同内容要失败”固化为测试

3. `MetadataManifestService` / `ModuleMetadataStore`

- 读取有效视图时，保持 `runtime` 优先、仓库根目录兜底
- 写入 authoring 内容时，应逐步收口为“默认写可提交源目录，应用链路由内核负责”

4. `MetadataConfigCenter`

- 继续只承担定义层 authoring
- 不把“应用”“切换版本”“回滚投影”下推到元数据配置服务内部

## 7. 近期最值得做的收口项

按优先级建议如下：

1. 在 Kernel 中补齐 `resources/**` 的冲突检测与失败语义，并加回归测试
2. 明确 `ModuleMetadataStore` 的 authoring 写入根，避免默认写入 `runtime`
3. 为 `resources/**` 增加最小声明面，只声明 owner / scope / override-allowance，不引入流程描述
4. 逐步把插件包中的关键身份声明从“源码正则抽取”收口到“显式声明 + 代码校验”

## 8. 一句话准则

如果某项信息是在说明“它是什么、归谁、允许什么”，优先进入元数据。

如果某项信息是在决定“怎么装、怎么校验、怎么切、怎么回滚”，必须留在代码内核。
