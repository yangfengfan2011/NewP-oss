# Codex 审查清单

本文档用于 Codex 审查执行结果，目标是让实现、文档和验证收口保持稳定且可重复。

## 1. 范围审查

- 当前改动是否只覆盖当前工作包？
- 是否修改了工作包未授权的文件？
- 是否把文档任务扩成了实现任务？
- 是否把局部任务扩成了阶段性大改？

## 2. 口径审查

- 是否与 `AGENTS.md` 的架构和 AI-first 规则一致？
- 是否与 `docs/phases/post-phase-6-stage-map.md` 和任务相关设计、计划、验证记录的阶段口径一致？
- 是否把“建议”“边界”“待实现”误写成“已完成”？
- 是否引入了仓库内没有依据的新机制或新术语？

## 3. 文件边界审查

- `AGENTS.md`
- `docs/phases/post-phase-6-stage-map.md`
- `docs/designs/*`
- `docs/superpowers/specs/*`
- `docs/superpowers/plans/*`

如果这些文件被改动，必须确认：

- 是否在当前工作包允许范围内
- 是否确有必要
- 是否没有顺手混入无关修改

## 4. 可复用性审查

- 文档是否能直接推送到 GitHub？
- 是否使用相对路径而不是本机绝对路径？
- 是否避免依赖单机临时文件、缓存目录、IDE 状态？
- 是否对跨机器继续工作的读者仍然成立？

## 5. 质量审查

- 是否存在 `TODO`、`TBD`、`待补`、`占位` 等占位词？
- 是否有明显重复、矛盾或前后不一致？
- 是否把要求写得足够具体，避免后续再次靠口头解释？
- 是否保留了最小必要范围，而不是过度设计？

## 6. 验证审查

- Copilot 是否按工作包要求做了自检？
- 已运行的验证是否与任务类型匹配？
- 没跑的验证是否被明确说明？
- 对于纯文档工作，是否至少做了范围和占位词自检？

## 7. `askQuestions` 审查

- Copilot 是否先读了仓库上下文，再决定提问？
- 提问是否只围绕当前工作包真正缺失的信息？
- 是否出现了本可自行保守假设却反复追问的情况？
- 用户补充的关键信息，是否被正确反映到最终改动或汇报里？

## 8. 结论模板

审查时优先给出以下结论之一：

- 通过：可以进入下一工作包
- 需返修：范围对了，但有遗漏或表述风险
- 不通过：范围漂移、口径冲突或关键约束缺失

如果需要返修，优先指出：

- 哪个文件有问题
- 问题属于范围、口径、验证还是边界
- 下一轮应只改什么，不要重写什么
