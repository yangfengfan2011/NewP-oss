# 生成单文件票据板

把已确认的规格转换为一个可连续执行、可中断恢复的 `tickets.md`。让该文件同时承担任务分解、依赖关系、实时状态和收口证据的唯一来源。

## 输入与输出

- 默认读取 `.scratch/<feature-slug>/spec.md`；未指定功能目录时，只在来源唯一且明确时自行定位。
- 先读取仓库 `AGENTS.md`、`docs/agents/issue-tracker.md` 和与任务直接相关的项目规则。
- 把结果输出到规格同目录的 `.scratch/<feature-slug>/tickets.md`。除非用户明确指定其他路径，不要写入 `docs/superpowers/specs/`、`docs/superpowers/plans/` 或其他目录。
- 在文件顶部记录规格来源。用户明确以一个既有规格或其他路径为来源时，仍把新票据板写入对应的 `.scratch/<feature-slug>/tickets.md`，不要迁移或改写原规格。
- 使用 [assets/ticket-board-template.md](assets/ticket-board-template.md) 作为结构起点，并按实际任务删减不需要的字段。

## 工作流

1. 确认规格已覆盖目标、范围、非目标、关键行为和验收边界。若缺口会改变票据拆分，列出缺口并保持票据板为 `draft`，不要自行发明产品决策。
2. 对依赖代码现状的内容，按 `AGENTS.md` 的代码定位规则核对真实入口、影响范围和可执行验证命令。
3. 按可验证的纵向行为切分票据。优先让一张票据交付一个完整、可测试的增量，避免仅按前端、后端、测试等技术层机械拆分。
4. 为票据分配稳定编号 `01`、`02`……，写出依赖关系，并保证依赖图无环。
5. 在票据板顶部预留执行基线并写明默认提交策略；为每张票据写明状态、依赖、目标、允许与禁止范围、验收条件、验证方式，以及 TDD/seam、提交前审查和提交信息的执行记录占位。
6. 仅在跨票据的 runtime、浏览器或全链路验收确实需要独立工作时增加收口票据；否则把全量验证放在文件末尾的收口章节。
7. 将初次生成的票据板状态设为 `draft`。用户确认票据板，或明确要求“生成后直接执行”时，才进入 `ready` 或执行状态。

## 票据质量要求

- 让每张票据保持单一主要目标，并能独立判断完成或失败。
- 把范围外事项显式写入非目标，不把顺手重构混入票据。
- 验收条件描述可观察结果，不只写“完成实现”。
- 验证命令尽量具体到项目、测试或手工路径；无法预先确定时写出需要确认的验证类型和失败信号。
- 依赖使用票据编号；无依赖时写“无”。
- 票据板状态只使用 `draft`、`ready`、`in-progress`、`blocked`、`completed`；单票状态只使用 `pending`、`in-progress`、`blocked`、`completed`、`skipped`。`docs/agents/triage-labels.md` 中的值只用于 GitHub Issue 分流，不写入票据板状态字段。
- 不创建 `.scratch/<feature-slug>/issues/` 下的逐票文件。既有逐票文件只作为历史参考，不与 `tickets.md` 双向同步。

## 更新已有票据板

- 先保留已经完成的验收勾选、执行记录、验证证据和提交信息。
- 规格变化影响已完成票据时，明确记录变化原因；只有确实需要重做时才把它重新打开。
- 新票据使用后续编号，不复用已经出现过的编号。
- 不同时维护另一份实施计划或拆分票据副本。

## 完成输出

报告票据板路径、票据数量、首批可执行票据、关键依赖和仍需确认的问题。除非用户同时明确授权实施，否则在票据板生成后停止，不修改业务代码，也不提交变更。
