# Shell 控件展示页详细设计

## 1. 背景

当前仓库已经在 `frontend/packages/ui` 中沉淀了一批共享控件与结构型页面块，但缺少一个在运行中可直接访问的统一展示入口。现阶段团队想确认“我们现在有哪些控件类型”，仅靠 README、实现目录和零散模块消费页面，不利于快速盘点、协作沟通和后续复用。

因此需要在 `frontend/packages/shell` 中新增一个正式可访问的静态展示页，用最小交互示例统一展示当前已存在的共享控件类型，并通过左侧导航暴露入口，便于团队日常查阅。

## 2. 目标

- 在 `frontend/packages/shell` 中新增一个正式可访问的“控件展示”页面。
- 页面以静态布局集中展示当前 `@icp-platform/ui` 中已有的控件类型。
- 每个控件提供最小可操作示例，而不是仅做文本罗列。
- 页面在左侧导航中可见，作为 Shell 内正式页面访问。
- 明确区分“稳定可用控件”和“候选/预建控件”。

## 3. 非目标

- 不引入 Storybook 或独立文档站。
- 不新增后端 API、数据库或真实业务数据依赖。
- 不修改 Host 侧装载逻辑。
- 不扩展为完整的设计系统管理平台。
- 不顺带重构现有 Home、模块页或 UI 包内部实现。

## 4. 设计原则

- **最小接入**：变更收敛在 `frontend/packages/shell`，只新增页面、路由接入和导航入口。
- **真实展示**：每个控件都给出一个最小但真实可理解的交互示例。
- **清晰分层**：按当前组件库分层方式组织内容，避免页面结构与组件库认知脱节。
- **边界明确**：候选控件明确标识为“预建/非稳定公开 API”。
- **AI-first**：单页目标明确、可读性高、验证路径清晰、回滚范围小。

## 5. 页面信息结构

页面建议命名为“控件展示”，路由建议为 `/ui-showcase`。

页面整体结构分为以下区块：

1. 页面头部
2. 基础控件区
3. 结构型页面块区
4. 复合控件区
5. 候选控件区

页面头部展示：

- 页面标题
- 页面说明
- 当前统计摘要，例如“稳定控件数量”“候选控件数量”

每个区块使用统一的分组标题与说明文本，内部采用卡片栅格或纵向卡片列表展示控件示例。

## 6. 控件展示范围

### 6.1 基础控件

展示以下稳定基础控件：

- `Button`
- `Input`
- `Textarea`
- `Select`
- `Checkbox`
- `Switch`
- `Radio`
- `Badge`
- `Tabs`
- `EmptyState`
- `LoadingState`
- `ErrorState`
- `Pagination`

### 6.2 结构型页面块

展示以下结构型页面块：

- `PageHeader`
- `Panel`
- `SummaryCard`
- `TableWrap`
- `StatusBadge`
- `FormInline`

### 6.3 复合控件

展示以下复合控件：

- `Modal`
- `Drawer`
- `ConfirmDialog`
- `FilterBar`
- `KeyValueEditor`

### 6.4 候选控件

展示以下候选/预建控件，并在 UI 中显式标注“当前为候选能力，不视为稳定公开 API”：

- `Tree`
- `TreeSelect`
- `DataTable`
- `Uploader`

## 7. 交互设计

页面是静态布局，但每个控件卡片提供最小交互示例。所有示例仅使用本地 mock 数据和页面内状态，不依赖真实接口。

### 7.1 基础控件交互

- `Button`：展示常见变体与禁用态。
- `Input` / `Textarea`：展示输入、标签、错误文本。
- `Select`：展示选项切换。
- `Checkbox` / `Switch` / `Radio`：展示勾选与切换行为。
- `Badge`：展示不同状态。
- `Tabs`：展示切换不同面板。
- `EmptyState` / `LoadingState` / `ErrorState`：直接展示典型状态。
- `Pagination`：通过本地页码切换体现交互。

### 7.2 结构型页面块交互

结构型页面块主要展示布局用途，不做复杂行为：

- `PageHeader`：展示标题、说明和操作按钮区域。
- `Panel`：展示标题、meta、actions 与内容承载方式。
- `SummaryCard`：展示摘要信息。
- `TableWrap`：用 mock 数据展示简单表格。
- `StatusBadge`：展示多种状态。
- `FormInline`：用小型表单控件组合展示行内布局。

### 7.3 复合控件交互

- `Modal`：按钮打开、关闭。
- `Drawer`：按钮打开、关闭。
- `ConfirmDialog`：按钮触发确认与取消。
- `FilterBar`：用 mock 筛选字段和本地 state 演示查询/重置。
- `KeyValueEditor`：演示键值对新增、修改和删除的最小交互。

### 7.4 候选控件交互

- `Tree`：使用静态树数据演示节点选择。
- `TreeSelect`：使用静态树数据演示下拉选择。
- `DataTable`：使用 mock 数据演示排序、选择或工具栏区域。
- `Uploader`：使用本地 mock 列表演示添加项、删除项或重试动作。

候选区的交互目标是“展示能力轮廓”，不是承诺稳定接口。

## 8. 视觉与布局策略

- 页面使用当前 `@icp-platform/ui` 的页面块搭建，不引入新的 Shell 私有视觉体系。
- 区块之间采用清晰留白与分组标题，保证长页面也易于扫描。
- 每个控件卡片保持统一结构：
  - 控件名称
  - 简短说明
  - 示例区域
- 对候选控件卡片增加提示标签或说明文案。

## 9. 路由与导航接入

本次改动仅在 `frontend/packages/shell` 范围内完成接入：

- 新增页面文件，例如 `src/pages/UiShowcase.tsx`
- 在 Shell 路由中注册该页面
- 在左侧导航中新增“控件展示”入口

该入口属于平台内建展示能力，不通过业务模块前端插件注册，不改变 Host 侧边界。

## 10. 文件边界

预计会修改或新增以下文件：

- 新增 `frontend/packages/shell/src/pages/UiShowcase.tsx`
- 视需要新增 `frontend/packages/shell/src/pages/UiShowcase.css` 或复用现有样式文件
- 修改 `frontend/packages/shell/src/App.tsx`
- 修改 `frontend/packages/shell/src/components/Sidebar.tsx`
- 新增或修改相关测试文件

如能复用现有 Shell 样式，则优先不拆独立样式文件；如页面样式明显超出复用能力，再单独新增局部样式文件。

## 11. 测试与验证

### 11.1 测试策略

先补测试，再实现页面：

- 路由/导航测试：
  - 断言“控件展示”入口可见
  - 断言访问 `/ui-showcase` 能渲染页面主体
- 页面渲染测试：
  - 断言页面标题存在
  - 断言四个分组标题存在
  - 断言若干代表控件示例存在，例如 `Button`、`PageHeader`、`Modal`、`Tree`

### 11.2 命令验证

建议至少执行：

```powershell
pnpm --dir .\frontend\packages\shell exec vitest --run
```

```powershell
pnpm --dir .\frontend build
```

如果全量 `shell` 测试成本过高，可先定向跑新增测试文件，再补一次前端构建。

## 12. 风险与控制

| 风险 | 影响 | 控制方式 |
|------|------|----------|
| 页面过长、信息密度过高 | 可读性下降 | 按分组组织并保持卡片结构统一 |
| 交互示例写成业务逻辑 | 展示页边界失控 | 全部使用本地 state 与 mock 数据 |
| 候选控件被误认为稳定 API | 误导后续使用者 | 显式标识“候选/非稳定公开 API” |
| 样式过度定制 | 增加维护成本 | 优先复用现有 UI 组件和 Shell 样式能力 |

## 13. 回滚思路

本次改动的回滚应收敛为：

- 删除展示页组件
- 删除对应路由
- 删除侧边栏入口
- 删除新增测试

由于不涉及后端、数据或迁移脚本，回滚风险低，范围清晰。

## 14. 实施结论

本次采用“Shell 内正式页面 + 左侧导航入口 + 单页分区展示 + 最小交互示例”的方案。

这样既能满足“把现有控件类型集中展示出来”的直接需求，也能保持平台边界稳定，不把本次任务扩展成独立文档站或新的 UI 平台工程。
