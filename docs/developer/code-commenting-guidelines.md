# 代码注释规则

本文档定义本仓库的默认代码注释约定，目标不是“把每行代码都解释一遍”，而是让人和 agent 都能在小上下文内理解、修改、验证和回滚关键实现。

适用范围：

- `server/`
- `frontend/`
- `modules/`
- `tests/`

如果要在“多写一点注释”和“保持代码整洁”之间做选择，默认优先保留高价值注释，而不是保留口口相传的隐性知识。

默认新增代码注释使用简体中文。只有两类例外：

- 文件本身已经长期采用英文注释约定，继续写中文会破坏一致性
- 注释必须保留英文术语、协议名、接口名、字段名或错误字面量，例如 `manifest`、`runtime`、`default export`、`Content-Type`

## 1. 注释的目标

本仓库中的注释主要承担下面几类职责：

- 解释实现为什么存在，而不只是它做了什么
- 标出模块边界、宿主边界和受控接入点
- 说明状态切换、生效顺序、冲突处理与回滚路径
- 暴露失败信号、排查入口和验证方式
- 帮助后续 agent 在不通读全仓的前提下继续修改

## 2. 哪些地方默认必须写注释

以下位置默认应有注释；如果没有，需要能明确说明为什么代码本身已经足够表达：

- 宿主装配入口
  - 例如 Host / Shell 的模块注册、运行时清单装载、插件发现与组合
- 跨模块边界代码
  - 例如 Kernel 与模块、Shell 与模块、SDK 与消费者之间的桥接逻辑
- 迁移、导入、投影、生效切换、回滚恢复
  - 例如 staging、swap、restore、fallback、prune 等流程
- 有隐藏前提或显式保护的路径
  - 例如路径安全校验、冲突拒绝、权限兜底、幂等保护
- 大型页面或应用服务中的关键状态编排
  - 例如“已保存未应用”“本地草稿 vs 已生效数据”“宿主管理模块补注册”
- 非直观的测试意图
  - 例如测试某个历史回归、边界条件、异常顺序，而不是普通 happy path

## 3. 哪些地方不应堆注释

以下情况通常不应写注释，除非有特殊上下文：

- 对变量赋值、if 分支、循环体逐句翻译
- 代码名已经足够清楚的简单 getter / setter / DTO 字段
- UI 里的显而易见样式字面量
- “开始处理数据”“返回结果”这类没有新增信息的句子

坏例子：

```ts
// 设置 loading 为 true
setLoading(true);
```

这类注释不会降低理解成本，反而会稀释真正重要的信息。

## 4. 优先写什么

当你只能补少量注释时，优先级按下面顺序处理：

1. 为什么这个实现必须存在
2. 哪些边界不能被打破
3. 失败时会出现什么信号
4. 如何验证它仍然正确
5. 如果后续要改，应该先看哪里

推荐注释风格：

- 用 1 到 3 行的短注释概括一个代码块的意图
- 放在代码块前，而不是行尾堆说明
- 术语与项目文档保持一致，比如“authoring 真源”“host-managed”“运行时视图”“已保存未应用”

## 5. 按层次的默认要求

### 后端

- 公共契约和 DTO：保留必要 XML 注释，确保字段语义、边界和用途清楚
- 公共契约和 SDK 的 `public` 方法：默认补 XML 方法注释，至少说明方法职责、关键参数语义和返回结果含义
- 应用服务 / 核心流程：注释关键状态机、容错、回滚和冲突处理
- Controller：只在路由、权限边界、兼容路径不直观时写注释

### 前端

- 模块入口 / Shell 装配：注释模块接入规则、回退路径和宿主管理逻辑
- 页面组件：注释关键状态关系，不要给每个 hook 或样式对象写说明
- 服务层：注释接口契约差异、兼容假设和错误处理前提

### 测试

- 优先通过测试名表达意图
- 当测试覆盖历史 bug、复杂前置条件或回滚路径时，在测试块前补一句说明

## 6. 方法注释规则

不是每个方法都要写注释，但关键方法应当有明确规则，而不是靠个人感觉。

### 哪些方法默认应写注释

- `public interface` 中的方法
- 对外暴露的 SDK 方法
- 含业务语义、参数约束或返回状态不直观的 `public` 方法
- 关键实现方法
  - 例如负责状态切换、投影替换、恢复、依赖校验、冲突处理的方法

### 哪些方法通常不必写方法注释

- 语义已经非常直接的简单查询方法
- 仅做字段映射、简单拼装、无隐藏约束的小方法
- 纯 UI 事件透传方法，且方法体本身已经足够清楚

### 方法注释怎么选形式

#### XML 方法注释

适用于：

- 公共契约
- SDK 入口
- 需要 IDE 悬浮提示直接帮助调用方理解的方法

推荐写法：

```csharp
/// <summary>
/// 将 authoring 目录中的 SettingDefinition 投影到运行时目录。
/// 该操作只负责生效切换，不修改 authoring 真源。
/// </summary>
/// <param name="moduleId">要应用的模块 ID。</param>
/// <param name="cancellationToken">取消令牌。</param>
/// <returns>应用结果，包含当前是否仍存在未应用变更。</returns>
public Task<ApplySettingDefinitionsResult> ApplySettingDefinitionsAsync(
    string moduleId,
    CancellationToken cancellationToken = default)
```

要求：

- `summary` 说明职责，不要只复述方法名
- `param` 只写有业务语义或容易误解的参数
- `returns` 只在返回值不能一眼看懂时写

#### 方法前普通注释

适用于：

- `private` / `internal` 实现方法
- 关键流程收口点
- 状态切换和恢复方法

推荐写法：

```csharp
// 这里用 staging + backup 的方式替换 runtime 目录，
// 目的是保证 apply 失败时仍能恢复到上一版有效视图。
private async Task ReplaceRuntimeProjectionAsync(
    string sourceDirectory,
    string runtimeDirectory,
    CancellationToken cancellationToken)
```

### 方法注释的坏例子

```csharp
/// <summary>
/// 获取模块
/// </summary>
public Module GetModule()
```

这种注释几乎没有新增信息，不如不写。

## 7. 推荐模板

### 代码块前注释

```csharp
// 这里先在 staging 目录完成投影，只有全部成功后才替换正式 runtime/public，
// 这样失败时仍可回到上一版有效视图，而不是留下半更新状态。
```

```ts
// host-managed 模块不应依赖运行时 manifest 是否包含自身；
// 即使外部清单存在，Shell 仍要补注册这些宿主内建能力。
```

### XML 注释

适用于公共契约、模型和 SDK 入口。重点写字段语义，不要只重复属性名。

## 8. 与 AI-First 目标的关系

对本仓库来说，注释不是附属装饰，而是 AI-First 约束的一部分。高价值注释至少要帮助回答下面这些问题：

- 入口在哪里
- 边界是什么
- 验证怎么做
- 失败信号是什么
- 回滚思路是什么

如果这些问题只能靠人工口头补充，说明当前实现还不够适合 agent 持续接手。

## 9. 最低自检清单

提交前至少快速检查：

- 这次改动里是否新增了复杂流程或关键状态切换
- 这些位置是否有解释“为什么/边界/失败信号”的注释
- 新增或改动的公共方法是否需要 XML 方法注释
- 是否出现了逐行翻译式注释
- 文档、代码术语是否一致

如果答案分别是“是 / 否 / 是 / 否”，那这次改动通常还不适合直接提交。
