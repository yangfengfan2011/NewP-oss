# 组件化护栏与接入机制设计

## 1. 背景

当前平台整体仍然沿着组件化方向推进，但已经识别出三类结构性风险：

1. 公共能力的归属边界还不够硬，后续容易继续散落到具体模块实现中。
2. 前端模块接入虽然已有 SDK 和 `registerModules.ts` 入口，但实际机制仍接近“手工维护模块列表”，Shell 仍有被持续侵入的风险。
3. 前后端模板与脚手架已经存在，但还没有把“组件化红线”和“AI-first 执行约束”固化为默认输出。

本轮不调整现有业务模块实现，也不引入完整插件化自动发现机制，而是优先收紧新增开发轨道，使后续新增模块默认更符合组件化与 AI-first 目标。

## 2. 目标

- 把组件化红线补成显式约束，而不是口头共识。
- 把前后端模板和脚手架收紧成“默认产出合格组件”的机制。
- 把前端模块接入方式收紧成受控接入点，降低 Shell 被业务模块直接侵入的风险。
- 为后续 AI 或人工新增模块提供统一、可复制、可验证的路径。

## 3. 非目标

- 不在本轮重构已存在模块的内部实现。
- 不在本轮引入运行时自动发现、远程插件加载或完整插件市场机制。
- 不在本轮改动 Phase 5 的迁移实现代码。
- 不在本轮处理“所有历史模块一键迁移到新接入机制”。

## 4. 方案选择

### 方案 A：只补文档约束

优点：

- 成本最低。
- 不影响现有构建链和脚手架。

问题：

- 新模块仍可轻易绕过约束。
- 组件化风险会继续通过模板和脚手架被复制。

### 方案 B：补文档 + 收紧模板 + 收紧接入机制

优点：

- 成本可控。
- 可以直接作用到后续新增模块。
- 能同时覆盖三类风险点。

问题：

- 仍保留一个受控的宿主接入点，而不是彻底自动发现。

### 方案 C：直接做完整插件化自动发现

优点：

- 长期组件化最彻底。

问题：

- 范围显著扩大。
- 会引入构建、运行时发现、兼容性和调试复杂度。

本轮采用 `方案 B`。

## 5. 设计总览

本轮设计分为三块：

1. **组件化护栏文档化**
   在主文档、模块契约和接入指南中补齐“哪些能力必须沉到底层、哪些改动禁止直接进入 Shell/Host、模板默认应输出什么”。

2. **模板与脚手架组件化**
   收紧前后端模板与 `new-module` 脚本，让新增模块默认带有：
   - 标准模块入口
   - 最小服务层/页面层边界
   - 最小验证路径
   - 禁改提示与接入说明

3. **前端受控注册机制**
   不立即改成运行时自动发现，但把 `registerModules.ts` 明确成“唯一受控清单入口”，并让脚手架只修改该入口，不再鼓励手工侵入 Shell 其他内部结构。

## 6. 关键设计

### 6.1 公共能力归属表

新增一份组件化归属文档，至少明确以下分类：

- 必须进入 `Kernel / SDK / Contracts`
  - 模块元数据契约
  - 权限声明契约
  - 配置声明契约
  - 菜单/路由注册契约
  - 迁移/导入钩子契约
  - 通用注册帮助器

- 可以留在模块内部
  - 模块特定 DTO
  - 模块特定查询/命令服务
  - 模块私有页面布局
  - 模块私有映射规则实现

- 禁止直接进入 Host / Shell
  - 业务规则
  - 模块私有状态
  - 模块私有数据访问细节
  - 临时迁移逻辑

这个表的作用不是增加抽象，而是防止“先放模块里，后面再说”成为默认做法。

### 6.2 前端受控注册机制

保留当前集中注册思路，但将其正式定义为：

- `frontend/packages/shell/src/registerModules.ts` 是唯一允许的 Shell 级模块注册清单。
- 新模块接入只允许通过：
  - 脚手架自动更新该文件
  - 或按指南手工更新该文件
- 新模块不得直接修改 Shell 的布局、Provider 结构、路由装配内部实现，除非明确进入单独设计。

同时将该文件的角色从“普通实现文件”提升为“受控接入清单”，并在文档中明确：

- 它是允许修改的 Shell 文件。
- 其他 Shell 内部文件默认不应被模块接入任务直接修改。

### 6.3 模板与脚手架默认输出

前后端模板和 `new-module` 脚手架需要统一强调四件事：

- 模块声明通过标准入口暴露。
- 页面/服务/模块入口三层最小分离。
- 默认带一个最小联通验证路径。
- 默认生成的文档或 README 说明接入边界和禁改区。

前端模板默认输出应保持：

- `src/index.ts` 只做模块声明。
- `src/pages/*` 只做页面呈现与最小加载逻辑。
- `src/services/*` 只做接口访问。

后端模板默认输出应保持：

- `*Module.cs` 只做模块入口与声明。
- `Controllers/*` 只做轻量接口入口。
- `Services/*` 只做模块内部服务。

### 6.4 AI-first 接入说明

新增模块的脚手架与指南要补一个小节，明确告诉后续 agent：

- 可以改哪些文件。
- 默认不要改哪些文件。
- 完成新增模块后至少跑哪些命令。
- 如果需要超出受控接入点，应先补设计。

这一步是把“组件化”和“AI 可执行性”合并起来，避免后续新增模块虽然结构上像组件，但操作路径仍高度依赖人工经验。

## 7. 文件级设计

### 7.1 需要新增的文件

- `docs/architecture/componentization-guardrails.md`
  组件化红线、公共能力归属表、Shell/Host 禁改区说明。

### 7.2 需要修改的文件

- `AGENTS.md`
  增加组件化护栏与受控接入规则摘要。

- `docs/architecture/module-contract.md`
  增加“Host/Shell 受控接入点”和“公共能力归属”说明。

- `frontend/docs/module-integration-guide.md`
  补齐“唯一受控接入点”“禁改区”“最小验证命令”。

- `frontend/packages/shell/src/registerModules.ts`
  补注释或结构说明，明确其作为受控清单入口的角色。

- `server/templates/backend-module-template/README.md`
  补齐模板边界说明和公共能力归属约束。

- `frontend/templates/frontend-module-template/README.md`
  补齐模板边界说明和 Shell 禁改提示。

- `scripts/new-module.ps1`
- `scripts/new-module.sh`
  补齐生成说明、受控接入提示，并确保脚手架只触达允许的接入点。

- `README.md`
  在项目入口处补一条“新增模块请遵循组件化护栏与受控接入机制”。

## 8. 验证方案

本轮以“机制和约束生效”为验证目标，不以业务功能变化为目标。

验证成功的标准：

1. 存在一份统一的组件化护栏文档。
2. 主文档、模块契约、前端接入指南对组件化红线口径一致。
3. Shell 受控接入点被明确写清。
4. 前后端模板 README 都能说明边界、禁改区和最小验证路径。
5. `new-module` 脚手架只修改允许的接入点，不引导开发者侵入 Shell 内部。

建议执行的验证：

- `Get-Content` 检查相关文档是否口径一致。
- 运行一次脚手架的 dry-run 式检查或至少人工检查脚手架修改目标文件列表。
- 如环境允许，使用现有样例模块对照模板说明做人工核对。

## 9. 风险与控制

### 9.1 风险

- 文档改了，但脚手架仍沿用旧习惯。
- 脚手架只更新受控清单，但使用者仍手工改 Shell 其他文件。
- 公共能力归属表过宽，导致无意义抽象增加。

### 9.2 控制方式

- 让脚手架和指南口径一致，而不是只改文档。
- 在接入指南中把“允许修改文件列表”写清楚。
- 归属表只覆盖当前已稳定的公共能力，不提前抽象未知需求。

## 10. 结论

本轮通过“文档护栏 + 模板护栏 + 接入机制护栏”三层组合，先把新增开发轨道收紧到更符合组件化和 AI-first 的状态，而不对现有模块实现做大规模返工。

这能直接缓解当前三个风险点：

- 公共能力归属不清：通过归属表和契约文档收紧。
- 前端模块侵入 Shell：通过受控清单入口和禁改区说明收紧。
- 模板不够像可复制组件：通过模板 README、脚手架提示和最小验证路径收紧。
