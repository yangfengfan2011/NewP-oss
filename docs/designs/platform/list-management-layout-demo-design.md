# 列表管理界面静态页设计

## 1. 背景

当前平台已经在文档中收敛出以下方向：

- 列表管理页应优先采用 `list view`
- 表单承载方式按对象复杂度分为 `page / drawer / dialog`
- `page / drawer` 的标准维护动作更适合放在标题区，并随滚动保持可见
- 轻量表单或单任务表单仍可继续使用 `dialog`

但“新平台列表管理界面整体长什么样”还没有形成一张能直接讨论的完整静态页面。仅靠条目描述，仍然容易混淆：

- 查询区是长期固定在右边，还是只把复杂筛选放进右侧抽屉
- 导出按钮和分页应该放在表格的哪个层级
- 页面头部、轻筛选条、表格区和高级筛选抽屉之间如何分层

因此需要一份完整静态页面，作为新平台列表管理界面的布局讨论稿。

## 2. 目标

- 输出一个完整静态页面，展示新平台默认的列表管理界面布局。
- 页面同时体现：
  - 左侧导航
  - 页面头部
  - 轻筛选条
  - 表格主体
  - 表格底部导出与分页
  - 右侧高级筛选抽屉
- 让页面可以直接本地打开，用于后续继续讨论和收敛。

## 3. 非目标

- 不在本设计中接入真实前端工程。
- 不在本设计中接入真实 API、权限、规则中心或元数据运行时。
- 不在本设计中实现交互逻辑，只做静态展示。
- 不在本设计中替代平台主设计文档，只作为补充讨论稿。

## 4. 范围

本次交付：

- 一份补充设计文档
- 一个完整静态 HTML 页面

本次不交付：

- 真实列表页实现
- 真实抽屉交互
- 真实查询与导出逻辑

## 5. 设计约束

- 必须体现“轻筛选条”为列表页默认筛选入口。
- 若当前页面声明了高级筛选能力，则额外体现“右侧高级筛选抽屉”；若未声明，则不强行显示高级筛选入口。
- 导出按钮必须体现为表格区底部左侧能力，不与页面头部主动作混放。
- 分页必须体现为表格区底部右侧能力。
- 页面需要同时展示左侧导航与业务主体，便于讨论整体层级。
- 设计稿必须独立可打开，不依赖构建。

## 6. 布局结论

推荐的新平台列表管理界面默认布局为：

1. 左侧导航  
承接模块入口与分组，不承载页面内部结构。

2. 页面头部  
放标题、说明和少量主动作，例如：
- 新建
- 刷新

当前阶段不默认引入对象化摘要卡片区域；若后续某类页面确实需要 summary 区，应作为单独可选能力设计，而不是列表管理页默认骨架。

页面头部中的“说明”建议理解为：

- 来自 `view metadata` 的可选 `descriptionKey`
- 使用当前语言解析后的单一文案
- 只用于补充页面用途与范围，不用于承载操作说明书

同时建议当前页面对应一个独立 dic 文件，由：

- `view.dicKey`
- 局部 `titleKey / descriptionKey`

共同定位页面标题与说明文案。

这里不重复展开 `dic` 资源本体结构；`dic` 的识别、`dicKey` 来源与装载规则遵循已有字典/元数据基础设计，本稿只关注列表页如何消费这些文案。

最小解析规则建议与当前前端运行时保持一致：

- `view metadata` 内继续声明 `dicKey + 局部 key`
- `dic` 文件进入前端语言缓存时，统一扁平化成 `${dicKey}.${localKey} -> 文案`
- 运行时交给现有 `t(key, fallback?)` 的最终 key 统一拼成：
  - `${dicKey}.${localKey}`
- 例如：
  - `dicKey = PersonListView`
  - `titleKey = Title`
  - 最终解析为：`t("PersonListView.Title")`

这样可以直接复用前端已有的语言缓存与 `t()` 入口，而不必额外引入第二套页面文案解析机制。

当前不建议：

- 在同一界面同时显示多语言文本
- 把长段指导说明硬塞进头部说明区

3. 轻筛选条  
放最常用的 2 到 4 个筛选项，例如：
- 关键字
- 状态
- 所属公司
- 所属部门

若当前页面声明了高级筛选能力，则额外提供“高级筛选”入口；若常用筛选已经足够，则默认不显示该入口。

轻筛选条中的条件顺序建议直接由 `view metadata.query.fields` 决定，而不是页面代码临时拼装。

轻筛选条中每个条件的 label 文案建议按当前语言显示，并遵循：

- 每个条件都在 `view metadata.query.fields` 中显式声明自己的 `labelKey`
- `source = model` 时，`model metadata` 继续提供字段静态语义，但不直接决定最终 label
- `source = preset` 时，预置查询项定义继续提供查询能力语义，但不直接决定最终 label

也就是说，查询条件的显示文案建议由：

- `view.dicKey`
- 条件自身的 `labelKey`

共同定位，并在运行时统一拼成 `${dicKey}.${labelKey}` 后再交给 `t()` 解析。

4. 表格主区域  
包含：
- 表格工具条
- 列表主体
- 表格底部左侧导出能力
- 表格底部右侧总数与分页

5. 右侧高级筛选抽屉（可选）  
仅在页面声明了高级筛选能力时出现，用于承接更多筛选项，不长期挤压表格宽度。

高级筛选抽屉中的内容建议进一步拆成：

- `sections`
- `section.fields`

也就是不仅要声明“有没有高级筛选”，还要声明：

- 抽屉分几个 section
- 每个 section 的标题是什么
- 每个 section 里放哪些查询条件

这里的 `section.fields` 应直接定义高级筛选抽屉自身显示的条件，而不是再回头复用轻筛选条里的字段引用。

轻筛选条与高级筛选抽屉中的字段都建议统一显式声明一个查询操作符，首轮支持：

- `=`
- `like`
- `>`
- `>=`
- `<`
- `<=`
- `in`

高级筛选抽屉中的条件 label 也应遵循同一条多语言规则：

- 字段 label 只显示当前语言
- 字段 label 由 `section.fields[].labelKey` 显式定义
- `source = model` 时由 `model metadata` 提供字段静态语义
- `source = preset` 时由预置查询项定义提供查询能力语义
- `section` 标题则继续由 `section.titleKey` 负责

列标题也建议采用同一思路：

- 每列在 `list.columns` 中显式声明 `labelKey`
- 列标题通过 `view.dicKey + labelKey` 定位，并在运行时统一拼成 `${dicKey}.${labelKey}` 解析
- 不再默认回退到模型字段名或 projection 字段名

这样静态稿、后续运行时装配和实际 view metadata 才能保持一致，不会退回到页面代码里手工组织抽屉内容。

## 7. 推荐原因

- 比老平台那种“查询区长期在右边”更省空间，也更适合移动和窄屏收缩。
- 当页面确实存在更多筛选项时，仍然可以通过可选抽屉保留“右侧筛选”的使用习惯。
- 页面头部、轻筛选条、表格区、抽屉四层职责清楚，后续更容易元数据化。
- 不把“摘要卡片区”默认塞进列表页，有利于保持不同对象之间的通用骨架稳定。

- HTML 文件可直接本地打开

  - 轻筛选条
  - 表格区

## 10. 风险与回滚

- 若静态页把太多辅助说明塞进画面，可能削弱主布局判断
- 若静态页没有把“导出属于表格底部能力”表达清楚，会误导后续平台设计

回滚方式：

- 这只是讨论稿，不接入运行时
- 直接删除补充文档与 HTML 文件即可
- 不影响现有平台主设计文档

### 失败信号是什么

- 页面头部、筛选条、表格底部能力混成一层
- 高级筛选入口在未声明能力时仍默认出现
- 高级筛选抽屉看起来像长期固定右栏
- 导出和分页没有体现出表格内归属

### 如何回滚

- 删除该补充设计文档与静态 HTML 文件
- 保留当前主设计，不影响既有结论
