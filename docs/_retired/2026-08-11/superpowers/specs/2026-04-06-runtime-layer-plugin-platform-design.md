# 运行层插件平台设计

## 1. 背景

当前平台已经具备部分“运行时模块装配”基础，但整体仍然处于“源码集成优先、运行时加载为辅”的过渡状态：

- 宿主项目 [HostApi.csproj](D:/Github/ICP-X/NewP/apps/host-api/HostApi.csproj) 仍通过 `ProjectReference` 直接引用后端模块工程。
- 宿主启动代码 [Program.cs](D:/Github/ICP-X/NewP/apps/host-api/Program.cs) 已经开始扫描 `*Module.dll` 并尝试运行时加载模块程序集。
- 内核已有模块装配基础，如 [AssemblyModuleLoader.cs](D:/Github/ICP-X/NewP/server/kernel/ModuleLoader/AssemblyModuleLoader.cs) 和 [ModuleRegistry.cs](D:/Github/ICP-X/NewP/server/kernel/ModuleLoader/ModuleRegistry.cs)。

在此前提下，如果未来客户只拿运行包和模块包，不拿源码，且客户会要求自行开发扩展，那么当前框架还不够。

当前模式更像：

- 内部源码研发仓库
- 宿主编译期静态装配
- 发布时附带 DLL

目标模式则应升级为：

- 平台运行层独立交付
- 模块以独立包交付和装配
- 外部开发者通过稳定 SDK / Contracts 开发插件模块
- 宿主通过正式的模块发现、校验、加载、隔离和兼容机制运行模块

这不再只是“运行包 + 模块包”交付问题，而是正式的插件平台问题，因此本轮选择 `方案 C`。

## 2. 目标

- 把当前框架演进成“运行层 + 模块包 + 外部扩展开发”模式。
- 让客户部署时不需要拿源码，只需要拿运行包、模块包和配置。
- 让客户或合作方在受控前提下，能基于公开 SDK / Contracts 开发自己的扩展模块。
- 形成正式的模块发现、清单、兼容、装载和验证机制。
- 让内部研发和外部扩展走同一套插件协议，而不是两套平行体系。

## 3. 非目标

- 本轮不直接实现完整插件市场、远程分发平台或在线安装中心。
- 本轮不引入微服务化拆分。
- 本轮不一次性解决所有模块的前后端运行时动态装配。
- 本轮不要求客户立即获得全部源码级调试体验。

## 4. 方案对比结论

### 4.1 为什么不选 B

`方案 B` 适合“客户只部署、不自己开发”的场景。

但一旦客户会自己开发，就会出现以下问题：

- `ProjectReference` 和内部仓库约定无法作为稳定外部扩展协议。
- 运行时加载只是宿主内部技巧，无法替代正式插件契约。
- 缺少模块包元数据、版本兼容、依赖规则和校验机制。
- 缺少面向外部的 SDK 稳定面、开发模板和验证标准。

因此，`B` 可以作为演进过渡步骤，但不能作为终局架构。

### 4.2 为什么选 C

`方案 C` 更适合当前目标，因为它把“交付不带源码”和“外部可扩展开发”一起纳入正式架构能力：

- 平台对外暴露稳定扩展面。
- 模块成为正式插件包，而不是内部工程副产物。
- 宿主通过正式协议装配模块，而不是依赖源码引用或特判。
- 外部开发者和内部开发者共享统一规则。

## 5. 目标架构

目标平台分为五层：

### 5.1 Runtime Layer

运行层，负责：

- 宿主启动
- 认证和基础设施
- 插件目录管理
- 插件包发现
- 插件清单解析
- 插件依赖与兼容检查
- 插件装配和生命周期管理

运行层不承载业务模块私有规则。

### 5.2 Platform SDK / Contracts

对内对外统一的稳定扩展面，负责：

- 模块元数据契约
- 服务注册契约
- 菜单、路由、权限、配置契约
- 迁移或导入钩子契约
- 插件清单模型
- 版本兼容声明模型

这一层必须成为外部扩展开发的主依赖。

### 5.3 Module Package

每个模块最终交付为独立模块包，至少包含：

- 模块程序集
- 模块清单文件
- 兼容声明
- 依赖声明
- 可选静态前端资源或前端清单
- 模块验证说明

### 5.4 Development Tooling

开发工具层负责：

- 插件脚手架
- 包构建脚本
- 本地调试宿主
- 模块打包脚本
- 最小验证脚本
- 外部开发者指南

### 5.5 Governance

治理层负责：

- 模块版本兼容规则
- 禁用或回滚策略
- 模块来源校验
- 模块签名或哈希校验
- 运行期错误隔离策略

## 6. 当前与目标的核心差距

### 6.1 宿主装配方式

当前：

- 主要依赖 `ProjectReference`
- 辅助性扫描 DLL
- 存在文件名规则和特判

目标：

- 正式依赖插件目录和插件清单
- 不再以 `ProjectReference` 作为正式装配方式
- 不依赖模块文件名特判

### 6.2 模块交付模型

当前：

- 模块本质上是源码工程
- DLL 更像构建副产物

目标：

- 模块首先是“插件包”
- 插件包有正式结构、清单和兼容声明

### 6.3 外部开发能力

当前：

- 更偏内部研发仓库
- 尚无正式外部开发协议

目标：

- 外部开发者基于公开 SDK / Contracts 开发
- 开发与打包流程稳定
- 文档和模板足够独立

### 6.4 前后端装配一致性

当前：

- 后端有 DLL 装配雏形
- 前端仍主要依赖源码工作区注册

目标：

- 至少形成后端正式插件化
- 前端需逐步具备插件清单或模块资源装配能力
- 最终前后端不再依赖仓库内手工接线作为正式交付模型

## 7. 分阶段改造路线

### Phase C0：协议冻结

目标：

- 冻结插件平台的基本协议，不再继续使用“临时扫描 + 特判”作为长期机制。

交付：

- 插件包目录结构设计
- 插件清单模型
- 插件元数据字段定义
- 版本兼容规则初版
- 插件装配流程设计

### Phase C1：后端正式插件装配

目标：

- 把后端从编译期模块装配切到运行时正式插件装配。

交付：

- 插件目录扫描器
- 清单解析器
- 稳定的模块加载器
- 宿主插件加载配置
- 去除宿主对业务模块的正式 `ProjectReference`

### Phase C2：模块包与打包流程

目标：

- 让模块成为正式交付物，而不是源码工程副产物。

交付：

- 模块包结构
- 模块打包脚本
- 发布目录规范
- 模块包校验规则
- 示例插件包

### Phase C3：外部开发者 SDK 与模板

目标：

- 让客户或合作方可以在不接触宿主源码的前提下开发模块。

交付：

- 稳定 SDK / Contracts
- 面向外部的模板项目
- 开发者文档
- 最小本地调试宿主
- 外部模块构建和验证流程

### Phase C4：插件治理

目标：

- 让插件平台具备基本运行治理能力，而不是只能“能加载”。

交付：

- 插件版本兼容检查
- 依赖冲突检查
- 插件禁用机制
- 插件回滚说明
- 哈希或签名校验
- 加载失败隔离与日志

### Phase C5：前端插件化收口

目标：

- 让前端从工作区源码注册过渡到正式插件装配模型。

交付：

- 前端模块清单或资源清单
- Shell 对模块前端清单的加载策略
- 前后端插件包配套规则
- 前端插件验证路径

## 8. 详细改造项

### 8.1 Runtime Layer

需要改造：

- 宿主配置模型
- 插件目录约定
- 插件发现与清单加载
- 插件生命周期钩子
- 模块加载错误处理

### 8.2 SDK / Contracts

需要改造：

- 插件清单契约
- 模块版本与兼容声明
- 更清晰的扩展点模型
- 对外发布的稳定 API 面

### 8.3 Packaging

需要改造：

- 模块输出目录
- 包内元数据
- 模块资源布局
- 安装和升级策略

### 8.4 Tooling

需要改造：

- `new-module` 脚手架升级为插件模板脚手架
- 打包脚本
- 本地运行层调试脚本
- 示例外部插件仓库模板

### 8.5 Governance

需要改造：

- 插件兼容矩阵
- 插件签名或哈希校验
- 禁用和回滚
- 运行期日志与审计

## 9. 风险

### 9.1 过度设计风险

如果一次性把插件生态能力全部拉进来，主线会被拖慢。

控制方式：

- 先做协议和正式装配。
- 再做外部开发模板。
- 最后补治理和前端插件化收口。

### 9.2 双轨并行过久风险

如果源码集成和插件装配并行太久，架构会长期摇摆。

控制方式：

- 明确开发期便利机制和正式交付机制的边界。
- 设定阶段目标：从某个阶段开始，新增模块必须能以插件包方式验证。

### 9.3 前端落后于后端风险

后端先插件化而前端仍源码注册，会导致交付模型不对称。

控制方式：

- 接受“先后端、再前端”的分步路径，但在 Phase C0 就定义前端目标接口。

## 10. 验收标准

平台可以视为进入 `C` 方案主轨道，至少应满足：

1. 宿主可在无业务模块源码引用的前提下启动。
2. 宿主可从正式插件目录和清单中发现并加载模块。
3. 至少一个模块可以独立打包、部署和装配。
4. 外部开发者可基于公开模板和 SDK 开发最小插件。
5. 插件兼容失败时，宿主能给出清晰错误并阻止错误装配。

## 11. 结论

在“客户会要求自己开发，但不交付源码”的前提下，平台终局必须是正式插件平台，也就是 `方案 C`。

当前框架并非不能演进到这个方向，反而已经具备一部分基础；但它还没有正式跨过“源码仓库集成”到“插件平台装配”的分界线。

因此，后续改造的重点不是继续堆模块，而是优先完成：

- 协议冻结
- 宿主正式插件装配
- 模块包交付
- 外部开发模板
- 插件治理

这五个方向构成 `C` 方案的正式改造主线。
