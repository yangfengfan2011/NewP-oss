# 开发环境数据库结构同步工具详细设计

> 当前状态说明：本文是工具第一版的基础设计。后续已通过
> [`dev-schema-sync-risk-confirm-apply-design.md`](./dev-schema-sync-risk-confirm-apply-design.md)
> 补充 CLI 高风险确认执行设计，并已在 Host 开发启动链路中接入 Safe 级自动同步；Host 仍不会自动执行 Confirm 级高风险计划。

## 1. 背景

当前仓库已经形成正式环境基于 EF Core migration 的数据库结构演进链路。该链路适合发布、审计和回滚，但在开发阶段存在两个明显问题：

- 每次新增或调整一个模型，都需要在多个迁移工程中生成多组 `.cs` 文件；
- 当变更频繁、仍处于探索阶段时，开发者为了让本地数据库跟上模型，经常需要先生成 migration，再执行启动或手动更新数据库，反馈回路偏长。

本设计要解决的问题，不是替代正式环境的 migration 体系，而是为开发环境提供一条更轻量的“根据当前 `model` 文件直接同步数据库结构”的受控工具链，缩短本地迭代路径，同时保持正式环境的可审计、可发布和可回退能力不变。

## 2. 目标

- 提供一个独立可执行的开发工具，根据当前仓库中的 `model` 文件与开发数据库实际结构做 diff。
- 默认输出结构化执行计划；可选输出 SQL 预览；只有在明确要求时才执行。
- 执行时自动应用低风险结构变更；遇到高风险变更时提供二次确认。
- 默认支持全量扫描并同步所有 `model` 文件，不要求用户手动选择数据库类型或指定模型文件。
- 第一版只支持 SQL Server，但整体结构预留多 provider 扩展点。
- 不生成 migration 文件，不更新 `ModelSnapshot`，不修改 `__EFMigrationsHistory`。

## 3. 非目标

- 不替代正式环境现有的 migration 发布链路。
- 不兼容手写 `ModelDefinition`，只管理 `model` 文件。
- 不负责复杂数据迁移、数据修复、数据搬运或跨表重组。
- 不自动处理与 `model` 无关的数据库对象治理。
- 第一版不支持 MySQL、Oracle 的实际执行。
- 基础工具设计阶段不修改 Host API 启动逻辑；当前实现已在 Host 开发启动链路中受控接入 Safe 级自动同步，Confirm 级计划仍阻断启动并要求回到 CLI 显式确认。

## 4. 范围

本轮设计覆盖：

- 新增独立工具项目：`server/tools/dev-schema-sync/`
- 工具输出与执行入口
- `model` 文件扫描、校验、投影
- SQL Server 数据库结构读取、diff、计划输出、风险确认和执行
- 对现有配置的受控复用

本轮不覆盖：

- `apps/host-api/` 启动链路改造
- 现有 migration 工程结构调整
- 非 `model` 管理对象的自动接管
- 删除数据库之外的文件、配置、部署流程改造

## 5. 设计约束

- 工具只服务开发环境，不得弱化正式环境基于 migration 的结构治理能力。
- 输入源必须唯一：只读取仓库中的 `model` 文件，不允许与手写定义混用。
- 数据库连接来源必须复用系统现有配置，不再新增一套独立连接串 authoring 入口。
- 默认不做隐式执行：必须先输出计划，再显式要求执行。
- 高风险变更必须再次确认，确认失败时整次执行停止，避免落入半成功状态。
- 重命名不依赖启发式猜测，必须由 `historyName` 等显式元数据提供历史名称。
- 删除列、类型变更、可空性收紧、显式 rename 等高风险动作允许执行，但必须在计划和确认阶段明确暴露风险。
- 第一版不支持通过当前 `model` 集合缺失直接自动删表。
- 工具输出、日志和文档默认使用简体中文，便于后续 agent 在小上下文中继续维护。

## 6. 总体方案

### 6.1 方案概述

新增一个独立控制台工具 `dev-schema-sync`，作为开发环境数据库结构同步器。它在运行时执行以下流程：

1. 读取系统当前数据库配置并识别目标数据库。
2. 递归扫描仓库中的 `model` 文件。
3. 使用现有 modeling 校验与投影能力构造目标 schema。
4. 读取开发数据库当前真实结构。
5. 生成结构化变更计划。
6. 默认输出计划；传入 `--sql` 时输出 SQL 预览；传入 `--apply` 时进入确认与执行流程。
7. 执行低风险动作；若计划包含高风险动作，则在整体确认后再进行二次高风险确认。

### 6.2 为什么选这个方案

- 它把“开发期快速同步”与“正式环境 migration 发布”清晰分离，符合当前仓库的边界要求。
- 它把复杂逻辑放在工具项目中，而不是脚本中，便于测试、演进和后续多 provider 扩展。
- 它坚持只认 `model`，能够推动建模入口统一，不继续扩大手写定义的长期成本。
- 它通过计划预览和二次确认降低高风险结构变更误执行的概率。

### 6.3 为什么不选其他方案

- 不选“继续仅依赖 migration 文件”：开发阶段反馈回路过长，无法解决本轮痛点。
- 不选“直接把逻辑写进 PowerShell 脚本”：扩展性、可测试性和结构清晰度都不足。
- 不选“启动时自动同步数据库”：会把开发辅助能力固化进 Host 启动链路，增加运行时隐式行为和排错成本。
- 不选“兼容手写定义和 model 混合输入”：会让同步边界模糊，不符合当前 AI-First 统一 authoring 方向。

## 7. 关键模型

### 7.1 核心内部模型

- `TargetSchema`
  - 表示从全量 `model` 文件投影出来的目标数据库结构。

- `DatabaseSchema`
  - 表示从 SQL Server 当前数据库读取出来的实际结构快照。

- `SchemaPlan`
  - 表示一次同步计划，包含 summary、受管对象、计划动作、SQL 预览与风险统计。

- `SchemaOperation`
  - 单个结构动作，建议至少支持：
  - `CreateTable`
  - `AddColumn`
  - `DropColumn`
  - `RenameTable`
  - `RenameColumn`
  - `AlterColumnType`
  - `AlterNullability`
  - `CreateIndex`
  - `DropIndex`
  - `RecreateIndex`

- `RiskLevel`
  - `Safe`
  - `Confirm`

### 7.2 model 扩展元数据

为支持显式 rename，模型 authoring 增加可选历史名称属性：

- 模型级：`historyName`
- 字段级：`historyName`

该属性作为 `schemaVersion: "1.0"` 下的向后兼容可选扩展，不单独提升 schemaVersion。

使用规则：

- 当当前名称不存在、但 `historyName` 指向对象存在时，识别为 rename。
- 当当前名称和 `historyName` 同时存在时，视为冲突并报错。
- 工具不做启发式 rename 猜测。

### 7.3 模块与边界

- `Cli`
  - 负责参数处理、计划输出、确认交互、退出码。

- `ModelSchemaLoader`
  - 负责扫描并加载全量 `model` 文件，输出目标 schema。

- `DatabaseSchemaReader`
  - 负责读取 SQL Server 当前表、列、主键、索引、类型、可空性等信息。

- `SchemaDiffEngine`
  - 负责把目标 schema 与当前 schema 比较成结构化 plan。

- `RiskClassifier`
  - 负责为每个动作标记风险级别并汇总高风险项。

- `SchemaApplyExecutor`
  - 负责把动作转换为 SQL 并按顺序执行。

## 8. 核心流程

### 8.1 主流程：预览计划

1. 用户运行 `dev-schema-sync.exe`。
2. 工具读取系统数据库配置。
3. 工具扫描全量 `model` 文件并投影目标 schema。
4. 工具读取当前数据库结构。
5. 工具生成 `SchemaPlan`。
6. 工具输出：
   - summary
   - 本次受管对象
   - 计划动作列表
7. 若用户带 `--sql`，继续输出 SQL 预览。
8. 未带 `--apply` 时结束。

### 8.2 主流程：执行同步

1. 用户运行 `dev-schema-sync.exe --apply`，可选带 `--sql`。
2. 工具先输出 plan，并输出 SQL 预览；`--apply` 会强制输出 SQL Preview，`--sql --apply` 是推荐写法。
3. 工具进行第一次确认：“是否执行本次同步计划”。
4. 若存在高风险动作，工具汇总高风险项并进行第二次确认。
5. 用户确认后，工具按计划顺序执行。
6. 执行完成后输出成功 summary。

### 8.3 高风险动作

以下动作标记为 `Confirm`：

- `DropColumn`
- `RenameTable`
- `RenameColumn`
- `AlterColumnType`
- `AlterNullability`（从可空改为非空）
- 导致唯一性变化或需要重建的索引调整

### 8.4 异常流程

- `model` 文件加载失败、校验失败或投影失败：整次操作立即失败，不进入执行。
- `historyName` 冲突：整次操作立即失败。
- 数据库连接失败或元数据读取失败：整次操作立即失败。
- 第一次确认被拒绝：不执行任何变更，返回“用户取消”。
- 第二次高风险确认被拒绝：整次操作终止，不执行任何变更。
- SQL 执行中途失败：输出失败动作和已执行位置，停止后续动作。

## 9. 接口与集成点

### 9.1 命令行接口

建议第一版支持：

- `dev-schema-sync.exe`
  - 输出结构化计划，不执行。

- `dev-schema-sync.exe --sql`
  - 输出结构化计划和 SQL 预览，不执行。

- `dev-schema-sync.exe --apply`
  - 输出结构化计划和 SQL 预览，确认后执行。

- `dev-schema-sync.exe --sql --apply`
  - 输出结构化计划和 SQL 预览，确认后执行。

- `--json`
  - 输出 JSON 格式计划。

第一版直接支持 `--json`，便于后续脚本、CI 与 agent 消费结构化计划。

当前实现不支持 `--yes`、`--allow-risk` 或其他跳过确认参数；这是有意保留的安全边界。

### 9.2 配置接入

- 工具直接复用系统现有持久化配置读取逻辑。
- 用户不手动传数据库 provider 或连接串。
- provider 由配置决定；第一版只对 SQL Server 进入实际执行。
- 配置解析优先级与 Host API 保持一致：
  - 仓库内基础配置文件
  - 开发环境配置文件
  - 环境变量覆盖
- 工具需要从仓库根定位配置根目录，而不是依赖当前终端工作目录。
- 若当前配置 provider 不是 SQL Server，工具直接报错并退出，不进入计划生成。

### 9.3 model 发现规则

- 默认扫描：`modules/**/metadata/models/*.model.json`
- 全量发现，不要求用户手工指定
- 不读取手写 `ModelDefinition`

## 10. 数据与状态

- 输入数据源：
  - 仓库中的 `model` 文件
  - 当前系统数据库配置
  - 开发数据库当前结构元数据

- 运行状态：
  - 本次同步计划为内存对象，不落库、不写 migration 文件
  - SQL 预览仅作为计划输出的一部分，不单独持久化

- 一致性要求：
  - 一次执行中，目标 schema 以本次扫描到的 `model` 集合为唯一权威源
  - 若计划中包含高风险动作但用户拒绝确认，整次执行不落任何结构变更
  - 工具不写入 `__EFMigrationsHistory`

- 未托管对象策略：
  - 数据库中存在、但不在本次 `model` 集合中的表，工具可在计划中提示为“未托管对象”
  - 不因未托管对象自动触发删除或接管
  - 默认输出中增加 `Unmanaged Objects Summary` 区块，只显示数量与前若干项样例，不展开全部明细

- 删表策略：
  - 第一版不支持通过“当前 model 集合缺失某张表”直接生成 `DropTable`
  - 不在本次 `model` 集合中的表统一归类为未托管对象
  - 若后续需要支持删表，必须额外引入显式 authoring 语义，再通过单独设计补充

## 11. 错误处理与风险

### 11.1 主要风险

- `model` 与数据库结构的命名约定不稳定，导致 rename、删列、加列判断混乱。
- 高风险动作误执行，带来数据兼容性或数据丢失风险。
- 仓库中仍存在手写定义时，工具无法覆盖全部持久化对象，造成“部分对象自动同步、部分对象仍靠 migration”的混用状态。
- SQL Server 元数据读取与实际 SQL 执行顺序不一致，导致计划正确但执行失败。

### 11.2 风险控制方式

- rename 只依赖显式 `historyName`，不依赖猜测。
- 所有高风险动作进入第二次确认。
- 默认只输出计划，不隐式执行。
- 执行日志中明确输出当前动作、目标对象与失败位置。
- 文档中明确：仅 `model` 管理对象由该工具接管，手写定义继续走 migration。

### 11.3 回滚与降级思路

- 本工具不承担自动回滚；若执行后需回退，应通过开发库重建、手工 SQL、或补 migration 方式处理。
- 若工具行为异常，可停止使用该工具，回到现有 migration 开发链路，不影响正式环境发布能力。

## 12. 验证方案

### 12.1 功能验证

- 能扫描并加载全量 `model` 文件。
- 能在无参数时输出结构化计划。
- `--sql` 能输出 SQL 预览。
- `--apply` 能在第一次确认后执行低风险动作。
- 存在高风险动作时，能触发第二次确认。
- 用户拒绝第一次或第二次确认时，不执行任何变更。

### 12.2 差异场景验证

至少覆盖：

1. 新增表
2. 新增列
3. 新增索引
4. 使用 `historyName` 的表重命名
5. 使用 `historyName` 的列重命名
6. 删列
7. 列类型变更
8. 可空变更
9. 数据库多出未托管表时，输出未托管对象摘要且不自动删表

### 12.3 SQL Server 端到端 smoke

- 准备一个开发库基线
- 调整若干 `model` 文件
- 运行工具输出计划
- 再运行 `--sql --apply`
- 确认数据库结构与 `model` 对齐

### 12.4 与正式链路隔离验证

- 运行工具前后，仓库中不应新增 migration 文件
- `ModelSnapshot` 不应被修改
- `__EFMigrationsHistory` 不应新增记录

## 13. 已确认决策

- `historyName` 作为 `model` 的标准可选属性保留在 `schemaVersion: "1.0"` 中：
  - 模型级放在模型对象下
  - 字段级放在字段对象下
  - 不单独提升 schemaVersion
- 第一版直接支持 `--json` 输出。
- 默认计划输出中增加 `Unmanaged Objects Summary` 区块。
- 第一版只交付 SQL Server，MySQL 与 Oracle 仅保留扩展位，不纳入本轮承诺范围。
- 第一版不支持自动删表；数据库中多出的表统一归类为未托管对象。

## 14. 实施拆分建议

1. 建立工具项目骨架
   - 最小交付：`exe` 可运行，能读取配置并输出当前数据库连接目标与基础运行摘要。

2. 接入 `model` 扫描、校验与投影
   - 最小交付：能输出受管对象清单。

3. 接入 SQL Server schema reader
   - 最小交付：能输出当前数据库结构摘要。

4. 实现 diff engine 与结构化 plan
   - 最小交付：能输出建表、加列、删列、rename、索引变化计划。

5. 实现 SQL 预览与 apply executor
   - 最小交付：能针对低风险动作执行。

6. 实现高风险确认与失败输出
   - 最小交付：高风险场景可二次确认，失败时输出明确位置。

7. 补齐验证与文档收口
   - 最小交付：具备最小 smoke 证据。

## 15. AI-First 最小检查清单

1. 入口在哪里
   - 第一版已实现为 `server/tools/dev-schema-sync/DevSchemaSync.csproj` 对应的独立 `dev-schema-sync.exe`。
   - 当前命令入口支持 `--json`、`--sql`、`--apply`。

2. 边界在哪里
   - 只读 `model` 文件；只管开发环境 schema sync；不接管手写定义；不替代正式 migration。

3. 如何验证
   - 通过 plan 输出、SQL 预览、`--apply` 执行、高风险确认、SQL Server smoke 进行验证。
   - 验证记录落点见 `docs/verification/dev-schema-sync-tool-verification.md`。

4. 失败信号是什么
   - `model` 校验失败、`historyName` 冲突、数据库连接失败、SQL 执行失败、用户拒绝确认。

5. 如何回滚
   - 停用该工具并回到现有 migration 开发链路；已执行的开发库结构变更通过重建数据库或手工 SQL 回退。
