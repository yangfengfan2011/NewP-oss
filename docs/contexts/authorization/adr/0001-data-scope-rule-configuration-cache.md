# 数据范围规则配置使用完整内存缓存

状态：已采用（核心生命周期 [#339](https://github.com/yangfengfan2011/NewP/issues/339)、资源级坏配置隔离 [#340](https://github.com/yangfengfan2011/NewP/issues/340)）。正式规格：[Spec #338](https://github.com/yangfengfan2011/NewP/issues/338)。

数据范围判权频繁读取相同规则配置。Authorization 完整缓存自己拥有的 `DataScopeRuleNode` 与 `DataScopeRuleSubject`，包含停用节点和全部主体项，并按资源提供已解析的完整规则树或明确的配置故障。数据库继续作为持久化事实源；缓存仅承载规则配置，不保存用户的最终允许或拒绝结果。当前身份、对象直接授权、业务事实及数据库侧过滤继续沿既有裁决边界处理；LocalAdmin 豁免、停用动作及其读取依赖保持原有短路顺序。

缓存由 Authorization 内部装载和维护，复用平台具名缓存及事务提交参与机制。现有权限契约保持，业务模块无需适配或显式刷新。规则管理列表继续使用现有数据库分页读取；保存、删除在原事务内读取实际旧配置，完成校验和审计。管理读库与判权缓存不承诺跨请求的全局一致快照。

两张表在初始化时读取一致集合，作为完整不可变结果发布；正式写入按实际变更局部维护，节点、主体项、资源与关联索引和资源错误状态共同发布。一次逻辑判权使用同一份完整规则快照。已经取得规则的在途操作可以完成；保存成功后新取得规则的操作必须使用新配置。

正常更新在数据库提交之前建立读取屏障，提交至缓存发布的窗口中，需要新取得规则的操作短暂等待，发布完成后继续判权。这是正常同步，不因正在发布而立即报告缓存故障，也不跳过规则检查。准备失败且数据库回滚时，保留原有效配置；请求等待仍遵循取消语义。

能够明确归属的坏规则保留为快照中的资源错误，只使所属资源无法正常判权；停用节点及主体同样完整校验，不跳过坏规则或将其当成未配置。其他资源继续使用同次发布的完整有效规则，Host就绪不因资源局部故障变为整体不可用。根与父关联按完整节点事实核对，跨资源损坏同时封闭关系两端，不能按资源分桶后隐藏坏子树。全表读取失败、孤立主体、未登记资源等无法建立可靠归属的配置，以及整体发布失败，使整份缓存不可用。合法空表是有效配置，不等同于装载失败。

整份缓存不可用时，依赖有效规则缓存的请求返回服务暂不可用，后台自动恢复；不使用已知失效的旧配置，不把故障解释为没有配置，也不自动回源数据库。若数据库已提交而缓存发布失败，保存响应明确表达“已保存，但规则暂不可用”，不声称回滚或自动重放写入。无法确认提交结果时沿用平台已有的提交结果未知语义，恢复读取数据库事实后再发布。平台统一负责将故障翻译为各现有消费入口的稳定响应，业务模块无需分别增加处理。

本次沿用单活动 Host 的部署边界。运行期间规则变更只能通过正式系统写入口；必须直接改库时停服维护，重启后重新装载。旧配置可以完整物化时，正式保存继续记录实际旧值并随发布清除对应资源错误；旧值无法完整读取时不绕过审计或新增修复入口。健康缓存不轮询数据库，不引入跨实例同步或数据库变更捕获。

硬性验收边界是正常稳态判权对两张规则表的查询次数为零，以及既有权限结果、整树保存和删除、在途快照、提交发布等待、回滚、故障隔离及恢复语义正确。规则管理、初始化和故障恢复所需读取分别按原职责处理，不计作稳态判权查表；不把所有授权或业务 SQL 均为零作为本次目标。

容量与并发采用 100／1,000 个规则节点、每节点 10 条主体项，以及普通用户请求并发 1／16／64 的代表性样本，覆盖多资源、层级规则和读取过程中保存规则。它们是测量规模，不是产品上限，也不等同于在线用户数。在相同数据和请求条件下比较改造前后的真实请求 SQL 次数、吞吐量及延迟，记录完整装载、内存、更新及提交发布等待成本；本次不预设响应时间、内存或提升倍数的通过预算，内存观察区分分配量、GC 后整个测试进程的托管存活量和工作集；进程数值包含 Host、fixture 及客户端等对象，不代表精确缓存对象驻留。

本决策替代规则读取不跨请求缓存的旧实现边界；当前正式判权已经使用完整缓存，管理分页及事务内实际前值仍读取数据库。回退时恢复平台内部从数据库读取规则及相应服务注册，保留规则、主体项、审计数据和原裁决语义；不通过删除配置或跳过数据范围检查回退。自动回源、多实例一致性及缓存最终授权结果需要独立评审。
