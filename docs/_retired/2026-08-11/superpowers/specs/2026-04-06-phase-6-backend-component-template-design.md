# Phase 6 第一版：后端组件化模板设计

## 1. 背景

`Phase 5` 已完成首个旧资产迁移 POC，证明了新平台能够承接真实旧资产，并形成一条可被 AI 复用的迁移模板。下一阶段不应立即转向“万能脚手架”或整套 `Icp Studio` Web 化实现，而应继续夯实平台的组件化开发体验。

结合当前仓库状态，服务端已经具备：

- `Kernel` 模块契约与模块装配能力
- `Sdk` 中的 `ModuleBase`
- 多个真实模块样本：`Demo`、`Authorization`、`ConfigCenter`、`Audit`、`Files`
- 对应的模块级测试项目

但目前仍缺少一套正式、统一、可复用的“后端模块标准模板”。这会带来两个问题：

- 新模块接入方式主要依赖阅读现有模块和口头约定，规则分散
- AI 或新成员新增模块时，容易把模块边界、依赖方向和测试责任做散

因此，`Phase 6` 第一版的目标应聚焦为：先沉淀“仓库内标准模板 + 活示例模块 + 最小验证链路”，让后端模块接入变得契约化、重复性高、便于 AI 执行，同时不偏离组件化设计目标。

## 2. 目标

- 形成一份正式的后端组件化模板设计文档
- 在仓库内提供一套标准后端模块模板骨架
- 提供一个真实的后端示例模块，作为活模板持续维护
- 固化新增后端模块所需的最小文件集合、职责边界和验证方式
- 让后续的前端模板与脚手架建立在稳定契约之上，而不是反过来定义契约

## 3. 非目标

- 本阶段不实现可执行脚手架命令
- 本阶段不处理前端组件化模板
- 本阶段不引入新的平台级业务能力，只解决模板化与开发体验问题
- 本阶段不改变现有 Host、Kernel、SDK 的基础装配模型
- 本阶段不提供隐藏式跨模块快捷调用或宿主内部访问通道

## 4. 设计原则

### 4.1 组件化优先于便利性

模板的首要职责不是“更快生成代码”，而是“确保新增模块仍按组件化契约接入平台”。任何为了省事而绕过模块边界、SDK 或契约的做法，均不属于本阶段目标。

### 4.2 契约优先于脚手架

在模块契约、职责边界、测试结构尚未完全稳定前，不应过早固化成命令行脚手架。第一版先沉淀标准模板与示例模块，后续脚手架只负责把已稳定的模板自动化。

### 4.3 活模板优先于静态模板

单纯的模板目录容易漂移。第一版必须同时提供一个真实示例模块，使模板、文档和验证链路始终围绕真实样本演进。

### 4.4 AI-First 但不牺牲边界

模板设计要让 AI 能在小上下文中新增或修改模块，但不能因此把规则做成“万能入口”或把职责揉在一起。AI 友好来自边界清晰、入口稳定、验证局部化，而不是来自耦合度更高的封装。

## 5. 方案选型

### 方案 A：标准模板文档 + 示例模块 + 最小验证链路

做法：

- 输出正式模板设计文档
- 在仓库内沉淀标准模板骨架
- 提供一个真实后端示例模块
- 补齐对应验证命令与最小测试模板

优点：

- 最符合当前组件化目标
- 不会过早把不稳定约定写死进工具
- 便于 AI 与人工共同维护

缺点：

- 第一次复制模块时仍需要少量手工替换

### 方案 B：文档模板 + 代码骨架目录

做法：

- 只提供模板文档和可复制骨架目录

优点：

- 上手快，实施成本低

缺点：

- 没有真实样本时，模板容易失真
- 难以长期验证模板与现有模块契约是否一致

### 方案 C：直接实现脚手架命令

做法：

- 直接做一个内部生成命令

优点：

- 使用体验最好

缺点：

- 过早固化不稳定契约
- 容易引入为脚手架妥协的结构设计
- 最容易偏离组件化目标

### 推荐结论

采用 `方案 A`，并吸收 `方案 B` 的一部分做法：既产出正式规范，也在仓库中提供可复制骨架，但以真实示例模块为主，确保模板不是“死文件”。

## 6. 交付物设计

第一版交付物分为三层。

### 6.1 规范层

提供正式文档，明确一个标准后端模块至少应说明：

- 模块用途与边界
- 依赖的公共能力
- 模块入口与装配方式
- DI 注册方式
- API 控制器接入方式
- 权限声明方式
- 配置声明方式
- 可选迁移/导入钩子接入方式
- README 最小内容
- 对应测试项目的最小结构

规范层的目标是把“应该怎么接入”写成统一口径，而不是让开发者从多个现有模块中自己归纳。

### 6.2 骨架层

在仓库内提供一套可复制的后端模块标准骨架。骨架不是强制每个目录都必须存在，而是给出默认结构及其职责：

- `ModuleNameModule.cs`
- `Controllers/`
- `DTOs/`
- `Services/`
- `Models/`
- `Repositories/`
- `README.md`

按需启用但需要在规范中明确：

- 哪些目录是必选
- 哪些目录是按需启用
- 哪些职责禁止混放

例如：

- 控制器不应直接承载业务规则
- 权限声明不应零散写在控制器内部
- 配置声明不应直接绑定宿主内部实现
- 模块初始化不应通过隐式启动逻辑偷偷执行迁移或导入

### 6.3 示例层

提供一个真实的后端示例模块，作用包括：

- 作为新增模块的活模板
- 作为后续脚手架的来源样本
- 作为模板规范与测试模板的对照物

示例模块应尽量保持“小而完整”：

- 有模块入口
- 有一个最小 API
- 有最小服务层
- 有至少一种声明能力（权限或配置）
- 有对应测试项目

不要求引入真实复杂业务，重点是把接入路径走通。

## 7. 模块边界要求

后端组件化模板必须显式保留以下边界：

### 7.1 模块只能通过契约接入平台

模板产物必须通过 `Kernel` 契约与 `Sdk` 暴露的稳定入口接入平台，而不是直接依赖 Host 内部细节。

### 7.2 模块内部职责分层清晰

至少要区分：

- 模块入口与装配
- API 层
- 业务服务层
- 数据模型与仓储层

允许小模块省略某些目录，但不能把所有职责都堆进单个入口文件。

### 7.3 不引入跨模块隐藏依赖

模板不应鼓励直接引用其他业务模块内部类，也不应提供“便捷但不透明”的调用方式。跨模块协作只能通过公共契约、公共 SDK 或明确的共享层完成。

### 7.4 不让模板反向定义平台

模板只能复用并封装既有规则，不能为了模板方便去新增绕过契约的后门。脚手架化必须晚于模板稳定，而不是反过来。

## 8. AI-First 对齐方式

本阶段对 `AI-First` 的落实，体现在以下方面：

- 每个交付物都应支持 AI 在小上下文中独立理解与执行
- 模板结构稳定，便于 AI 通过固定入口定位改动点
- 规范中要明确“可以改哪里、不要改哪里、怎么验证”
- 示例模块要足够简单，便于后续拆分为多个局部任务
- 验证方式优先局部化，而不是依赖整仓库人工联调

换句话说，本阶段不是做“AI 生成代码工具”，而是做“让 AI 和人都更容易稳定新增模块的模板体系”。

## 9. 验证标准

`Phase 6` 第一版完成时，应至少满足以下标准：

- 已存在正式的后端组件化模板设计文档
- 已存在仓库内标准模板骨架
- 已存在一个真实后端示例模块
- `HostApi` 可以加载该示例模块
- 示例模块具备最小测试项目或接入现有测试体系
- 至少覆盖模块注册、最小 API、权限或配置声明其中一条关键接入链路
- 文档已明确复制方式、允许改动区、禁止改动区和验证命令

## 10. 实施边界

第一版实施应控制在“后端模板闭环”内，不混入以下工作：

- 前端页面模板
- 端到端全栈示例模块
- CLI 脚手架命令
- `Icp Studio` Web 化功能实现
- 新的公共模块能力开发

如果实施过程中发现需要调整 `Kernel`、`Sdk` 或模块契约，也应以“小幅补齐模板接入所需缺口”为限，避免借机扩展为新一轮平台重构。

## 11. 后续衔接

在第一版后端模板稳定后，推荐按以下顺序推进：

1. 前端组件化模板
2. 端到端示例模块
3. 可执行脚手架命令

这样可以确保自动化工具建立在稳定模板之上，而不是让工具反过来塑造架构。

## 12. 结论

`Phase 6` 第一版应聚焦为“后端组件化模板”，并以“仓库内标准模板 + 活示例模块 + 最小验证链路”作为核心交付物。这个阶段的成功标准不是做出一个看起来方便的生成器，而是在不偏离组件化目标的前提下，先把新增后端模块的接入方式做成可复用、可验证、可被 AI 稳定执行的标准路径。
