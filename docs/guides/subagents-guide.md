# 通用 Subagents 触发模板

本文档说明如何在任务中使用 subagents 进行并行协作。

## 核心原则

- 主线程保留架构判断和最终决策权
- 子代理并行补足能力草案、探索、审查、文档核对、受控实现和测试修复
- 在不扩大范围的前提下，提高任务推进速度
- 当前项目后续以新平台逐步设计开发为主，不默认按旧平台迁移盘点来拆分任务

## 何时适合触发 subagents

满足以下至少 2 条时建议触发：
- 当前任务已经有明确边界
- 主线程已知道自己要产出的结果是什么
- 任务中存在可并行的只读探索或审查工作
- 任务不是纯单文件小改
- 任务存在"摸底 + 审查 + 实施 + 验证"这几类天然可拆分的子工作

## 可用的 Subagents

### 1. platform_explorer
- 只读扫描目录、项目、入口文件
- 列出影响范围
- 找关键类、关键接口、关键配置
- 默认定位当前新平台能力、宿主、运行时资产、扩展点和模块边界

### 2. capability_designer
- 将产品诉求、领域需求或旧平台中可借鉴的思想整理为新平台能力草案
- 区分平台公共能力、模块私有能力、产品专属流程和本轮非目标
- 判断能力更适合落在 Contracts / SDK / Kernel / Host / Shell / templates / modules 的哪个边界
- 输出小步可验证切片、取舍理由和建议方案，不替代主线程做最终架构决策

### 3. design_reviewer
- 在正式实施前审查详细设计或实施计划
- 检查是否满足 `AGENTS.md`、AI-first 五项检查、受控入口、验证方案、失败信号和回滚要求
- 发现缺少详细设计、范围混杂、Host/Shell 越界、元数据承载执行逻辑时，应作为阻塞项提出

### 4. contract_reviewer
- 审查模块边界
- 审查 Host / Kernel / Module / SDK 是否越界
- 审查契约设计是否可扩展

### 5. docs_researcher
- 核对版本行为
- 核对框架配置
- 确认某项实现是否符合当前技术栈

### 6. module_worker
- 在父线程明确文件边界后实现一个模块、能力或文件集合
- 不扩大范围，不主动修改 Host/Shell 内部结构
- 不与其他 live thread 同时修改同一批文件
- 返回实际改动、验证结果、风险和回滚说明

### 7. test_fixer
- 跑 build / test
- 修复编译、类型、lint、测试问题

## 严格并行规则

- 主线程负责最终方案与最终改动
- 子代理尽量只做只读能力设计、探索、设计审查、契约审查和文档核对
- 真正写代码的线程尽量只有一个
- 不允许两个 live thread 同时修改同一批文件
- 不允许子代理绕开 `scope-v1` 擅自扩大范围
- `capability_designer` 和 `design_reviewer` 不负责最终拍板
- `module_worker` 只有在父线程给出明确文件集合和实施边界后才适合使用

## 执行顺序

1. 主线程明确目标和边界
2. 如需求尚未形成平台能力边界，先让 `capability_designer` 产出能力草案
3. 子代理只读探索
4. 详细设计或实施计划完成后，让 `design_reviewer` 做一致性审查
5. 涉及契约、SDK、Host/Shell 或模块边界时，让 `contract_reviewer` 做契约审查
6. 主线程汇总，做最终方案
7. 主线程或单个 `module_worker` 实施代码或文档修改
8. `test_fixer` 在最后统一验证与修复
9. 主线程输出最终摘要
