# Icp Studio Web 化战略路线草案

## 1. 背景

`Icp Studio` 长期承担旧平台中的配置维护、元数据编辑、页面与视图设计、部分平台治理与发布辅助能力。随着新平台 `NewP` 逐步建立模块宿主、认证授权、配置中心、审计和前端 Shell，继续依赖桌面端工具会带来以下问题：

- 配置和元数据维护入口分裂，难以形成统一平台体验。
- 桌面端工具与 Web 平台能力演进节奏脱节，增加维护成本。
- 新平台若仍依赖旧工具，会削弱模块契约、配置中心和审计体系的价值。
- 未来模块、配置、元数据和治理能力需要统一的权限、审计和协作入口，桌面端不再适合作为长期载体。

因此，`Icp Studio` 的最终方向不是继续共存，而是逐步由 Web 平台完整替代。

## 2. 战略目标

- 以 `NewP` 作为唯一长期平台承载体，逐步替代 `Icp Studio`。
- 在 Web 平台内统一承载配置、字典、枚举、元数据和设计器能力。
- 让旧平台资产的迁移、管理、治理和审计进入同一平台能力体系。
- 通过分阶段替代，避免在平台主干尚未稳定时过早重建整套 Studio。

## 3. 非目标

- 不在当前阶段立即逐功能重做 `Icp Studio` 全部界面。
- 不以“桌面交互原样复制”为目标。
- 不把旧平台全部元数据运行时机制直接搬入新平台核心。
- 不在战略草案阶段细化到页面、接口和任务级实现方案。

## 4. 基本判断

`Icp Studio` Web 化不是单个项目，而是一条覆盖多个阶段的长期主线。它依赖新平台自身先具备稳定的：

- 模块宿主与扩展契约
- 统一认证与权限体系
- 配置中心与导入能力
- 审计与治理能力
- 前端 Shell 与模块装配能力

换句话说，Web 化 `Icp Studio` 的前提，不是先做一个网页版 Studio，而是先让新平台具备承接 Studio 能力的底座。

## 5. 能力分层

建议将 `Icp Studio` 现有和未来替代能力分为四层。

### 5.1 配置运营能力

包括：

- `Setting`
- `Dictionary`
- `Enumeration`
- 模块配置查询与修改
- 环境/租户覆盖
- 导入导出
- 配置审计与基础治理

这一层决定新平台是否能先替代 Studio 的日常“配置维护工具”角色。

### 5.2 元数据承载能力

包括：

- `Model`
- `Schema`
- 模块清单或应用注册信息
- 轻量元数据映射与导入能力

这一层决定旧配置资产、结构资产和平台元数据是否能进入新平台的统一模型。

### 5.3 设计器能力

包括：

- 页面设计
- 视图配置
- 表单与布局设计
- 元数据编辑器
- 规则或模板辅助设计

这一层是 `Icp Studio` 最复杂、最容易失控的部分，应当在底层模型稳定后再进入系统性替代。

### 5.4 治理与发布能力

包括：

- 配置变更治理
- 权限与审批扩展
- 审计追踪
- 发布、生效与回滚辅助

这一层不一定完整复刻旧流程，但需要逐步形成更适合 Web 平台的治理能力。

## 6. Web 化原则

### 6.1 先统一模型，再建设工具

如果底层配置模型、元数据模型和迁移链路不稳定，任何 Web 化界面都会很快返工。

### 6.2 先承接资产，再替代入口

先让旧资产能够进入新平台，再让用户在 Web 端维护这些资产。否则只会得到一个“能点但没有真实数据闭环”的空壳。

### 6.3 优先 Web 原生，不原样复制桌面交互

Web 化的目标不是把桌面 UI 照搬到浏览器，而是用新的模块、权限、审计、表单和工作流重新组织能力。

### 6.4 能淘汰的旧机制，不强行保留

像旧 `.generator`、部分强耦合页面配置和运行时动态机制，应优先判断是否应该退场，而不是默认保留。

### 6.5 分阶段替代，避免“大爆炸式重构”

不把配置中心、元数据迁移、设计器替代和治理能力升级压在同一轮中完成。

### 6.6 默认兼容旧规则，必要时受控升级

后续迁移默认应尽量保留旧平台配置项和工具能力的使用规则、命名习惯与理解方式，降低迁移和认知切换成本。

但如果旧规则已经明显不合理、过时、强耦合，或会阻碍新平台长期演进，则应采用更适合新平台的新规则。发生这类升级时，必须同步说明：

- 为什么不继续保留旧规则
- 新旧规则如何映射
- 对使用方式造成了哪些变化
- 是否需要过渡期或兼容说明

## 7. 推荐阶段路线

### 阶段 A：平台与迁移底座固化

目标：

- 稳定 `Host / Shell / Contracts / ConfigCenter / Authorization / Audit`
- 建立首批旧资产迁移路径
- 为后续 Web 化提供统一承载层

完成标志：

- 至少一类旧配置资产已成功导入新平台
- 配置中心、权限和审计能形成闭环

### 阶段 B：配置运营能力 Web 化

目标：

- 用 Web 页面替代 Studio 中的高频配置维护动作
- 统一配置查看、编辑、分组、权限与审计入口

范围示例：

- `Setting`
- `Dictionary`
- `Enumeration`
- 配置导入和基础批处理

完成标志：

- 日常配置维护可以不再依赖 `Icp Studio`

### 阶段 C：元数据管理能力 Web 化

目标：

- 建立结构化元数据的统一管理入口
- 让模型、结构、模块注册等能力逐步摆脱旧资产维护方式

范围示例：

- `Model / Schema`
- 模块清单
- 元数据导入与映射结果管理

完成标志：

- 平台元数据进入统一维护范式，而不是继续依赖桌面端或散落文件

### 阶段 D：设计器能力 Web 化

目标：

- 逐步替代 `Icp Studio` 中最重的页面、视图和设计器能力
- 按价值判断重做、简化或淘汰旧设计器

范围示例：

- 页面设计器
- 视图配置器
- 表单或布局设计
- 规则和模板辅助设计

完成标志：

- 关键设计器能力已有 Web 端替代方案

### 阶段 E：桌面端退出与能力收口

目标：

- 完成剩余差异能力处理
- 停止对 `Icp Studio` 的新增依赖
- 建立统一培训、治理和运维入口

完成标志：

- `Icp Studio` 不再是平台运行所依赖的必需工具

## 8. 与当前 NewP 路线的关系

在当前阶段，`NewP` 不应直接跳入整套 Studio Web 化。更合理的顺序是：

1. 先完成 `Phase 5` 的首个旧资产迁移 POC。
2. 再继续稳固 `ConfigCenter` 等公共能力。
3. 在迁移链路、配置承载、权限和审计都稳定后，再正式启动 Web 化专项。

这意味着：

- 当前工作重点仍是“让新平台能承接旧资产”。
- `Icp Studio` Web 化草案现在先作为方向文档存在。
- 只有当底座成熟后，才进入功能级和页面级设计。

## 9. 关键风险

- 过早把 Studio 设计器整体重做，会导致范围失控。
- 如果没有统一模型，后续每个 Web 管理页都会形成新的孤岛。
- 若直接复制旧元数据机制，会把旧平台技术债带入新平台。
- 如果没有明确的“保留 / 重做 / 简化 / 淘汰”判断，Web 化项目会长期拖延。

## 10. 关键决策口径

后续每类 `Icp Studio` 能力进入实施前，都应先回答以下问题：

- 该能力在新平台中的目标形态是什么？
- 是 `Import`、`Rewrite`、`Wrap` 还是 `Retire`？
- 是否必须保留原有操作方式？
- 是否可以降级为结构化配置编辑，而非完整设计器？
- 是否已经具备权限、审计、导入和验证闭环？

## 11. 当前建议

在正式启动 `Icp Studio` Web 化专项前，建议先完成以下前置铺路：

1. 完成 `Phase 5` 首个旧资产迁移 POC。
2. 继续加固 `ConfigCenter` 的持久化、导入、审计联动和运行验证。
3. 逐步形成旧资产分类与迁移清单。
4. 在未来进入专项前，再输出功能拆解清单和实施路线图。

## 12. 结论

`Icp Studio` 的最终方向应是由 Web 平台完整替代，但替代方式不应是“先做网页版 Studio”，而应是“先建设统一平台底座，再逐层承接配置、元数据、设计器和治理能力”。当前最合理的动作不是立即全面 Web 化，而是先把迁移与配置承载主线走通，为未来替代打牢基础。
