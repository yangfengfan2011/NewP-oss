# Batch Grill With Docs

在采取行动前，以依赖感知的批量访谈压力测试计划或设计。全程同时加载并遵循 `$domain-modeling`。

## 准备

- 读取项目规则、用户提供的计划、现有 `CONTEXT.md` 或 `CONTEXT-MAP.md`，以及相关 `docs/adr/`。
- 把待澄清内容组织成决策树：节点是决策，边表示“必须先回答”的依赖。
- 区分事实与决策。可从代码、文档或工具中查明的事实自行调查；只把需要用户拍板的决策交给用户。
- 多项事实调查互不依赖且环境支持时，并行调查。某项调查尚未完成时，只延后依赖它的问题，不阻塞其他分支。

## 按前沿分轮盘问

1. 计算当前决策前沿：所有前置依赖已经解决、现在可以独立回答的未决问题。
2. 在同一条消息中询问整个前沿。按决策分支分组并使用稳定编号；每题都给出：
   - 需要决定什么。
   - 推荐答案。
   - 推荐理由与主要取舍。
3. 不要把答案依赖本轮其他未决问题的问题提前塞进同一轮；把它留到后续前沿。
4. 不要为了维持表面上的对话节奏，把同一前沿拆成一次一个问题。只有当前前沿确实只有一个问题，或用户明确要求逐题询问时，才一次只问一个。
5. 等待用户批量回答。允许用户用编号简答、接受推荐答案，或只修正不同意的部分。
6. 根据回答更新决策树，显式指出冲突、遗漏或被新答案推翻的前提，然后重新计算下一轮前沿。

## 同步领域文档

- 每轮答案形成共识后，立即按 `$domain-modeling` 更新文档，不等到访谈结束再批处理。
- 把已确认的规范术语写入相应 `CONTEXT.md`；它只保存领域词汇和定义，不写实现细节、规格或待办事项。
- 只有决策同时满足“难以逆转”“缺少背景会令人意外”“确实经过权衡”时，才提出或写入 ADR。
- 用户描述与现有词汇、ADR 或代码事实冲突时，先指出冲突并纳入下一轮决策，不要静默覆盖。

## 收口

- 当前沿为空时，总结已解决决策、仍有意保留的开放问题、词汇更新和 ADR 变更。
- 请求用户确认双方已经达成共同理解。
- 在用户确认前，不进入实现，也不擅自生成规格、票据或实施计划。
