# 表单操作区位置对比设计

## 1. 背景

当前平台已经明确：

- `model metadata` 负责字段在 `create/edit/view` 中的静态语义
- `view metadata` 负责页面级结构与标准维护动作承载方式
- `detail view` 用于承接复杂对象的单对象维护页

但在“标准维护表单究竟以什么容器承载、操作按钮又放在哪里”这个问题上，当前主线设计还没有明确收口：

- 它可能承载在 `page`
- 也可能承载在 `drawer`
- 同时按钮可能放在标题区域
- 也可能放在表单底部操作区

这两种做法都会影响：

- 标准维护动作的承载方式认知
- 表单阅读顺序
- 操作按钮的发现成本
- 长表单时的视线和滚动体验
- 后续 `create / edit / view` 标准承载模式如何统一

因此需要先做一个静态对比稿，把“承载方式”和“按钮位置”两个维度一起展开，再决定是否把结论并回平台级 `view metadata` 主线设计。

## 2. 目标

- 输出一个单文件静态网页，对比以下四种组合：
  - `page + 标题区按钮`
  - `page + 底部操作区`
  - `drawer + 标题区按钮`
  - `drawer + 底部操作区`
- 让四种方案使用同一份对象内容，避免因为字段不同而影响判断。
- 明确两种方案各自的适用场景和风险。
- 为后续是否把“表单操作区”写入平台设计提供可讨论的视觉依据。

## 3. 非目标

- 不在本设计中直接修改 `metadata-driven-backoffice-ui-design.md` 主文档。
- 不在本设计中实现真实前端路由或 API 联动。
- 不在本设计中定义最终的 `view metadata` 字段结构。
- 不在本设计中讨论权限、规则中心、对象授权或路由元数据。

## 4. 范围

本次仅交付：

- 一份补充设计文档
- 一个可本地打开的静态 HTML 对比页

静态页内容范围：

- 同一对象的表单页
- 相同的 section 和字段
- 两种按钮布局
- 简短差异说明

本次不交付：

- 产品级正式页面
- Shell 接入
- 真实 `view metadata` 消费实现

## 5. 设计约束

- 静态页必须独立可打开，不依赖前端工程构建。
- 两种方案必须使用同一份字段内容与页面结构，只改变按钮位置。
- 页面需同时兼顾桌面和窄屏展示，避免只在大屏下成立。
- 输出应保持“可讨论的设计稿”属性，而不是伪装成最终产品页面。

## 6. 对比方案

### 6.1 方案 A：标题区按钮

结构：

- 页面标题与对象状态放在顶部
- 主操作按钮放在标题区右侧
- 表单内容在下方 section 中展开

优点：

- 首屏即可看到主要操作
- 适合字段较少、阅读路径较短的对象
- 页面头部更像“工作台”而不是“长表单”

风险：

- 当表单较长时，按钮与用户当前编辑区域距离较远
- 用户在修改到页面底部后，需要回到上方才能保存
- 在 `create / edit` 场景下，标题区按钮容易与对象级次要动作混在一起

### 6.2 方案 B：底部操作区

结构：

- 页面标题区只放对象标题、说明和状态
- 表单 section 在中间展开
- 主操作按钮统一放在底部操作区

优点：

- 更符合“读完表单再提交”的线性心智模型
- 长表单时更自然
- 更容易把“保存 / 取消”与“删除 / 停用 / 跳转”等次要动作分层

风险：

- 首屏不一定立即看到提交按钮
- 如果页面结构过长，底部操作区会依赖滚动到末尾
- 对于非常轻量的对象编辑来说，可能略显正式

## 7. 推荐结论

当前更推荐把：

- `save / cancel` 这类标准表单动作放在底部操作区
- 标题区保留给对象标题、状态、说明和少量导航信息

原因：

- 组织模块人员中心这类对象天然不是轻量编辑对象
- 后续如果 detail view 包含多个 section 和只读摘要块，底部操作区更稳定
- 它更容易与“对象级次要动作”分层，避免所有动作挤在顶部

但本次先不把该结论强行并回主设计，而是先通过静态页帮助团队形成共同直觉。

## 8. 交付物

本次静态演示文件建议放在：

- `docs/designs/platform/artifacts/form-action-area-comparison.html`

该页面应包含：

- 四种组合卡片
- 同一组字段与摘要块
- 对 `page / drawer / dialog` 的解释说明
- 简短差异说明

## 9. 验证方案

- 静态页可直接本地打开
- 四种组合能在同一页面对比
- 桌面和窄屏下都能保持可读
- 能让“承载方式”和“按钮位置”两个维度分别被看清

## 10. 风险与回滚

- 若静态页表达不清，会误导后续平台设计判断
- 若页面同时改变内容结构和按钮位置，会降低对比有效性

回滚方式：

- 该静态页只是讨论稿，不接入运行时
- 若方向不合适，直接删除该补充文档与 HTML 文件即可
- 不影响当前三份主设计文档

## 11. AI-First 最小检查清单

### 入口在哪里

- 设计文档入口：`docs/designs/platform/form-action-area-comparison-design.md`
- 静态页入口：`docs/designs/platform/artifacts/form-action-area-comparison.html`

### 边界在哪里

- 本设计只讨论“表单操作按钮位置”
- 不修改主平台元数据结构，不实现真实页面逻辑

### 如何验证

- 通过本地打开 HTML 对比两种布局
- 通过同内容、不同按钮位置观察阅读和操作感知差异

### 失败信号是什么

- 页面同时改变了字段结构、信息量和按钮位置，导致无法公平对比
- 讨论稿反而被误用成正式实现标准

### 如何回滚

- 删除补充设计文档与静态 HTML
- 保留现有平台主设计文档，不影响既有结论
