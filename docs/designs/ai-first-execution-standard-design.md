# AI-First 执行标准设计

## 1. 背景

当前仓库已把"更适合 AI 辅助开发并逐步过渡到 AI 主导开发"写入 `AGENTS.md` 作为首要目标。围绕这个方向，仓库内已形成多份相关文档：

- `AGENTS.md` 提出 AI-First 约束、架构规则、变更规则和验证要求。
- `docs/architecture/ai-first-platform-criteria.md` 给出 7 项判定准则和快速否决信号。
- `docs/architecture/componentization-guardrails.md` 规定 Host / Shell / 模块的组件化护栏和受控接入点。
- `docs/designs/detailed-design-template.md` 提供设计文档的结构模板。

这些文档从不同角度提出了 AI-first 相关约束，但尚未形成一份统一的执行标准。执行者在开始一项任务时，需要自行从多份文档中推导出判断口径，这本身就不够"AI-first"。

本设计的目的是将上述分散约束收敛成一份统一的执行标准，供后续所有新增任务、新增模块和新增设计作为日常执行与验收依据。

## 2. 目标

- 将仓库已有的 AI-first 约束统一收敛成一份可直接引用的执行标准。
- 明确新增任务、设计、模块和改动在 AI-first 维度的最低要求。
- 为设计文档补齐统一的最小检查清单。
- 为后续工作包和阶段验收提供 AI-first 判断口径。

## 3. 非目标

- 不重写或替代 `AGENTS.md`、`ai-first-platform-criteria.md` 或 `componentization-guardrails.md`，本文只做统一收口和补齐。
- 不在本设计中定义具体模块的业务逻辑、接口或数据模型。
- 不引入新的组织架构或工具链要求。
- 不要求对 Phase 1 到 Phase 6 的既有成果做推倒重来式返工。

## 4. 适用范围

本标准适用于当前仓库中所有新增的：

- 任务拆分与工作包定义
- 详细设计文档
- 后端模块与前端模块实现
- 迁移链路与导入规则
- 文档与验证记录

既有模块和文档不要求一次性全量补齐，但后续修改时应逐步对齐。

## 5. 核心判断标准

以下 8 项准则来自 `docs/architecture/ai-first-platform-criteria.md`，本标准将其作为统一执行口径：

### 5.1 边界清晰

模块职责、入口、依赖和禁止修改区必须明确。执行者不需要跨越大量文件才能理解一项改动的范围。

### 5.2 任务可切小

单个需求应能拆成多个可在短时间内完成的小任务，每个任务可独立提交、独立验证、独立回滚。

### 5.3 局部可验证

每项改动应有局部的测试、脚本、接口或 smoke 路径。验证不应依赖整仓人工联调。

### 5.4 契约先于实现

模块接入、数据映射、迁移规则、API 输入输出先文档化，再实现。减少执行者在隐式规则上猜测。

### 5.5 低上下文负担

避免超大文件、跨层隐式耦合和多处同步手改。优先使用稳定目录结构、单一职责文件和可搜索入口。

### 5.6 文档可执行

文档不仅说明"做了什么"，还应说明"从哪里入手、允许改哪里、如何验证、失败怎么看、回滚怎么做"。

### 5.7 并行安全

不同执行者可以围绕不同模块或文件集合并行推进，冲突范围可控，不依赖共享的隐式现场状态。

### 5.8 可复制迁移

当前任务产物应能成为后续同类任务的模板，而不是只能完成一次性的手工特例。迁移类任务尤其要求：固定样本、映射规则、执行路径和验证记录都能被后续执行者直接复用。

## 6. 快速否决信号

如果一项任务或设计出现以下任意两项，应优先判断为偏离 AI-first，在继续实施前须先调整：

- 改一个点必须理解半个仓库。
- 一个任务同时混入重构、新功能和迁移。
- 主要验证方式依赖人工点击和口头说明。
- 关键规则只存在于人的记忆里，没有文档或固定入口。
- 同类工作无法复制，只能再次人工摸索。
- 一个执行者的改动很容易波及多个无关模块。

## 7. 任务拆分标准

### 7.1 单一聚焦

新任务默认只聚焦一个模块或一种能力。不在同一次改动里把重构、重命名和新功能混在一起。

### 7.2 可独立验证

每个任务在完成后，应能通过至少一种方式验证结果（构建、测试、smoke、接口调用），而不需要等待其他任务先完成。

### 7.3 可独立回滚

每个任务的改动应能被独立回退而不破坏主干功能。如果回滚代价高，应在任务定义时提前说明。

## 8. 文档标准

### 8.1 设计文档最小检查清单

每份新设计文档至少回答：

1. 入口在哪里
2. 边界在哪里
3. 如何验证
4. 失败信号是什么
5. 如何回滚

如果上述五项中有任何一项无法回答，应在文档中显式说明原因，而不是留空。

### 8.2 设计先行规则

没有详细设计文档时，不进入正式实现。

没有设计文档时，只允许做：

- 信息收集
- 问题排查
- 方案讨论
- 设计草稿

详细设计文档默认放在 `docs/designs/`，模板见 `docs/designs/detailed-design-template.md`。

### 8.3 禁止口口相传

如果某项实现只能依赖人工口口相传才能继续推进，则视为不符合 AI-first。关键规则、入口、边界和验证方式必须有文档化记录。

### 8.4 文档可移植

文档不应依赖单机路径、单机用户名或特定 IDE 会话状态。文档推送到 GitHub 后，应能在另一台机器上直接使用。

## 9. 模块与文件边界标准

### 9.1 模块接入规则

正常模块接入优先通过 `Contracts / SDK / templates / controlled entry points`，不通过直接修改 Host 或 Shell 内部结构来接入。

前端模块正常接入时，唯一允许修改的 Shell 级入口是 `frontend/packages/shell/src/builtin-runtime-plugins.ts`。如果一个新增模块需要修改 Shell 的其他内部文件，应先补设计说明为什么现有契约或受控清单不够用。

### 9.2 Host / Shell 边界

与 `docs/architecture/componentization-guardrails.md` 保持一致：

- Host 只负责启动、组合、模块加载、全局中间件、统一认证与宿主级接入。
- Shell 只负责布局、全局 Provider、菜单聚合、路由聚合和模块受控注册。
- 不把模块私有业务流程放进 Host / Shell。
- 不为单个模块在宿主中新增私有接入特例。

### 9.3 文件结构要求

- 避免超大单文件。如果单个文件需要读取大量代码才能理解一项改动的上下文，应考虑按职责拆分。
- 模块之间不直接访问对方数据库或持久化细节。
- 公共能力进入 `Kernel / SDK / Contracts`，模块私有能力留在模块内部。

## 10. 验证标准

### 10.1 改动级别验证

每次改动结束后，应尽量执行以下检查（根据改动范围选择适用项）：

- 后端构建：`dotnet build ICP-Platform.sln`
- 后端测试：`dotnet test`
- 前端构建：`cd frontend && pnpm build`
- 前端测试：对应模块或 Shell 的 `pnpm test`
- 契约检查或 smoke 验证（如改动涉及模块注册、登录、权限或配置）

### 10.2 设计级别验证

每份设计文档应在"验证方案"部分明确说明该设计落地后如何验证，至少包括：

- 哪些 build / test / smoke 能证明设计已按预期落地
- 哪些失败信号说明实现偏离了设计

### 10.3 迁移级别验证

迁移类任务至少包含以下验证交付：

- 固定样本
- 映射规则
- 固定执行路径（API 或脚本）
- 可复跑的验证记录

## 11. 失败信号与回滚标准

### 11.1 通用失败信号

以下情况应视为当前改动或设计存在问题，需要暂停并调整：

- 构建失败且无法通过当前改动自行修复。
- 既有测试因当前改动而失败，且非有意调整。
- 改动后，一个模块的变化导致其他无关模块出现异常。
- 改动的实际行为与设计文档中描述的预期行为不一致。

### 11.2 AI-first 偏离信号

以下情况应视为偏离 AI-first 方向，需要在继续前调整方案：

- 完成当前任务需要同时理解三个以上模块的内部实现细节。
- 当前任务的验证无法通过脚本或命令完成，只能依赖人工全流程操作。
- 后续执行同类任务时，无法参考当前产出作为模板，必须重新摸索。

### 11.3 回滚思路

- 代码改动：通过版本控制回退到改动前状态，确认 build 和 test 恢复正常。
- 文档改动：恢复到前一版本，更新周边文档中的引用一致性。
- 迁移改动：通过导入 API 的幂等性或数据清理脚本回退，需在迁移设计中预先说明。
- 配置或清单改动：恢复 `plugin.json`、`builtin-runtime-plugins.ts` 或其他受控入口的前一版本。

## 12. 与现有文档的关系

本标准不替代以下文档，而是作为统一的 AI-first 执行收口层：

| 文档 | 职责 | 本标准的关系 |
|------|------|--------------|
| `AGENTS.md` | 项目总规则，包含架构规则、变更规则、验证要求和 AI-First 约束 | 本标准归纳并细化其中的 AI-First 约束部分 |
| `docs/architecture/ai-first-platform-criteria.md` | AI-first 判定准则与否决信号 | 本标准直接引用并扩展为统一执行基线中的 8 项准则与否决信号 |
| `docs/architecture/componentization-guardrails.md` | 组件化护栏，Host / Shell / 模块的接入边界 | 本标准在模块边界部分与其保持一致 |
| `docs/designs/detailed-design-template.md` | 设计文档结构模板 | 本标准补充最小检查清单，作为模板的必答补充 |
| `docs/history/collaboration/github-copilot-working-mode.md` | 历史 Copilot 协作模式与文件边界 | 本标准定义执行层面的判断口径，历史协作文档保留旧角色与流程作为参考 |

各文档的规则在各自范围内继续有效。在 AI-first 执行维度上，如果出现口径不一致，以本标准为准，并同步推动对应源文档的修订来消除分歧，不在执行过程中临场裁决。

## 13. 落地步骤

本标准推荐按以下步骤逐步落地：

### 第一步：新增任务立即适用

从本文档正式入库起，所有新增的工作包、设计文档和模块实现任务，默认遵守本标准中的规则。

具体表现为：

- 新增设计文档必须回答第 8.1 节的 5 项最小检查清单。
- 新增任务默认只聚焦一个模块或一种能力（第 7.1 节）。
- 新增改动结束后执行适用的验证检查（第 10.1 节）。

### 第二步：存量模块逐步对齐

在后续修改既有模块时，顺带检查以下方面并逐步补齐：

- 模块是否有清晰的入口与边界说明。
- 模块的验证路径是否可脚本化或可命令行完成。
- 模块的设计文档是否已回答 5 项最小检查清单。

不要求一次性全量补齐，但每次修改时应留下比修改前更好的状态。

### 第三步：阶段验收引用

后续新阶段的验收标准中，应显式引用本标准作为 AI-first 维度的评判依据。

具体表现为：

- 阶段总结中说明本阶段产出是否可被后续同类任务复用。
- 阶段验收时检查是否出现第 6 节的否决信号。
