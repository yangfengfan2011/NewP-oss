# 插件与小组件分层设计

## 1. 背景

当前平台已经逐步形成两条主线：

- 平台层具备插件发现、装载、启停与版本治理方向
- 业务层希望继续推进组件化，但实际业务能力存在明显的域内聚合特征

在继续讨论“模块数量”后，已经明确两个事实：

1. 平台级插件不需要细到“每个业务对象一个插件”。
2. 业务域内部仍然需要继续拆分成更小的能力单元，避免单个插件内部失控。

例如，“人员”“部门”“角色”这三个能力虽然可以分别建模、分别授权、分别配置菜单和路由，但它们通常共享同一业务域、同一发布节奏、同一启停节奏和高度关联的数据模型。把它们直接做成三个平台级插件，会过早放大依赖治理、版本协调和运行时治理成本。

因此，本设计的核心目标不是继续讨论“要不要组件化”，而是明确：

- 什么层级才是平台真正需要治理的插件
- 什么层级应当作为插件内部的小组件存在
- 后续命名、目录、路由、权限与代码组织应如何统一

## 2. 目标

- 明确平台、插件、小组件、页面/服务之间的固定分层关系
- 明确插件是唯一平台级生命周期治理单元
- 明确小组件是插件内部能力单元，而不是平台级插件
- 为后续控制在 `50` 个以内的平台级插件提供统一拆分规则
- 允许插件内部继续容纳 `100+` 级别的小组件/业务单元，而不把平台治理复杂度同步放大
- 为现有统一插件包设计补充更清晰的语义边界

## 3. 非目标

- 不在本轮把所有现有模块立即重构为新的目录形态
- 不在本轮引入新的插件运行时协议
- 不在本轮实现小组件级单独发布、单独启停或单独升级
- 不在本轮设计新的权限模型或菜单模型，只规定它们的归属层级
- 不在本轮处理跨租户隔离、远程市场、细粒度热插拔等后续主题

## 4. 术语定义

### 4.1 平台

平台负责宿主、运行时、插件发现、插件装载、统一入口能力和生命周期治理。

平台不直接承载具体业务对象实现。

### 4.2 插件

插件是平台唯一感知的业务交付单元，也是唯一平台级治理单元。

插件必须满足：

- 可独立安装
- 可独立启停
- 可独立升级与回滚
- 有稳定的插件 ID 与版本
- 对平台暴露统一的后端与前端接入契约

本设计中的“插件”本质上对应业务上的“大组件”。

### 4.3 小组件

小组件是插件内部的业务能力单元，用于组织高相关度的子域能力。

小组件可以拥有自己的：

- 菜单
- 路由
- 权限点
- 服务
- 查询/命令
- 导入器或业务适配器

但小组件不是平台级插件，不单独安装、不单独启停、不单独升级。

### 4.4 页面 / 服务 / 查询 / 权限点

这些都是比小组件更细的实现层元素，必须归属于某个明确的小组件，不应直接漂浮在插件根目录。

## 5. 方案比较

### 方案 A：插件 = 细粒度功能单元

例如把“人员”“部门”“角色”都定义为平台级插件。

优点：

- 理论上最灵活
- 每个业务对象都可独立发布

问题：

- 平台级插件数量会快速膨胀
- 依赖治理、版本协调和联调成本显著上升
- 高关联业务对象会被迫走跨插件协作路径
- 与当前“通常整体发布”的业务现实不匹配

### 方案 B：插件 = 大组件，小组件 = 插件内部能力单元

例如把“身份治理”定义为一个插件，内部包含“人员”“部门”“角色”三个小组件。

优点：

- 与当前整体发布、整体启停、整体升级的交付习惯一致
- 平台治理数量可控
- 同域能力高内聚，跨插件依赖显著减少
- 仍保留插件内部继续细分的组织能力

问题：

- 插件内部必须建立清晰的小组件边界，否则插件内部会再次长成“大泥球”

### 方案 C：插件 = 中组件，再引入上层业务组

例如“组织结构组”下再管理“人员插件”“部门插件”“角色插件”。

优点：

- 未来拆分与复用空间较大

问题：

- 平台治理概念增加一层
- 交付、依赖、启停和升级模型更复杂
- 当前阶段收益明显小于复杂度

本轮采用 `方案 B`。

## 6. 推荐分层模型

固定分层如下：

```text
平台
  └─ 插件（大组件，平台级交付与治理单元）
       └─ 小组件（插件内部能力单元）
            └─ 页面 / 服务 / 查询 / 权限点 / 导入器
```

这个模型下：

- 平台层只管理插件，不直接管理小组件
- 插件层负责聚合本业务域的小组件
- 小组件层负责承接业务对象、业务流程和能力边界
- 实现层元素必须明确归属某个小组件

## 7. 设计原则

### 7.1 插件按业务域和生命周期切分

插件拆分的第一判断标准不是“功能点数量”，而是：

- 是否通常一起发布
- 是否通常一起启停
- 是否共享主要数据模型
- 是否共享主要业务流程
- 是否由同一团队长期维护

如果上述答案大多为“是”，则应优先放入同一个插件。

### 7.2 小组件按业务对象或业务能力切分

小组件适合承载：

- 人员
- 部门
- 角色
- 权限模板
- 审批规则

这类能力在业务上可独立理解，但又不值得上升为平台级插件。

### 7.3 平台只治理插件，不治理插件内部细节

平台侧应关注：

- 插件发现
- 插件元数据
- 插件版本
- 插件依赖
- 插件启停
- 插件升级与回滚

平台侧不应直接感知：

- 某个小组件的内部服务实现
- 某个页面的状态管理
- 某个小组件的私有数据访问细节

### 7.4 插件内部仍必须有显式边界

采用“大组件插件”不等于允许插件内部自由堆砌。

插件内部仍需遵守：

- 小组件边界明确
- 公共能力有归属
- 跨小组件访问尽量通过插件内显式接口
- 不把所有页面、服务、查询、权限声明全部平铺在插件根目录

## 8. 拆分判断规则

### 8.1 应放入同一插件的信号

- 一起发布
- 一起启停
- 一起升级
- 数据模型强关联
- 业务流程强联动
- 同一团队长期维护

### 8.2 应拆成独立插件的信号

- 明显需要独立发布
- 明显需要独立启停
- 可能由不同团队维护
- 被多个业务域反复复用
- 生命周期与版本节奏经常不同步
- 存在独立的宿主兼容性或授权边界

### 8.3 默认策略

当无法快速判断时，默认优先合并为同一插件下的不同小组件，而不是立即拆成多个平台级插件。

只有当独立生命周期需求已经被反复验证时，再升级为独立插件。

## 9. 命名规范

### 9.1 插件命名

插件名应使用业务域名，不使用页面名、技术名或过细的业务对象名。

推荐示例：

- `Identity`
- `Organization`
- `Audit`
- `ConfigCenter`
- `Files`

插件 ID 建议：

- 全局唯一
- 稳定
- 短
- 小写连字符或小写单词

例如：

- `identity`
- `organization`
- `audit`

### 9.2 小组件命名

小组件名应使用业务对象名或能力名。

推荐示例：

- `Users`
- `Departments`
- `Roles`
- `PermissionTemplates`

小组件 ID 可用于插件内部注册、菜单分组或前端局部命名，但不应与平台级插件 ID 混用。

### 9.3 路由命名

推荐以插件为第一层路径，小组件为第二层路径：

- `/identity/users`
- `/identity/departments`
- `/identity/roles`

### 9.4 权限点命名

推荐格式：

`<pluginId>.<subcomponent>.<action>`

例如：

- `identity.users.read`
- `identity.users.manage`
- `identity.roles.assign`

### 9.5 服务命名

服务名应体现小组件归属，不要只使用泛化名称。

推荐示例：

- `UserService`
- `DepartmentService`
- `RolePermissionService`

## 10. 目录建议

推荐目录应天然反映“插件 > 小组件 > 实现元素”的关系。

示例：

```text
plugins/
  Identity/
    plugin.json
    backend/
      IdentityPlugin.cs
      Shared/
      Components/
        Users/
          Controllers/
          Services/
          Queries/
          Permissions/
        Departments/
          Controllers/
          Services/
          Queries/
          Permissions/
        Roles/
          Controllers/
          Services/
          Queries/
          Permissions/
    frontend/
      src/
        index.ts
        shared/
        components/
          users/
            pages/
            services/
            permissions/
          departments/
            pages/
            services/
            permissions/
          roles/
            pages/
            services/
            permissions/
```

目录规则：

- 插件根目录只放插件声明、聚合注册和插件级共享能力
- 小组件目录放本小组件自己的页面、服务、查询与权限声明
- 只有被多个小组件复用的代码才提升到插件级 `Shared/shared`
- 不要因为“以后可能复用”而过早抽公共层

## 11. 平台治理边界

平台级治理对象应固定为插件。

平台负责：

- 插件目录发现
- 插件元数据读取
- 插件装载
- 插件启停
- 插件升级与回滚
- 插件版本兼容与依赖治理

平台不负责：

- 小组件单独启停
- 小组件单独发布
- 小组件单独升级
- 小组件内部代码结构治理

这意味着现有统一插件包、插件运行时加载、插件治理文档中的“模块/插件”语义，应优先理解为“大组件插件”，而不是任意细粒度业务对象。

## 12. 对现有设计的解释与收口

### 12.1 对统一插件包设计的解释

当前“一个统一插件包只承载一个业务模块”的规则，应收敛解释为：

- 一个统一插件包只承载一个平台级插件
- 该插件内部可以包含多个小组件
- 平台对其执行一次安装、启停、升级与回滚

这里的“业务模块”不应再理解为“人员”“部门”“角色”这类细粒度对象。

### 12.2 对组件化护栏的补充

组件化护栏仍然成立，但应增加一层语义：

- 护栏既适用于“插件接入平台”
- 也适用于“插件内部继续拆成小组件”

也就是说，平台层防止插件侵入宿主，插件层也要防止小组件互相无边界侵入。

### 12.3 对数量预期的修正

后续应把数量控制目标改成：

- 平台级插件控制在 `50` 个以内
- 插件内部允许存在大量小组件
- 总业务能力单元可以超过 `100`

这样既保留了业务拆分能力，又避免把平台治理复杂度同步放大到 `100+` 级别插件。

## 13. 示例：身份治理插件

推荐建模：

```text
插件：Identity
  小组件：Users
  小组件：Departments
  小组件：Roles
```

该模型下：

- 平台只安装和治理 `Identity`
- 前端可分别暴露“人员管理”“部门管理”“角色管理”菜单与路由
- 后端可分别组织 `Users`、`Departments`、`Roles` 的服务与控制器
- 三者共享同一插件版本与生命周期

## 14. 设计收益

- 平台级治理对象数量可控
- 业务域内部高内聚
- 跨插件依赖减少
- 插件版本协调压力下降
- 结构上兼容后续继续增长的小组件数量
- 与当前整体发布、整体启停、整体升级的实际习惯一致

## 15. 风险与控制

### 风险 1：插件内部重新长成大泥球

控制：

- 强制目录分层到小组件
- 小组件级命名、路由、权限、服务归属明确
- 插件根目录只保留聚合与共享能力

### 风险 2：把“小组件”偷偷重新升格成平台级插件

控制：

- 拆分前必须先验证独立生命周期需求
- 没有独立发布/启停/升级需求时默认不拆

### 风险 3：共享层膨胀

控制：

- 只有跨多个小组件稳定复用的能力才进入插件共享层
- 只有跨多个插件稳定复用的能力才进入平台共享层

## 16. 验收标准

本设计落地后，应能满足：

- 团队在讨论新业务能力时，能先判断“这是新插件还是插件内新小组件”
- 插件命名、小组件命名、路由与权限命名有统一规则
- 平台治理文档中的插件语义不再混淆
- 目录结构能直接体现分层关系
- “平台插件 <= 50，业务能力单元 > 100” 的规模目标仍然可控

## 17. 后续建议

建议后续按以下顺序继续推进：

1. 在架构文档中补充本设计的正式版本
2. 调整模板或脚手架，使新增插件默认带有 `Components/` 或 `components/` 结构
3. 在统一插件包和插件治理文档中补充“插件 = 大组件”的术语说明
4. 在示例插件中落一个真实目录模板，作为团队默认参考
