这个线程对应一个独立 worktree，只做一个大任务。目标不是“把所有事情都塞进一个分支”，而是把一个边界清楚、可验证、可回滚的大任务独立推进到底。

## 一、什么时候适合新建 worktree

适合新建 worktree 的场景：
- 当前任务会持续多轮
- 当前任务会改多个目录
- 当前任务与其他任务在文件层面可以分开
- 你希望把“平台主干 / 前端 Shell / 最小登录 / Demo Module / Authorization”分开推进

不适合新建 worktree 的场景：
- 只是改一两个文件的小修
- 还没搞清楚任务边界
- 任务会频繁和其他线程改同一批文件

## 二、worktree 级任务的基本规则

每个 worktree 必须遵守：
- 一个 worktree 只负责一个大任务
- 一个大任务只对应一个明确目标
- 不要和其他 worktree 修改同一批核心文件
- 如果发现范围扩张，先收敛，再继续
- 真正改代码的线程尽量只有当前 worktree 主线程

## 三、开始之前必须做的事

- 预计会验证哪些命令
- 是否需要 subagents 协助

## 五、推荐执行流程

### 阶段 1：摸底

- 阅读相关文档
- 读相关目录和关键文件
- 确认是否在 `scope-v1` 范围内
- 判断是否需要子代理

### 阶段 2：收敛方案

- 用 5 到 10 条要点写清方案
- 说明为什么这样做
- 标记风险点
- 标记本轮先不做的内容

### 阶段 3：实施改动

- 主线程实施核心改动
- 子代理只做探索、审查或最后阶段验证
- 不混入无关重构

### 阶段 4：验证

根据任务至少执行相关验证：
- 后端 build
- 后端 test
- 前端 build
- 前端 test
- smoke 验证

### 阶段 5：输出

必须输出：
- 改动摘要
- 影响范围
- 验证结果
- 风险点
- 回滚方式
- 下一步建议

## 六、和其他 worktree 的协作边界

你必须主动避免以下冲突：
- 同时修改 `Host` 启动入口
- 同时修改登录页与前端全局路由
- 同时修改同一个模块契约文件
- 同时修改共享 SDK 入口

如果当前任务必须触碰这些共享文件：
- 缩小本轮修改面
- 明确改动边界
- 优先只做当前任务最小必需修改

## 七、推荐的验证清单

### 对后端主干 / Host 任务

至少验证：
- `dotnet build`
- Host 能启动
- 健康检查接口可访问

### 对前端 Shell 任务

至少验证：
- 前端依赖安装成功
- 前端 build 成功
- 登录页可访问
- 登录后主界面可进入

### 对最小登录能力任务

至少验证：
- 默认管理员登录成功
- 当前用户接口可返回
- 退出登录后受保护页面不可直接访问

### 对 Demo Module 任务

至少验证：
- 登录后能看到菜单
- 菜单能进入页面
- 页面受权限守卫保护

### 对 ConfigCenter / Audit / Authorization 任务

至少验证：
- 后端 build
- 相关测试
- 前端 build
- 对应功能可通过最小路径访问

## 十、贴近本项目的示例

### 示例 1：shell-login worktree

worktree 名称：
- `shell-login`

任务标题：
- 最小登录能力与前端平台壳联调

任务目标：
- 登录页可访问
- 默认管理员可登录
- 登录后进入主界面
- 当前用户状态可获取

本轮明确不做：
- 完整用户中心
- 外部统一认证
- 组织树

预计影响目录：
- `apps/host-api`
- `frontend/packages/shell`
- `frontend/packages/core`
- `server/modules/IdentityLite`

### 示例 2：config-import-poc worktree

worktree 名称：
- `config-import-poc`

任务标题：
- Setting / Dictionary 首个导入 POC

任务目标：
- 选择一类旧配置资产
- 建立目标数据模型
- 打通最小导入流程
- 可通过接口读取导入结果

本轮明确不做：
- 全量元数据兼容
- `.generator/.page/.view` 全量处理
- 工作流和报表配置迁移

预计影响目录：
- `server/modules/ConfigCenter`
- `server/kernel`
- `tests`
- `docs`
