# 连续执行并提交单文件票据板

把一个 `tickets.md` 作为唯一执行状态源，在同一任务中持续推进所有可执行票据。内部保持逐票实现、验证、审查和提交边界，但不要求用户逐票重新调用、不强制每票新开上下文。

## 开始前

1. 获取明确的票据板路径；只有候选唯一时才自行定位。
2. 读取仓库 `AGENTS.md`、`Docs/agents/issue-tracker.md`、票据板引用的规格，以及当前票据涉及的代码注释或验证规则。
3. 检查 `git status`，记录开始执行时的 `HEAD` 作为整板审查基线，并识别、保护用户已有的未提交内容。不要回退、覆盖或顺带提交无关变更。
4. 验证票据编号、状态和依赖关系。若只有规格而没有票据板，且工作属于多步骤行为变更，先使用 `$to-ticket-board`，不要跳过本仓库的默认拆分入口。
5. 用户明确要求执行某个 `draft` 票据板时，将这次指令视为对该票据板的确认；否则等待票据板进入 `ready`。
6. 把用户调用本技能或明确要求执行、继续整张票据板视为对实施和当前分支本地提交的授权。默认每张票据形成一个提交；只有改动不可安全拆分时才按独立回滚的逻辑组提交并记录原因。用户明确要求“不提交”时才跳过提交。
7. 恢复旧版或中断中的票据板时，先核对已标记 `completed` 的票据是否缺少提交前审查或提交哈希。默认提交策略下仍有任务改动留在工作区时，先审查并补交这些改动，再选择新前沿；无法安全还原逐票边界时，按最小可回滚逻辑组提交，把共同哈希和合并原因写回相关票据。

## 选择执行前沿

- 优先恢复 `in-progress` 票据，先核对现有改动和执行记录，避免重复实现。
- 否则选择编号最小、状态为 `pending`、且所有依赖均为 `completed` 或 `skipped` 的票据。
- 不执行 `blocked`、`completed` 或依赖未完成的票据。
- 一张票据阻塞后，可继续执行与它无依赖关系的其他前沿票据；若阻塞使整体规格或共享基础不再可信，则停止并报告。

## 连续执行循环

对每张前沿票据依次执行：

1. 在编辑业务文件前，把票据状态改为 `in-progress`，把票据板状态改为 `in-progress`，并立即保存。
2. 只实现该票据的目标和必要支撑，不混入后续票据或无关重构。尽可能在规格或票据已经确认的 public seam 上使用 `$tdd`；把规格或票据明确写出的 seam 视为已预先确认。若 seam 缺失且选择会改变架构边界，先记录缺口并暂停，不自行发明。
3. 在实现过程中定期执行最小相关测试、类型检查或构建；完成票据前执行票据列出的全部必需自动化和手工验证。文档或无法使用 TDD 的票据记录“不适用”及原因，不伪造 red-green 证据。
4. 验证通过后，记录影响文件、实际命令、结果、已知限制和未执行项原因，但先保持 `in-progress`；随后完成“提交前审查与逐票提交”。
5. 只有提交前审查通过，并且本票据提交成功或用户已明确要求不提交时，才勾选实际满足的验收条件并把状态改为 `completed`。
6. 验证、审查或提交失败时，把状态改为 `blocked`，记录失败信号、已尝试操作和解除阻塞所需条件；不要把失败票据标记完成。
7. 每次状态变化都立即写回同一个 `tickets.md`，然后重新计算执行前沿，直到没有可执行票据。

没有可执行前沿但仍存在必需的未完成票据时，把票据板状态改为 `blocked`，记录阻塞链和恢复入口，不要误判为收口完成。

不要仅因为进入下一张票据就清空上下文或启动 subagent。整板收口必须执行一次 `$code-review`；除此之外，只有用户明确要求、票据明确要求，或风险确实需要且仓库规则允许时，才增加委派或独立审查。上下文压缩或任务中断后，以票据板记录为准，从 `in-progress` 或第一个未完成前沿继续。

## 提交前审查与逐票提交

- 每次提交前只暂存本票据拥有的实现、测试和交付物，不把 `tickets.md` 混入逐票实现提交；逐票哈希在提交后立即回写，票据板及收口证据在整板结束时单独提交。
- 以待提交差异为输入，从“是否符合规格”和“是否符合仓库标准”两条轴审查 `git diff --cached`，并执行 `git diff --cached --check`。同时核对 `git status --short`，避免遗漏本票据新增文件。
- 发现问题时先修复、重新暂存并重跑受影响验证，再重新审查；不要带着已知审查问题提交。
- 审查通过后，在当前分支使用简体中文提交信息创建提交。默认一票一提交；确需合并逻辑组时，在相关票据执行记录中写明共同提交哈希和不可拆分原因。
- 提交成功后立即把哈希、提交主题和审查结论写回对应票据。提交钩子或 Git 错误导致提交失败时，把票据标记为 `blocked`，不要只留下“实现完成”。
- 用户明确要求不提交时，改为审查该票据的工作区差异，在执行记录中注明“用户要求不提交”；验证和审查通过后仍可标记完成。
- 每次暂存都排除任务开始前存在的无关改动。若任务改动与既有未提交 hunk 无法安全分离，停止该票据的提交并记录冲突，不擅自把用户改动纳入提交。

## 收口

- 所有实施票据完成后，执行票据板要求的全量测试、构建和必要的 runtime/浏览器验收。
- 使用开始执行时记录的 `HEAD` 作为 fixed point，对本轮已提交实现运行一次 `$code-review`。若用户明确要求不提交或当前环境无法运行该技能，则在主会话中对整板工作区差异完成同样的规格与标准双轴审查，并记录替代原因。
- 修复审查发现，重新执行受影响验证，审查待提交修复差异后再创建修复提交。仍有未解决的必需发现时，把票据板标记为 `blocked`，不要收口。
- 在收口章节记录实际验证、整板审查结论、未执行验证及原因、已知风险、遗留问题、各票据提交和工作区状态。
- 只有所有必需票据、必需收口验证、整板审查和当前提交策略均完成时，才把票据板状态改为 `completed`。
- 提交启用时，最后单独审查并提交 `tickets.md` 和任务拥有的收口证据，不混入无关工作区改动。
- 最终报告完成票据、阻塞或跳过票据、影响模块、验证结果、审查结论、提交哈希和下一步建议。
