# AI-First 平台判定准则

## 1. 目标重申

新平台的首要目标不是单纯重写旧平台，而是把仓库、模块和交付方式建设成“适合 AI 持续辅助开发，并逐步过渡到 AI 主导开发”的平台。

这意味着我们优先优化的不是功能数量，而是以下能力：

- AI 能快速定位改动边界。
- AI 能在小上下文内完成单个任务。
- AI 能在不依赖隐式知识的前提下完成验证。
- AI 能并行处理多个低耦合任务而不互相踩踏。

## 2. 判定准则

一个设计、模块、任务或阶段，只有同时尽量满足以下准则，才算符合 AI-first 方向：

1. **边界清晰**
   模块职责、入口、依赖和禁止修改区明确，AI 不需要跨越大量文件才能理解一项改动。

2. **任务可切小**
   单个需求可以拆成多个 15 到 60 分钟内可完成的小任务，每个任务都能独立提交、独立验证、独立回滚。

3. **局部可验证**
   每项改动都有尽量局部的测试、脚本、接口或 smoke 路径，AI 不需要依赖整仓人工联调才能确认结果。

4. **契约先于实现**
   模块接入、数据映射、迁移规则、API 输入输出先文档化，再实现，减少 AI 在隐式规则上猜测。

5. **低上下文负担**
   避免超大文件、跨层隐式耦合和多处同步手改；优先使用稳定目录、单一职责文件和可搜索入口。

6. **文档可执行**
   文档不仅说明“做了什么”，还要说明“从哪里入手、允许改哪里、如何验证、失败怎么看、回滚怎么做”。

7. **并行安全**
   不同 agent 可以围绕不同模块、不同文件集合并行推进，冲突范围可控，不依赖共享的隐式现场状态。

8. **可复制迁移**
   当前任务产物应能成为后续同类任务的模板，而不是只能完成一次性的手工特例。

## 3. 快速否决信号

如果出现以下任意两项，应优先判断为偏离 AI-first：

- 改一个点必须理解半个仓库。
- 一个任务同时混入重构、新功能和迁移。
- 主要验证方式依赖人工点击和口头说明。
- 关键规则只存在于人的记忆里，没有文档或固定入口。
- 同类工作无法复制，只能再次人工摸索。
- 一个 agent 改动很容易波及多个无关模块。

## 4. 对现状的判断

当前仓库没有明显偏离到错误方向，但重心曾偏向“把平台做完整”，而不是始终围绕“让 AI 更容易独立完成工作”。

前期成果中可直接保留的部分：

- 模块边界和契约文档。
- Host / Shell / SDK / Demo 的最小闭环。
- 验证记录、阶段文档和协作规则。

需要校准的部分：

- 把 AI-first 从隐含目标升级为显式一号约束。
- 把阶段目标从“完成某个功能”改成“产出可被 AI 复制的实现模板”。
- 把验证路径从“能说明清楚”提升到“能脚本化、能复跑、能局部验证”。

## 5. 很短的返工清单

### 必须调整

- 在项目主文档中明确“AI-first”为首要目标和阶段评判标准。
- 以后每个阶段都要说明：边界、任务切分、局部验证、可复制模板分别是什么。
- Phase 5 交付不能只有导入功能本身，还必须交付固定样本、映射规则、复跑步骤和验证记录。

### 建议调整

- 对已经落地的模块逐步检查是否存在超大文件、隐式耦合和缺少局部验证入口的问题。
- 后续计划和设计文档增加“AI 执行视角”小节，明确 agent 从哪里入手、禁改哪里、怎么验收。

### 暂时不需要大返工

- 已完成的 Phase 1 到 Phase 4 功能与文档主线。
- 现有模块划分、登录闭环、Demo 贯通、公共模块首版。

## 6. 对 Phase 5 的调整建议

Phase 5 仍然应该继续做，而且方向基本正确，因为“真实旧资产迁移 POC”天然适合检验 AI 是否能处理来源分析、映射、导入和验证闭环。

但口径需要调整为：

- Phase 5 的核心产物不是“导入了一个 Setting”。
- Phase 5 的核心产物是“形成一条 AI 能重复执行的旧资产迁移模板”。

因此当前 Phase 5 至少应额外强调：

- 样本冻结：明确首批固定样本，避免范围漂移。
- 映射冻结：明确字段映射和覆盖规则，避免实现时临场猜测。
- 执行冻结：通过固定 API 或脚本完成导入，避免大量人工步骤。
- 验证冻结：通过固定查询、测试或 smoke 路径证明结果。
- 扩展冻结：说明后续 `Dictionary`、`Enumeration` 如何复用本次模板。

一句话结论：Phase 5 不需要推倒重做，但需要从“迁移一个样例”调整成“做出第一条 AI 可复制迁移流水线”。
