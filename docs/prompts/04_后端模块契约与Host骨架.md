请在新平台中实现“后端 Host 骨架 + 模块契约第一版”，目标不是堆很多模块，而是建立一个可以承载后续最小可运行平台的后端主干。

## 一、开始前先阅读

请先阅读并遵守：
- `AGENTS.md`
- `Plan.md`
- `docs/scope-v1.md`
- `docs/module-contract.md`
- `docs/module-boundaries-v1.md`
- `docs/identity-lite-module-boundary-v1.md`

如果你发现当前任务会超出 `scope-v1`，请先收敛，不要擅自扩大。

## 二、这轮任务的核心目标

这轮只解决 3 件事：

1. 建立后端 Host 的最小启动骨架
2. 建立模块通过契约接入 Host 的基础能力
3. 为“最小登录能力”“权限能力”“Demo Module”预留稳定接入点

本轮不是要把所有模块都实现完。

## 三、本轮必须产出的内容

请优先实现以下内容：

### 1. Host 启动主干
- Host 启动入口
- 基础配置加载
- 基础依赖注入
- 健康检查或最小可访问接口

### 2. Kernel 和契约层
- Kernel 基础抽象项目
- 模块元数据契约
- 模块服务注册契约
- 权限声明契约
- 菜单声明契约
- 配置声明契约
- 迁移 / 导入声明契约

### 3. 认证与上下文预留
- 为 `Identity Lite / LocalAuth` 预留认证上下文接入点
- 为当前用户上下文预留统一访问方式
- 不要求本轮把登录实现完整做完，但接入点必须清楚

### 4. Demo Module 的后端接入样例
- 至少有一个最小模块通过契约注册到 Host
- 能证明契约不是纸面设计

## 四、本轮明确不做

这轮不要做：
- 完整身份平台
- 组织树
- 租户体系
- 文件服务
- 工作流
- 报表系统
- 旧平台资产导入
- 大量业务模块迁移

## 五、建议的目录与结构关注点

优先关注这些区域：
- `apps/host-api`
- `server/kernel`
- `server/sdk`
- `server/modules/Demo`
- 与 Host 启动、契约定义直接相关的测试目录

如果发现需要触碰很多无关目录，说明范围可能已经扩张。

## 六、实施要求

### 1. Host 责任必须清晰

Host 只负责：
- 启动
- 组合
- 模块发现与注册
- 认证上下文接入
- 路由、菜单、权限声明聚合的总入口

Host 不负责：
- 模块业务规则
- 权限判断细节
- 配置中心逻辑
- 审计写入逻辑

### 2. 契约必须可扩展

请确保契约设计满足：
- 模块新增能力时不需要改 Host 内部实现
- 契约表达的是声明式信息，而不是硬编码逻辑
- 后续 `Authorization / ConfigCenter / Audit / Demo Module / Identity Lite` 都能接进去

### 3. 兼容层要留口但不要落重实现

如果某些旧平台能力后续需要兼容：
- 本轮只预留接口或扩展位
- 不要直接把旧框架启动逻辑搬进来
- 不要把兼容代码混进 Kernel

## 七、建议的实施顺序

请按这个顺序推进：

1. 建立或确认 Host 启动入口
2. 建立 Kernel 基础抽象
3. 定义模块元数据和注册契约
4. 定义权限、菜单、配置、迁移声明契约
5. 预留认证上下文接入点
6. 用 Demo Module 做最小验证
7. 补最小测试

## 八、验证要求

至少执行：
- `dotnet build`
- 最小契约测试
- Host 能启动
- 健康检查或最小 API 可访问
- Demo Module 的后端注册可被观察到

如果能做更多，建议补：
- 模块注册列表接口
- 当前加载模块的可观察输出

## 九、最终输出格式

请在完成后明确输出：
- 本轮改了哪些项目和目录
- Host 是怎么接入模块的
- 契约包含哪些内容
- 认证上下文预留在哪
- Demo Module 如何证明契约有效
- 验证结果
- 剩余风险

## 十、常见误区

请避免：
- 一边做 Host，一边把授权和登录细节直接写死在 Host 中
- 先写死 Demo，再回头补契约
- 先把旧平台代码复制过来再“慢慢整理”
- 把迁移 / 导入接口做成空洞但不可扩展的占位
