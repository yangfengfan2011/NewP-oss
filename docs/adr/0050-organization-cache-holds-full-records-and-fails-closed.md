# 统一缓存基类承载完整组织档案与一致更新

状态：已接受并实施。来源：[讨论 #207](https://github.com/yangfengfan2011/NewP/issues/207)。实施规格：[Spec #208](https://github.com/yangfengfan2011/NewP/issues/208)。

组织缓存包含公司、部门、岗位、人员的全部当前档案字段和关系，包括停用记录；账号凭据、角色授权、认证会话与历史审计记录仍由各自模块管理，不纳入这组缓存。完整缓存保留在服务端，对外接口仍按权限和既有契约返回字段，不能因内部完整装载而扩大数据暴露范围。档案字段变更也需要维护缓存，容量和更新成本按完整档案评估。

各具体缓存继承统一缓存基类；基类声明缓存名称的抽象成员，由每种具体缓存自行定义名称，并统一用于缓存诊断与状态识别。基类负责初始化、重载、可用状态、自动重试、重复加载合并、更新与重载协调、完整结果原子发布以及耗时和失败诊断。组织缓存负责完整档案装载、关系校验、索引、变更影响计算和组织查询；权限检查、组织写入、数据库事务与会话撤销仍由业务应用服务拥有，并通过统一机制衔接缓存维护。

缓存维护统一接入服务端正式写入及事务提交生命周期，扩展现有事务执行基础的通用提交参与机制；数据库事务仍由统一事务执行器拥有，不建立可绕过其提交的缓存写入管道。模块装配时登记模型与缓存参与者关系，平台通过注册解析，不硬编码组织模型。正式资源或专用命令在写入前声明可能影响范围并建立协调，持久化层收集实际新增、修改、删除及所需前后状态；普通 CRUD、仓储保存、条件删除及专用命令均须接入，按钮、页面或 Controller 不负责显式刷新缓存。只拦截普通保存既不能覆盖绕过变更跟踪的操作，也不能证明外层事务已提交。

特殊数据库写入须在同一协调及事务内执行，并主动登记实际变更或可准确修复的影响范围，由统一流程处理；不能先独立提交再补刷新。主动维护明确区分事务内仅登记、等待统一提交发布，与无关联写入的独立刷新、自行协调读取和发布。自动收集、主动登记及独立刷新共用同一个缓存维护实现，复用索引、局部更新、原子发布和故障恢复，不向调用方暴露可变缓存集合，也不放宽全量重建例外。固定上述职责及接口语义，具体方法名称、签名和内部算法仍由真实切片确定。

读取方取得受保护的只读结果，不能直接修改缓存对象或集合；同一次读取使用同一份完整结果，避免档案、归属与索引来自不同状态。局部更新也必须把本次受影响记录及索引作为一致结果发布，不能逐个暴露中间状态；启动或重载的旧结果不能覆盖后来已完成的更新。并发局部更新不能因基于相同旧结果计算而丢失彼此已完成的变更；装载与恢复必须读取一致的数据集合，并与局部更新共用发布协调边界，恢复不能覆盖后来完成的更新或重放原业务写入。首期用真实 Organization 缓存验证共用基类，不为尚未出现的第二组缓存增加扩展点。

正常更新时，数据库提交到缓存发布之间，新的缓存读取短暂等待，完整新结果发布后继续；发布失败则返回暂不可用。已经取得完整结果的请求可以完成，不追溯撤回；协调必须覆盖提交与发布的交界，不能在提交后才开始阻断读取而留下旧结果可见窗口。具体协调方式及等待成本通过真实组织切片验证，不把管理读库路径扩展为全局数据库与缓存的一致快照承诺。

服务启动初始化时全量装载并重建缓存；日常组织数据变更一律局部更新，明确业务需要的场景（例如导入组织结构）允许全量重建，本决策不实施组织导入功能。运行中故障恢复优先局部修复；仅当无法可靠确定或修复受影响范围时，才允许全量重建恢复，不能把普通更新失败一律转成全量刷新。无论局部修复还是全量重建，恢复完成且校验通过前，依赖请求继续暂停。

首期缓存读取覆盖登录准入、人员与组织关系查询、业务通过 Organization 查询接口按标识读取完整档案，以及批量名称解析。Standard CRUD 管理列表、管理详情和通用组织树保留现有数据库读取，列表与树继续在数据库过滤和分页；这些是固定读取路径，不是缓存故障时的自动回源。缓存仍保存完整档案，所有正式组织写入均须维护缓存；固定数据库读取不豁免既有认证、组织准入或字段返回约束。

首次装载及关系校验成功前，组织缓存保持未就绪；加载失败时 Host 保留健康检查并报告故障，自动重试，普通登录与依赖组织缓存的请求暂不可用，加载并校验成功后恢复。LocalAdmin 的登录不依赖组织缓存，但访问组织数据仍受缓存可用性约束；该例外不豁免其自身的认证、会话验证或功能授权。

运行中组织缓存不可用时，暂停依赖该缓存的请求并返回服务暂时不可用，保留 Cookie，不因缓存故障撤销会话，并尝试自动恢复。恢复成功后重新检查真实准入资格；此前因停用或归属清空等原因已经永久失效的会话仍然失效。

首期不增加自动数据库回源路径，以减少两套读取路径的一致性复杂度；这一取舍接受缓存恢复期间依赖请求暂时不可用。沿用 ADR-0007 对不可验证与确定无效的区分：基础设施故障不是 ADR-0049 定义的准入资格中断，不得把加载失败伪装成空组织、未绑定人员或账号停用，也不得使用已知失效的旧关系放行请求。

数据库中组织变更与受影响旧会话永久失效仍按 ADR-0049 原子提交；事务失败时整次回滚。若数据库已提交而随后内存缓存发布失败，必须明确反馈“已保存，但组织数据暂时不可用”，把缓存置为不可用并自动恢复，暂停依赖请求；不得声称数据库已回滚，也不自动重试该次写入。缓存恢复不能重新激活已失效会话。

运行期间只支持通过正式系统写入路径变更组织数据并维护缓存；必须直接改库的维护操作应停服执行，重启后重新装载。首期不增加数据库轮询或变更捕获机制。停服直接改库后的旧会话处理暂不纳入本次范围，不新增统一撤销或资格中断检测机制；重启重建只读取最终数据，不能保证识别维护期间发生后又恢复的准入资格中断。ADR-0049 的会话失效保证适用于正式写入路径，不覆盖这种维护方式。

首期以 1 万人员、1 千部门作为代表性验证规模，包含多级部门和停用记录，使用完整档案评估内存、启动装载与更新成本。该规模不是产品数量上限，不据此宣称已达到性能目标；测量用于评估并优化已确定的启动全量重建、日常局部更新策略，不能据此自行把日常变更切换为全量重建。

实现边界：`NamedCache<TSnapshot>` 持有协调与发布；模块通过 `PlatformCommitRegistration` 登记模型，统一事务执行器收集实际变更。事务内 `RegisterChange` 仅登记，事务外 `RefreshAsync` 按 `PlatformCacheRecord` 范围读取并复用 `ApplyAsync/Publish`；调用方不能在已持有事务协调权时调用独立刷新。后台 `MaintainAsync` 在初载及故障信号后恢复，健康时不查询数据库。Host 通过 `IPlatformCacheStatus` 汇总就绪，Organization 自身约束其端点可用性。已保存但发布失败返回 `Persistence.CommittedCacheUnavailable`；提交尝试后无法确认提交或回滚结果时返回 `Persistence.CommitOutcomeUnknown`，封闭缓存并从数据库恢复，不能按失败自动重放。

缓存名称抽象与职责边界按上文执行；当前使用不可变集合与直接关系索引局部更新；代表性规模证据见[实施 Issue #214](https://github.com/yangfengfan2011/NewP/issues/214)，尚未约定性能通过门槛。回退缓存实现时必须保持数据库事实与 ADR-0049 的准入及会话失效规则；若增加回源或放宽故障处理，须显式重新评审读取一致性，不能隐式降级。
