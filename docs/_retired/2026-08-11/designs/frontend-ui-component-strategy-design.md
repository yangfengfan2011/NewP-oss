# 前端公共控件建设策略设计

## 1. 背景

当前前端已经具备：

- `Shell` 主壳与页面骨架
- `Demo`、`Authorization`、`ConfigCenter`、`Audit`、`Files` 等模块接入能力
- 一部分共享页面样式和页面结构约定

但 `frontend/packages/ui` 仍基本处于空壳状态，真实页面中已经出现：

- 原生按钮、输入框、表格等基础控件的重复使用
- 页面头、信息卡、状态徽标、面板等结构块的重复使用
- 配置编辑、权限状态展示等具有复合交互倾向的页面片段

因此需要一套统一口径，回答：

- 是否应先把所有前端控件做完，再开发功能模块
- 哪些控件必须先进入公共层
- 哪些复杂控件应跟随真实功能场景推进
- 什么时候一个控件应从“模块内实现”升级为“平台公共控件”

## 2. 目标

- 为前端控件建设提供统一的推进原则。
- 明确“先做基础控件，再跟功能补复杂控件”的分层策略。
- 给出一份可执行的第一批、第二批控件建设清单。
- 降低模块各自实现一套 UI 的风险，提升 AI 与人工协作时的复用效率。

## 3. 非目标

- 不在本设计中直接实现任何控件代码。
- 不在本轮尝试一次性构建完整设计系统或组件大全。
- 不提前抽象尚未被真实页面验证过的复杂复合控件。
- 不将模块专属业务编辑器直接定义为平台基础控件。

## 4. 范围

本设计覆盖：

- `frontend/packages/ui`
- `frontend/packages/shell`
- `frontend/modules/*` 中会逐步沉淀为公共层的通用控件与结构块
- 配套文档、示例与验证口径

## 5. 设计约束

- 公共控件必须优先服务真实页面，不做脱离使用场景的空转抽象。
- 控件抽象应优先保证低上下文、易理解、易验证，而不是追求参数完备。
- 基础控件与复合控件分层管理，避免把业务耦合带入最底层 UI 包。
- 任何进入公共层的控件都必须补最小示例、说明和验证方式。
- 一个控件如果只有单一业务场景且短期没有复用信号，不强制提前公共化。

## 6. 总体方案

### 6.1 方案比较

#### 方案 A：先把所有控件做齐，再做功能模块

问题：

- 很容易做出大量没有真实使用验证的控件
- 树、复杂表格、权限选择器等控件往往会在真实功能接入时重做
- 阶段目标会从“支撑功能建设”偏移成“做组件大全”

#### 方案 B：完全跟着功能现做现用

问题：

- 公共层长期空转
- 不同模块很容易重复造轮子
- UI 结构和交互风格会逐渐分叉

#### 方案 C：先做一批高复用基础控件，复杂控件跟功能走，但按公共标准沉淀

做法：

- 先建立最小公共控件层
- 让真实功能模块在这套基础控件上推进
- 复杂控件根据实际需求跟功能一同建设
- 一旦出现第二次复用，就升级到公共层正式收口

这是本次推荐方案。

### 6.2 选择理由

- 能尽快建立 `frontend/packages/ui` 的真实承接能力。
- 不会把 Phase 6 演化成一个脱离业务场景的“组件大全工程”。
- 符合当前仓库 AI-first 的小步交付、低上下文、可复验原则。
- 可以让复杂控件在真实页面里被验证后再稳定抽象。

## 7. 关键模型

### 7.1 控件分层模型

#### 第一层：基础原子/基础表单控件

优先进入公共层：

- `Button`
- `Input`
- `Textarea`
- `Select`
- `Checkbox`
- `Radio`
- `Switch`
- `Tabs`
- `Tag` / `Badge`
- `Modal` / `Drawer`
- `LoadingState`
- `EmptyState`
- `ErrorState`

#### 第二层：结构型页面块

优先沉淀为公共模式块：

- `PageHeader`
- `PageActions`
- `SummaryCard`
- `MetaBlock`
- `StatusBadge`
- `Panel`
- `PanelHeader`
- `PanelBody`
- `TableWrap`
- `FormInline`

#### 第三层：复合控件

不适合脱离真实功能提前全部实现：

- `Tree`
- `TreeSelect`
- 复杂 `Table`
- 权限矩阵
- 配置编辑器
- 筛选工具栏
- 文件上传器

### 7.2 升级规则模型

- 第一次使用：允许在模块内先实现，但命名、样式和结构应为后续抽取留出空间
- 第二次复用：必须评估并优先迁入 `frontend/packages/ui`
- 正式公共化：补 README、示例、使用约束和最小验证口径

### 7.3 目录模型

建议 `frontend/packages/ui` 至少形成：

- `components/`
- `patterns/`
- `styles/`
- `README.md`

其中：

- `components/` 放基础控件
- `patterns/` 放结构型页面块和高复用组合
- `styles/` 放共享 token、状态类名和布局约定

## 8. 核心流程

1. 先为 `frontend/packages/ui` 建立第一批基础控件与结构块。
2. 用这批控件支撑真实公共功能模块继续开发。
3. 在功能开发中遇到复杂控件需求时，先结合具体页面实现。
4. 一旦复杂控件出现复用或趋于稳定，再抽入公共层。
5. 每次公共化后同步补文档、示例和验证记录。

## 9. 接口与集成点

- `Shell` 应优先消费公共层控件和结构块，不继续累积新的私有通用样式实现。
- 模块页面优先使用 `frontend/packages/ui` 的基础控件与结构型页面块。
- Phase 6 的前端模板应直接依赖这套公共控件分层策略，而不是再生成一套模块内私有 UI 写法。

## 10. 风险

- 过早做全量控件，导致大量无效抽象。
- 过晚建设公共控件，导致模块页面越来越分散。
- 把业务复合组件误判成基础控件，导致公共层耦合上升。
- 只有代码，没有示例和约束，导致公共控件反而更难复用。

控制方式：

- 第一批只做高复用基础控件与结构块。
- 第三层复合控件必须跟真实功能一起推进。
- 控件第二次复用时才要求正式公共化。
- 公共化后必须伴随文档和示例。

## 11. 验证方案

### 第一批控件验证

- `pnpm build` 可通过
- 至少一个 Shell 页面与一个模块页面接入新公共控件
- 公共控件 README 与示例存在

### 第二批控件验证

- 至少两个页面或两个模块使用同一控件
- 复杂控件具备最小交互验证
- 模块内重复实现明显减少

### 模板联动验证

- 前端模板生成的示例模块优先使用公共层控件
- 不再默认生成大量模块内私有 UI 样式

## 12. 实施拆分建议

### Phase A：公共控件基础层

第一批必做控件：

- `Button`
- `Input`
- `Textarea`
- `Select`
- `Checkbox`
- `Switch`
- `Tabs`
- `Tag` / `Badge`
- `LoadingState`
- `EmptyState`
- `ErrorState`

第一批必做结构块：

- `PageHeader`
- `SummaryCard`
- `StatusBadge`
- `Panel`
- `TableWrap`
- `FormInline`

### Phase B：功能带动型复合控件

第二批按需控件：

- 轻量 `Table`
- `Modal` / `Drawer`
- `Pagination`
- `FilterBar`
- `KeyValueEditor`
- `PermissionSelector`

### Phase C：高复杂度控件按证据推进

第三批后置控件：

- `Tree`
- `TreeSelect`
- 复杂 `Table`
- 批量编辑器
- 上传器

## 13. 推荐结论

不建议先把所有前端控件一次性做完，再开始功能模块开发。

推荐路线是：

1. 先完成第一批基础控件和结构块
2. 立即回到真实公共功能模块开发
3. 在功能推进中按需补复杂控件
4. 对达到二次复用的控件执行正式公共化收口

这样既能避免继续散落式开发，也不会把当前阶段拖成一个脱离场景的组件库工程。
