# 连续交付与审查门禁

本门禁适用于连续实施多个 GitHub child issue、运行终局 `$code-review`、修复审查 finding，以及通过验收 Gate 关闭最终 child 或父 issue。GitHub 查询、回写和关闭操作遵循 `docs/agents/issue-tracker.md`；被调用 skill 负责单次技能流程，本文件负责 NewP 的交付顺序、审查收敛和关闭条件。

## 核心术语

- **执行范围**：本轮交付明确包含的 issue、起始基线、目标契约和非目标。
- **验收资产**：Acceptance Gate 使用的 runner、场景、Fixture、测试数据和环境/进程编排。
- **实质性验收资产开发**：新增验收场景类别、Fixture/测试数据模型，或环境/进程编排；既有场景内的 locator、等待条件和诊断修正不属于此类。
- **冻结候选**：计划内实现和首次验收已完成，commit 与 tree 已记录，并使用与该 commit/tree 一致的干净输入执行后续门禁的候选版本。
- **阻塞 finding**：必须在当前候选关闭前解决的问题。
- **后续 finding**：保留证据并进入后续 issue，但不阻塞当前候选关闭的问题。
- **封闭复审**：只核对原阻塞 finding、修复差异和完整 Spec 遗漏，不重新开放式扫描整个历史范围。

## 1. 固定执行范围

1. 查询 map、child、原生阻塞关系和实时 frontier，不以历史汇报代替当前 GitHub 状态。
2. 记录第一个纳入实施的 issue 开始前基线、允许实施的 issue 列表、设计或 ADR 来源、非目标和所需验收。
3. 每次选择下一票前重新查询 frontier；口头“完成”只触发代码、证据和关闭状态复核。
4. 对所需 Acceptance Gate 建立验收资产基线：把每项验收行为映射到精确命令、runner 场景、成功信号和负责的 child，并标出尚不存在或尚未跑通的资产。
5. 将缺失的单票行为验收资产归给最早使该行为可运行的 child；只有无法在单票完成时独立成立的跨票组合场景归终局验收 child。

完成条件：基线可解析，范围内 issue 与非目标明确，当前票无未关闭 blocker；所需 Gate 的验收资产映射完整，每个缺口都有明确归属。

## 2. 逐票实施

1. 一次只实施一票；工作流要求新上下文时，为该票使用新的实施上下文，并传入固定范围、依赖事实和验收条件。
2. 先建立可复现失败，再完成最小实现；运行定向测试、受影响集成验证和该票要求的 smoke 或真实基础设施验证。
3. 当前票使某项 Gate 行为首次可运行时，同票交付相应 runner/Fixture 增量，并运行该场景或最窄 Gate slice；已可独立证明的行为不推迟到终局票首次验收。
4. 提交前检查 diff 范围、生成物 `--check`、行尾、秘密和工作区状态，只提交该票拥有的文件或 hunk。
5. 逐票质量门禁使用测试、验收条件和待提交差异检查；完整双轴 `$code-review` 保留给冻结候选，除非用户明确要求单票完整审查。
6. 获得写权限后，回写实际命令、结果、提交哈希和已知限制，关闭 child，再重新查询 frontier。

完成条件：该票的验收条件有可复跑证据，首次可运行的 Gate 行为已有场景证据，范围提交存在，GitHub 状态与证据一致，工作区不含该票遗留差异。

## 3. Gate 先行、冻结候选并执行一次完整审查

计划内实现和验收资产完成后、关闭最终 child 或父 issue 前：

1. 确认任务范围差异已全部提交，验收资产不再需要实质性开发，并记录 baseline、候选 commit、tree、Gate-only 命令、验证输入和一次性资源状态。当前工作区存在用户既有修改时保留原地，并从候选 commit 创建独立干净 worktree 执行终局验证和审查。
2. 在该干净 commit/tree 上先运行 Gate-only。失败时回到对应实施切片完成定向 RED→GREEN，再只重跑受影响验证和 Gate-only；此时不启动完整 `verify.ps1`。
3. Gate-only 暴露实质性验收资产缺口时，候选尚未冻结；按第 1、2 节重新分配归属并完成资产。既有场景内的 locator、等待条件或诊断修正可在当前验收票收敛，但必须有定向测试并重跑 Gate-only。
4. Gate-only 转绿后记录冻结 commit/tree，并对同一输入使用 `scripts/verify.ps1` 运行一次全量 test/build；需要真实基础设施验收时通过 `-AcceptanceGate` 显式选择 Gate，把完整 verify 内的 Gate 重跑作为终局证据。
5. Standards 与 Spec 使用同一固定 baseline 和冻结候选；审查期间保持候选不变。
6. 对该冻结候选执行一次完整双轴 `$code-review`，保留两轴原始报告，不在报告阶段合并或掩盖 finding。

完成条件：Gate-only 与完整 verify 均通过并对应同一 commit/tree；两轴报告均已返回且对应该候选，审查期间候选未变化。

## 4. 分级审查 finding

完整报告之后单独执行交付分级。一个 finding 只有同时满足以下条件才阻塞关闭：

1. 由执行范围引入，或使本次需求无法安全成立。
2. 有稳定 RED、可重复命令、静态检查或明确调用链证据；不能只依赖理论可能性。
3. 严重度为 P0 或 P1：
   - P0：可利用的安全问题、秘密泄露、数据丢失或损坏、不可逆错误迁移，或关键平台不可用。
   - P1：确定违反已确认 Issue、Spec、ADR 或仓库硬规则，并影响认证、授权、迁移、数据完整性、必需验收或核心行为。
4. 可在已确认设计和当前任务边界内修复；若需要扩大公共能力，先进入“设计升级”。

P2/P3、预先存在的问题、理论强化、与执行范围无直接因果关系的问题，以及需要新增通用平台能力的改进，先做立项判断。只有在受支持且遵守现有工作流的场景中存在合法触发路径、有具体影响或明确目标，并且现有流程约束不足以控制风险时，才归类为“后续”；获得 GitHub 写权限后创建非阻塞 issue，否则在交付报告中保留拟建 issue。仅在违反既定执行约束、非支持场景或人为攻击假设下成立，只有稳定 RED 而没有立项必要性，或成本收益不相称的 finding，归类为“不立项”，记录理由且不创建 issue。

完成条件：每个 finding 都有“阻塞、后续、不立项或证据不足”的唯一分类、理由和复现证据；每个“后续”均通过立项判断，阻塞清单固定后再开始修复。

## 5. 批量修复并封闭复审

1. 将固定的阻塞清单作为一个修复批次，逐项执行 RED→GREEN 和定向验证。
2. 阻塞项全部转绿后，形成新的干净 commit/tree，先运行受影响验证和 Gate-only；失败时继续定向修复，不启动完整 verify。
3. Gate-only 转绿后冻结新候选，再对同一 commit/tree 统一运行一次完整 test/build、真实基础设施验证和最终 Gate。
4. Standards 只复审原阻塞 finding 和修复差异，报告范围内新引入的 P0/P1。
5. Spec 从原 baseline 到新候选做一次完整遗漏确认，只报告范围内 P0/P1。
6. 修复差异若引入新的范围内 P0/P1，只在该修复差异上继续定向修复和复审；原始全范围 Standards 不重新开放扫描。

完成条件：原阻塞 finding 全部关闭，修复差异没有范围内 P0/P1，完整 Spec 没有范围内 P0/P1，Gate-only 与最终完整验证绑定同一新的候选 commit/tree。

## 6. 设计升级

出现任一信号时，停止逐点修补并核对现有设计工件：

- 同一底层 seam 在连续两次审查中产生新的同类 finding。
- 修复需要新增或改变公共 Contracts/SDK、Host/Shell 受控入口、跨模块边界、元数据协议、持久化或迁移内核、安全信任模型。
- 当前修复会扩大到与执行范围不同的模块或通用平台能力。

现有设计明确覆盖时，记录对应条款和最小实现边界后继续。现有设计未覆盖时，选择以下一种可回退路径：撤回或关闭引入风险的当前改动；或者在获得授权后创建独立设计/实施 issue。由当前候选引入的 P0/P1 在解决或回退前仍保持阻塞；预先存在、理论强化或非当前范围问题进入后续 issue。

完成条件：设计覆盖、回退或后续 issue 三者之一有明确证据，当前任务不携带未决的范围扩张继续实现。

## 7. 长运行验证与子代理接管

启动长运行验证或交给子代理前，提供一个显式执行包：

- 工作目录、baseline、候选 commit/tree 和拥有的文件范围。
- 精确验证命令、预期阶段、日志路径和成功信号。
- 数据库连接默认由 Acceptance 按验收覆盖、开发覆盖、本地 Development 配置的顺序解析；执行包只记录非默认覆盖的来源名称和一次性 catalog，不传递、输出或落盘秘密值。
- 进程、浏览器、临时数据库和生成产物的所有权与 cleanup 方式。

同一工作区一次只运行一个 `scripts/verify.ps1` 或 Acceptance。终局验证以 `.codex-temp/verify/runs/<run>/result.json`、阶段日志和退出码为事实；MSBuild 子节点异常时同时读取清单中的 `msbuildDiagnosticPath`。超过同一阶段最近一次成功时长且日志无进展时，先核对精确进程、结果清单和日志尾部。已无归属进程或子代理无法恢复消息边界时，停止该 turn，由新上下文接管现有差异和已完成阶段，不从头重做。完整 verify 在末段 Gate 失败时按第 3、5 节回到 Gate-only 收敛，不直接重启完整 verify。

完成条件：命令结果与日志位置可复查，归属进程和一次性资源均已清理，接管时已完成步骤不会被重复执行。

## 8. 关闭与交付

关闭最终 child 和父 issue 前逐项确认：

- 实时 GitHub 状态和阻塞关系与预期一致。
- 最终候选 commit/tree 与 test/build、真实基础设施验证和 Gate 证据一致。
- 范围内阻塞 P0/P1 为零；后续 finding 已创建 issue 或记录为待授权项。
- 工作区、归属进程、临时 catalog 和其他一次性资源处于预期终态。

按依赖顺序先回写并关闭最终 child，再汇总并关闭父 issue。最终报告列出候选 commit/tree、实际验证、后续 issue、未执行项及复跑方式。

完成条件：GitHub 状态、提交证据、验证证据和本地终态四者一致。
