# 强约束元数据与代码内核执行标准

## 1. 目的

本文档是 `NewP` 仓库中“强约束元数据 + 清晰代码内核”执行层的正式入口，用来把已经分散在 `AGENTS.md` 与 [metadata-kernel-boundary.md](metadata-kernel-boundary.md) 中的边界约束收成一套统一引用口径。

它不替代 [metadata-kernel-boundary.md](metadata-kernel-boundary.md)，而是提供日常设计、评审和实现时的最小判断入口。

## 2. 适用范围

默认适用于当前仓库中所有涉及以下内容的新增设计与实现：

- 模块元数据定义与 authoring 链路
- `resources/**`、运行时投影视图与统一插件包格式
- `MetadataConfigCenter`、`ModuleMetadataStore`、`RuntimeViewMaterializer` 等相关内核实现
- 任何试图把执行语义下沉到元数据的扩展点

既有内容不要求一次性返工，但后续修改时应逐步对齐。

## 3. 核心执行规则

### 3.1 元数据只表达受控输入

- 元数据负责声明“它是什么、归谁、允许什么”。
- 元数据可以表达类型、作用域、来源路径、归属关系、版本兼容约束和静态校验前提。
- 元数据不承载多步骤流程、条件分支算法、冲突解决算法、装载顺序算法和回滚算法。

### 3.2 代码内核负责执行语义

- 装载、解析、校验、冲突检测、投影、生效切换和回滚恢复必须由代码内核承担。
- 遇到冲突时，优先显式失败并给出信号，而不是依赖静默覆盖。
- 不允许继续把“怎么执行”伪装成“元数据配置”下沉到解释层。

### 3.3 运行时视图不是长期真源

- `runtime/`、`public/` 等投影视图表达的是“当前生效结果”，不是长期 authoring 真源。
- 读取有效视图时可以优先读运行时结果，但保存 authoring 内容时应默认回到可提交源目录。
- “应用到运行时”应由内核显式触发，不应由 authoring 服务隐式改写投影视图。

### 3.4 隐式规则不是正式规则

- 不依赖复制顺序、默认覆盖或口头约定来决定最终有效状态。
- 如果存在覆盖语义，元数据最多只声明 owner、scope、override allowance 等静态边界。
- 最终是否允许覆盖、如何排序、如何切换，仍由内核代码与显式校验负责。

## 4. 统一判断口径

日常设计、评审和实现时，默认用以下 5 条判断：

1. 这段信息是在表达事实和边界，还是在表达执行过程。
2. 这项能力是否仍然可以在不读取隐式现场的前提下被理解和验证。
3. 冲突、覆盖、切换和回滚是否已经收口到可测试的内核行为。
4. 运行时目录是否只是结果视图，而不是被悄悄当成唯一真源。
5. 实现是否仍然依赖“最后复制进去就生效”之类的隐式语义。

如果答案偏向“执行过程、隐式现场、静默覆盖、运行时写回真源”，则说明它偏离了本标准。

## 6. 当前收口范围

本轮只做规则入口收口，不额外引入：

- 新的脚本校验
- 新的 CI 门禁
- 对既有全部文档的一次性回填
- 对现有实现行为的超范围重写

后续如果需要把本标准进一步接入模板、脚本或门禁，应以小步增量方式推进，不与当前规则收口混在同一轮改动中。
