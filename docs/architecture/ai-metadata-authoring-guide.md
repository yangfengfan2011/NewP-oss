# AI 元数据生成规范

## 1. 文档目的

本文档用于约束当前阶段的模型语义生成方式。

当前阶段：

- 不建设给人直接使用的元数据设计器
- 模型语义默认由 AI 生成或修改
- 生成结果进入版本库并接受人工审核
- 校验器、测试、迁移与 smoke 负责兜底

本规范服务于 `Phase 6.5` 的混合架构路线：

- 内核代码优先
- 结构语义强约束
- 持久化适配层独立

## 2. 适用范围

本规范适用于以下内容的 AI 生成与修改：

- `ModelDefinition`
- `FieldDefinition`
- `IndexDefinition`
- `ModelKind`
- 模块级模型定义集合

当前首批模块：

- `ConfigCenter`
- `Authorization`

## 3. 输入要求

让 AI 生成元数据前，至少要提供以下输入：

- 模块名
- 模型名
- 该模型是独立业务对象还是关系对象
- 字段清单
- 每个字段的业务含义
- 必填/可空要求
- 主键要求
- 唯一约束要求
- 查询热点或索引要求
- 是否需要标准审计字段

如果输入不完整，优先补这些信息，而不是让 AI 自行发明：

- 主键
- 唯一约束
- 实体/关系类型
- 审计字段策略

## 4. 输出目标

AI 生成结果必须落到统一模型语义契约，不允许绕开这一层。

当前统一目标是：

- `ModelDefinition`
- `FieldDefinition`
- `IndexDefinition`
- `ModelKind`

推荐输出形式：

- 仓库内 C# 强类型定义
- 可被测试直接引用
- 可被 EF Core 适配器直接投影

## 5. 核心规则

### 5.1 `Entity` 与 `Link`

以下情况优先使用 `Entity`：

- 有独立生命周期
- 可以独立创建、更新、删除
- 不是单纯关系中间表

例如：

- `ConfigItem`
- `Role`
- `Permission`

以下情况优先使用 `Link`：

- 主要用于表达两个对象之间的关系
- 自身业务含义弱于关系语义
- 常见于多对多中间表或关系表

例如：

- `UserRole`
- `RolePermission`

### 5.2 字段定义

每个字段至少要明确：

- `Name`
- `StoreName`
- `Kind`
- `ValueType`
- `StoreType`
- `Required`
- `IsPrimaryKey`
- `IsAuditField`

不允许只给字段名，不说明语义。

### 5.3 字段语义与存储类型分离

AI 必须区分：

- 业务/值语义
- 存储实现

例如：

- `ValueType = Text`
- `StoreType = string`

而不是把数据库方言直接写进业务语义层。

### 5.4 主键规则

- 每个 `ModelDefinition` 必须至少有一个主键字段
- 主键字段必须显式标记 `IsPrimaryKey = true`
- 不允许依赖“默认推断主键”

### 5.5 索引规则

索引只为明确场景生成，不允许无依据堆索引。

需要优先考虑索引的场景：

- 唯一业务编码
- 高频按键查询
- 典型关系表联合查询
- 配置覆盖查询

索引名必须表达意图，不要生成无意义名称。

推荐风格：

- `UX_Role_Code`
- `UX_ConfigItem_Key_Environment_Tenant`
- `IX_ConfigItem_Module`

### 5.6 审计字段规则

如果模型需要审计能力，AI 必须显式说明：

- 哪些字段属于审计字段
- 审计字段是否属于通用模板复用

不允许一部分模型带审计、一部分模型完全随机处理。

### 5.7 多数据库规则

AI 在模型语义层生成时：

- 不得直接写 `SqlServer` / `Oracle` / `MySql` 分支
- 不得把 Provider 判断混进业务模型定义
- 不得把方言细节上推到模块服务层

Provider 差异只能留给适配层和方言层处理。

## 6. 生成步骤

推荐让 AI 按以下顺序生成：

1. 先判断模型是 `Entity` 还是 `Link`
2. 列出字段及其业务语义
3. 标记主键与审计字段
4. 生成唯一约束与普通索引
5. 输出 `ModelDefinition`
6. 再输出对应的仓储或适配器代码

不要反过来先写 EF 映射，再回头猜模型语义。

## 7. 禁止项

AI 生成元数据时，禁止：

- 生成万能 JSON 大杂烩
- 把业务规则塞进模型语义定义
- 直接在业务层写数据库 Provider 分支
- 为了凑完整而虚构字段含义
- 没有主键就强行输出模型
- 没有查询依据却堆大量索引
- 让设计器概念提前侵入当前实现

## 8. 推荐提示模板

建议以后给 AI 的任务提示至少包含以下结构：

```md
请为模块 `<ModuleName>` 生成模型语义定义。

目标模型：
- 名称：
- 类型：Entity / Link
- 业务含义：

字段清单：
- 字段名：
- 含义：
- 是否必填：
- 是否主键：
- 是否审计字段：

索引要求：
- 唯一约束：
- 常用查询：

约束：
- 输出为 `ModelDefinition / FieldDefinition / IndexDefinition`
- 不要输出 Provider 分支
- 不要跳过主键
- 结果应适合后续 EF Core 适配器投影
```

## 9. 生成后验收

AI 生成结果提交前，至少要经过以下检查：

- 模型定义能通过 `ModelDefinitionValidator`
- 字段名无重复
- 主键存在
- 索引引用的字段存在
- `Entity / Link` 选择合理
- 业务层未引入数据库分支
- 后续适配器测试可以承接

如果是首批持久化模块，还应继续经过：

- 模块测试
- 迁移验证
- smoke 验证

## 10. 未来设计器边界

后续如果建设设计器，设计器只是新的输入方式，不是新的架构中心。

设计器必须遵守：

- 输出仍然落到当前统一模型语义契约
- 输出仍然进入版本库
- 输出仍然经过校验器、测试、迁移与 smoke
- 不绕开当前代码审查与回滚机制

也就是说：

- 现在是 AI 生成元数据
- 未来可以是设计器生成人类可编辑元数据
- 但两者最终都必须落到同一套平台契约上

## 11. 当前推荐实践

当前阶段的推荐工作流是：

1. 人给出模块背景、字段语义和索引要求
2. AI 生成模型语义定义
3. 人审核定义是否符合业务意图
4. 校验器和测试验证结构正确性
5. 再由 AI 或开发者继续生成适配器与仓储代码

这套流程优先保证：

- 结构语义先稳定
- 工具链后建设
- 当前推进速度不被设计器开发拖慢
